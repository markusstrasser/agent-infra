Actual title: `Uncertainty Decomposition for Clarification Seeking in LLM Agents`

Mismatch flag: no mismatch. The paper is exactly about uncertainty decomposition for clarification seeking.

**Mechanism**

1. Start from a ReAct-style interactive agent that emits reasoning, an action, and uncertainty fields at each step.

2. Split the usual single verbalized confidence score into two fields:
   `c_t`: action confidence, meaning confidence that the chosen action advances the task given the current task interpretation.
   `u_t`: request uncertainty, meaning whether the user goal is underspecified.

3. Elicit `u_t` before the action, using an anchored scale:
   `0`: fully specified goal.
   `0.5`: at least one relevant parameter is open and the user likely has an unstated preference.
   `1`: critical details are missing; many valid interpretations exist.

4. Use deterministic routing:
   if `u_t >= theta`, set action to `request_clarification`;
   otherwise execute the proposed environment action.

5. Append all fields to history:
   observation, reasoning, request uncertainty, request-uncertainty explanation, action, action confidence, action-confidence explanation.

6. Evaluate two things:
   clarification seeking: did the agent ask when the task was deliberately underspecified?
   fault detection: do uncertainty scores predict trajectory failure?

7. For trajectory-level fault detection, aggregate action confidence with `last`, `avg`, `min`, and geometric `product`; aggregate request uncertainty with `first`, `avg`, `max`, and product-style uncertainty aggregation.

**Why it works**

The causal claim is narrow: a single confidence score conflates two different causes of uncertainty.

Low action confidence can mean “the task is hard” or “the user did not specify enough.” Those require different actions. A separate request-uncertainty channel gives the model a representational slot for goal ambiguity, and the threshold makes that slot behaviorally binding by routing to clarification.

The paper’s stronger claim is that this operationalizes “underspecification uncertainty” for black-box LLM agents without logprobs, multi-sampling, training data, or white-box access. Skeptically: the evidence supports “prompted decomposition improves synthetic clarification classification,” not “the model has calibrated internal uncertainty.”

**Preconditions**

The method needs:

- An interactive agent loop where `request_clarification` is a valid action.
- Tasks where underspecification is real and user clarification can change the correct next action.
- A model that follows structured-output prompts reliably.
- A threshold policy; default `theta = 0.5`, though the paper shows threshold choice matters.
- A benchmark or runtime label for whether clarification was actually appropriate, if evaluating it.
- Enough context budget to carry uncertainty explanations in history.
- Acceptance of prompt-only verbalized uncertainty, despite known overconfidence.

It is weaker when:

- Asking clarification is not an allowed or useful action.
- The missing information cannot be supplied by the user.
- The model treats “any open parameter” as reason to ask, causing over-asking.
- The goal is fully specified but execution is hard; request uncertainty should stay low, action confidence may be low.
- Success/failure is confounded by trajectory length.

**Measured results**

Benchmarks and protocol:

- Standard fault-detection benchmarks: WebShop, ALFWorld, REAL.
- Clarification benchmarks: WebShop-Clarification, ALFWorld-Clarification.
- Clarification variants deliberately underspecify 50% of tasks.
- Each `(method, benchmark)` pair is run on 100 tasks.
- Methods: ReAct+UE, UAM, Proposed.
- Models: GPT-5.1, DeepSeek-v3.2-exp, GLM-4.7, Qwen3.5-35B, GPT-OSS-120B.
- No CIs, p-values, or bootstrap intervals are reported. Runs appear single-pass per task; only the length-proxy random surrogate is averaged over 50 seeds.
- Pre-frontier / transfer flag: these are not measured on OUR current frontier operating stack; GPT-5.1 is also behind the current frontier named in local guidance, so behavioral rates should not be treated as current-model constants.

**Limitations / failure modes / non-transfer**

- Synthetic underspecification: WebShop strips attributes/options; ALFWorld removes object or receptacle. That is useful for controlled labels but may not transfer to organic ambiguity.

- Binary clarification scoring is crude. It measures whether the agent asked, not whether the clarifying question was useful, minimal, or well-timed.

- Capability dilution: adding request-uncertainty reasoning competes with task reasoning. The proposed method improves clarification F1 but often lowers task success.

- Overconfidence remains. The decomposition does not calibrate action confidence; all methods overpredict success.

- Aggregation is a hidden hyperparameter. Product aggregation can mostly measure trajectory length.

- Request uncertainty is not a general failure predictor. Table 6 says `u_r` aggregations are systematically weaker for fault detection than `c` aggregations.

- Prompt-only mechanism depends on model compliance and structured-output reliability.

- No reported confidence intervals. With 100 tasks per method/benchmark and no repeated-run uncertainty, small differences such as GPT-5.1 WebShop-Clarification F1 0.143 vs 0.151 should not be overread.

- Non-transfer to OUR system: the paper studies benchmark agents with a `request_clarification` action and synthetic labels. OUR harness has real operator supervision, over-ask already measured as a blindspot, and many actions can be probed cheaply instead of clarified verbally.

**Integration into OUR system**

act-drain: applicable, but only as a classifier distinction, not a new policy maze. Add an analysis label separating “low action confidence” from “request underspecification.” Concrete bolt-on: when act-drain mines over-ask corrections, classify whether the ask was due to missing user intent or avoidable execution uncertainty. This directly targets the existing `over_caution=63 / over-ask` blindspot.

session-trace: applicable. Add a trace query/view for episodes where the agent asked a question before a cheap probe was available. Extract fields: user request, proposed ask, available cheap probe, eventual human correction. This gives real labels for whether clarification was justified.

skills/rules/hooks: limited applicability. Do not add a broad hook that forces `u_request` everywhere. Better bolt-on: a path-scoped rule for irreversible/taste-boundary actions: before asking the user, distinguish `request underspecified` from `action uncertain`; if action uncertainty can be reduced by a read-only probe, probe first. This is consistent with OUR “probe before action” rule and avoids worsening over-ask.

MEMORY: not a direct runtime integration. NOT-APPLICABLE as a standalone memory update because this is a paper mechanism, not yet a demonstrated local lesson. If later evals show fewer over-asks, store the resulting rule with trace links.

`/eval`: applicable and probably the right home. Build an eval from agentlogs: binary label “should ask user vs should run cheap probe/act.” Metrics: clarification precision, recall, F1, and task-success/latency cost. Baselines: current harness behavior vs two-channel prompt/rule. Acceptance should require improved F1 without increasing over-ask.

predict-then-falsify: applicable. Pre-register: “this change should reduce over-ask corrections in session traces by increasing cheap-probe-before-ask decisions, not by suppressing legitimate asks.” Falsifier: inspect traces where the new rule fired and check whether the mechanism was actually `request underspecified` vs `action uncertain`.

Workflow: applicable only for human-gated workflow stages. Concrete bolt-on: add a decision node before human questions in file-bus workflows: `missing_user_preference`, `missing_external_fact`, `missing_execution_state`, `irreversible_boundary`. Only the first and fourth justify asking; the second and third should route to tools/probes.

ToolSearch: applicable. Deferred-tool loading already creates ambiguity between “I do not know what tool exists” and “the user request is underspecified.” Bolt-on: before asking the user, ToolSearch should be queried when the uncertainty is tool/action uncertainty. Ask the user only when the desired outcome itself is ambiguous.

Overall integration verdict: use the representation, not the paper’s prompt wholesale. The useful local mechanism is the two-way split: “Is the request underspecified?” vs “Am I uncertain how to act?” That maps cleanly onto OUR over-ask problem. The benchmark F1 gains are encouraging but not enough to justify adding scalar `u_request` fields globally.
