**Mechanism**

1. Start from failed agent executions plus harness code/prompts/configs.
2. Convert heterogeneous traces into HTIR, a step-level intermediate representation.
3. Represent each recoverable step as a `TraceStep` with request, response, role, execution status, and artifact/state effect.
4. Add links between steps:
   - temporal links for order,
   - input-provenance links for copied/summarized/transformed/semantically reused evidence,
   - control-flow links for why the harness advanced, retried, delegated, validated, finalized, or terminated.
5. Build node-local diagnostic evidence for each step: provenance evidence, control-flow evidence, artifact/state-effect evidence.
6. Map each candidate step to ETCLOVG harness layers: Execution, Tooling, Context, Lifecycle, Observability, Verification, Governance.
7. Diagnose failures by localizing the symptom, backtracking evidence, adjudicating responsible steps, and assigning implicated harness layers.
8. Consolidate repeated diagnosis records into flaw records grouped by layer and shared root cause.
9. Map flaw records to scoped repair operators, such as tool-schema narrowing, context-budget checking, verification-gated finalization, state-delta logging, or governance approval gates.
10. Generate a flaw-specific repair spec: allowed files/artifacts, forbidden resources, required behavior, validation metric, regression bound.
11. Generate candidate harness patches.
12. Validate patches with pre-validation checks and held-out validation tasks.
13. Accept only if target flaw occurrence drops and newly introduced regressions stay under bound.
14. Store accepted/rejected repair outcomes as harness repair memory.

**Why it works**

The causal claim is: agent failures often come from harness mechanisms, not just model reasoning. Outcome-only optimization sees final score but misses where the evidence was lost, hidden, malformed, or unvalidated. HTIR makes trajectory evidence attributable to concrete runtime steps and harness layers. Scoped repair operators then reduce the patch search space to the layer that caused the failure. Regression-aware validation prevents local fixes from becoming broad harness regressions.

In short: trace-grounding improves diagnosis; layer mapping improves edit locality; repair specs constrain patch generation; validation protects against Goodharting the target flaw.

**Preconditions**

The method needs:

- Raw execution traces with enough request/response/tool/environment detail to reconstruct step evidence.
- Access to harness artifacts: prompts, tool specs, orchestration code, config, logging, validators.
- A task evaluator or external failure signal.
- Enough failed trajectories to consolidate recurring flaw records, not one-off noise.
- Validation tasks separate from training/adaptation tasks.
- A target-flaw metric that can be recomputed on new trajectories.
- Regression checks over tasks previously solved by the original harness.
- LLM agents capable of trace abstraction, diagnosis, repair generation, and validation.
- Editable harness surfaces; this is not useful if only the prompt can change.
- Reliable artifact/state-effect observation where the flaw involves side effects.

**Measured results**

Main model: `openai/gpt-5-mini` across all benchmarks. Flag: non-frontier / pre-frontier relative to current frontier-class systems, so behavioral rates should not be assumed to transfer.

Benchmarks and splits:

- SWE-Bench Verified: 100 train / 50 validation / 100 test.
- Terminal-Bench 2.0 Verified: 34 train / 17 validation / 34 test.
- GAIA: 60 train / 30 validation / 60 test.
- AppWorld: 90 train / 45 validation / 90 test.

Primary metric: held-out test task success. No confidence intervals, p-values, repeated-run variance, or seed sensitivity are reported in the text I read.

Held-out test gains over selected initial harness `H0`:

- SWE-Bench Verified: `45/100` to `57/100`, 45.0% to 57.0%, relative improvement 26.7%.
- Terminal-Bench 2.0 Verified: `6/34` to `9/34`, 17.6% to 26.5%, relative improvement 50.0%.
- GAIA: `26/60` to `37/60`, 43.3% to 61.7%, relative improvement 42.3%.
- AppWorld: `33/90` to `38/90`, 36.7% to 42.2%, relative improvement 15.2%.

Against strongest human-designed baseline:

- SWE: HarnessFix `57` vs Trae-Agent `48`.
- TB2: HarnessFix `9` vs OpenCode `7`.
- GAIA: HarnessFix `37` vs MiroFlow `35`.
- AppWorld: HarnessFix `38` vs CUGA `37`.

Ablations on held-out test:

- Prompt-only: SWE `48`, TB2 `6`, GAIA `30`, AppWorld `34`.
- Without trace-grounded diagnosis: SWE `50`, TB2 `7`, GAIA `31`, AppWorld `34`.
- Without scoped repair operators: SWE `49`, TB2 `6`, GAIA `30`, AppWorld `34`.
- Without regression-aware acceptance: SWE `53`, TB2 `8`, GAIA `33`, AppWorld `35`.
- Full HarnessFix: SWE `57`, TB2 `9`, GAIA `37`, AppWorld `38`.

**Limitations / failure modes / non-transfer**

The paper gives no CIs or statistical uncertainty; TB2’s held-out test is only 34 tasks, so `6 → 9` is three tasks. AppWorld’s gain over CUGA is one task. Treat those as suggestive, not decisive.

The method depends on trace richness. If logs do not expose tool errors, state deltas, prompt construction, or finalization logic, HTIR attribution becomes guesswork.

The repair loop itself uses LLM agents. The paper does not deeply quantify diagnosis false positives, patch overfitting, or validator error.

Validation thresholds `δmin` and `rmax` are defined conceptually but not concretely reported in the visible text.

Some accepted edits are benchmark-specific, such as preferring official `/tests` or adding AppWorld API checks. That is fine for benchmark harnesses but may not transfer directly to open-ended local workflows.

The method assumes editable harness code. It is weaker for closed hosted agents where only user prompts or tool descriptions can change.

No token/cost accounting is reported, despite multiple LLM agents and repeated validation. That matters for OUR system because token cost is a first-class eval axis.

The result is not a reason to adopt the framework as a dependency. It is a mechanism paper: extract HTIR-style trace normalization, flaw records, repair specs, and regression-aware acceptance.

**Integration into OUR system**

session-trace / agentlogs.db: bolt on an HTIR-derived view over existing cross-vendor session logs. Start with `TraceStep(id, vendor, role, request_ref, response_ref, status, effect_kind, resource_ref)` plus provenance/control-flow link tables. Do not stand up a new DB.

act-drain / blindspot loop: replace flat correction mining with recurring flaw records: `{failure_signal, responsible_step_refs, implicated_surface, root_cause, count, representative_sessions}`. This directly addresses accretion by grouping rules/hooks by diagnosed recurring flaw instead of appending one rule per anecdote.

skills/rules/hooks: add a repair-operator taxonomy for local surfaces: tool-schema narrowing, failure-tail preservation, verification-gated finalization, delegated-output validation, read/write tool separation, prompt/rule de-duplication. Use it to choose the smallest structural fix, not to auto-generate broad policy.

MEMORY: add first-class links from condensed memory entries back to raw `agentlogs.db` session/turn/tool-call IDs. The paper’s provenance links map cleanly to this; memory without raw trace links is weaker than HTIR.

`/eval + ~/Projects/evals`: implement harness-edit evals as frozen-model comparisons with held-out traces/tasks. Measure success, target-flaw occurrence, regressions, and token cost. This is the home for the paper’s validation-set assessment.

predict-then-falsify: direct fit. Before accepting a harness/rule/hook change, pre-register: target flaw, expected trace-level mechanism, metric, regression bound. Accept only if the post-change trace shows the mechanism fired and the target flaw dropped.

Workflow tool / file-bus just recipes: map the paper’s pipeline into a local recipe chain: `trace-compile -> diagnose -> consolidate -> repair-spec -> eval -> accept/reject`. Single-writer-many-readers is compatible with our file-bus model.

ToolSearch: partial fit. Use HTIR diagnoses to improve deferred-tool retrieval only when the flaw is tool discovery or tool-menu overload. NOT-APPLICABLE as a general integration surface; most paper mechanisms target trace diagnosis and harness repair, not lazy tool loading.

NOT-APPLICABLE: adopting HarnessFix as a hosted framework or dependency. The primer rejects hosted runtime/server/DB stand-up, and the paper’s useful part is the representation and acceptance discipline, not the package.
