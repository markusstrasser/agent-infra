**Mechanism**

1. Start with an agent policy trained by GRPO and a skill bank.
2. For each task, GRPO samples a group of rollouts under the same task and current policy.
3. RESKILL assigns each rollout in the group to either `Snew` or `Sold` using Thompson Sampling over Beta posteriors.
4. The rollout then does triple duty: it contributes GRPO policy gradients, enters an experience reservoir, and updates the old-vs-new skill posterior from reward.
5. The reservoir stores tagged success/failure trajectories by skill version.
6. A skill creator pipeline grades failures with dynamic rule-based assertions, clusters failure modes, and proposes ADD/MODIFY/DELETE skill operations.
7. Each skill has compact structured content: `when_to_use`, `action`, examples, plus deterministic trigger type: `general`, `beginning`, or `action_pattern`.
8. Proposed action-pattern triggers are validated against the reservoir; default required trigger coverage is `δtrig = 0.5`, with up to 3 rewrite attempts.
9. Every `Ke = 5` steps, the system accepts `Snew` if posterior mean `E[pnew] > E[pold]`; otherwise it rejects and keeps `Sold`.
10. Posterior evidence is adaptively discounted with `wt = (1 + nt/M)^-1`, where `M` is estimated by predictive likelihood over completed A/B cycles.

**Why it works**

The causal claim is not “skills help” generically. It is: skill creation must be evaluated inside the same policy-learning loop because the policy is non-stationary. External or auto-accepted skill updates can conflict with the evolving policy.

GRPO’s within-group structure gives a controlled comparison: same task, same policy snapshot, different skill version. That makes reward differences more attributable to skill version than ordinary between-task comparisons.

Adaptive Thompson Sampling is claimed to solve two pressures at once: keep exploring both skill versions enough to estimate value, but allocate more rollouts to the version that currently appears useful so training budget is not wasted.

Assertion-based diagnosis is claimed to work because reservoir-wide rule checks produce stable failure profiles; direct per-episode LLM diagnosis is noisier and less targeted.

**Preconditions**

Requires verifiable environment rewards. The method depends on binary or scalar task reward to update GRPO and skill-version posteriors.

Requires grouped rollout training, specifically GRPO-like same-task rollout groups. Without within-group sampling, the controlled comparison mechanism disappears.

Requires enough rollout volume per evaluation cycle for old/new skill posterior estimates to mean anything.

Requires skills to be conditionally loadable and triggerable. The paper’s implementation assumes deterministic trigger evaluation plus in-context `when_to_use` filtering.

Requires a skill creator model or agent capable of reading trajectories and writing structured skills. The main experiments use `Claude Sonnet 4.5 API`; base-model skill creation is ablated.

Requires per-domain tuning or adaptation of evolution frequency. The paper says `Ke = 20` degraded ALFWorld because the policy adapted to a fixed skill context and later updates caused distribution shift.

Requires the base policy to use skills as guidance, not executable actions. The authors observed smaller models sometimes emit skill names as environment commands or over-apply inapplicable skills.

**Limitations / failure modes / non-transfer**

This is an RL training method, not an inference-only harness recipe. Direct transfer to OUR system is limited because OUR system is a local single-operator harness, not a hosted RL training service.

No extra rollout budget is claimed, but compute is still substantial: examples use Ray/VeRL, `1-2` nodes with `8×A100` each. That is not a natural bolt-on for OUR subscription-dispatch local harness.

Reward must be verifiable. The method does not solve taste, architecture judgment, or open-ended synthesis where the verifier is partial or human-owned.

Auto-accepting skills is actively harmful in their ablation: ALFWorld drops to `62.7±0.2`, below vanilla GRPO `75.3±3.7`.

Evolution frequency is fragile. Too-low frequency causes policy adaptation to stale skill context and later distribution shift.

Skill invocation can overload smaller models. Observed failures: treating skill names as environment actions, and over-applying skills when irrelevant.

The reported gains may depend on benchmark structure with binary rewards, short action spaces, and grouped rollouts. Do not inflate to “skills improve all agents.”

The paper reports mean/std over 3 seeds but no CIs and no independent replication in the text.

**Integration into OUR system**

`skills/rules/hooks`: applicable. Concrete bolt-on: add a “candidate skill/rule version” lifecycle where every new rule/skill proposal carries trigger conditions, expected activation surface, and accept/reject history. Do not auto-promote prose rules from observations without a tested mechanism.

`act-drain`: applicable. Concrete bolt-on: replace monotonic rule accretion with RESKILL-style ADD/MODIFY/DELETE recommendations from correction clusters, plus explicit reject/prune decisions. This directly targets the primer’s measured accretion failure mode.

`predict-then-falsify`: strongly applicable. Concrete bolt-on: every proposed hook/rule/skill must pre-register the trace signature it should move, then accept only if session-trace evidence shows the mechanism fired. This is the non-RL analogue of accepting `Snew` only when reward posterior beats `Sold`.

`session-trace`: applicable. Concrete bolt-on: use agentlogs as the experience reservoir. Store paired examples around human corrections: success/failure, old/new rule active, tool sequence, and outcome. Needed for controlled comparison and later forensic rejection.

`MEMORY`: applicable but only as linked condensation. Concrete bolt-on: every condensed lesson should link back to raw session-trace spans and carry lifecycle status: proposed, active, rejected, pruned, superseded. This addresses the primer’s “condensed→raw link is not first-class” issue.

`/eval`: applicable. Concrete bolt-on: build a small harness-edit eval that compares old vs candidate rule/skill on historical trace replays or synthetic task slices, with token cost as a tracked axis. This is not GRPO, but it preserves the paper’s controlled old/new comparison.

`Workflow`: partially applicable. Concrete bolt-on: file-bus recipes can run the candidate lifecycle: mine failures → propose ADD/MODIFY/DELETE → run replay eval → promote/reject → journal. Keep single-writer-many-readers.

`ToolSearch`: applicable. Concrete bolt-on: treat deferred tools like conditional skills: add trigger metadata, observed activation rate, success/failure snippets, and prune or down-rank tools that trigger but do not improve task completion. Avoid global eager loading.

`act-drain / over-ask`: applicable. Concrete bolt-on: mine over-caution corrections into assertions such as “asked despite cheap reversible probe available,” then test a candidate rule/hook against future traces. This maps directly to the primer’s `over_caution=63 / over-ask` blindspot.

NOT-APPLICABLE: adopting RESKILL as a dependency or training framework. The primer rejects hosted runtime/server/DB stand-up and framework adoption; the right move is mechanism extraction: versioned skill/rule candidates, controlled old/new trace comparison, adaptive promotion, and pruning.
