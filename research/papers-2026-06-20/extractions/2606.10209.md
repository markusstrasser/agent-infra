**Mechanism**

1. The agent runs a long tool-using workflow where tool responses are verbose D365 F&O form snapshots.
2. Before each agent inference, the harness reconstructs context from full message history `H`.
3. It counts tool messages and computes how many old tool call/response pairs exceed the keep window `N`.
4. It evicts the oldest tool messages plus their preceding assistant tool-call messages as whole semantic units, not token-level fragments.
5. For pruning-only mode, it keeps the last `N=5` tool call/response pairs and discards the rest.
6. For pruning + summarization, it keeps the last `N=5` tool pairs and summarizes the most recent evicted window `W=3`.
7. The summary is inserted as a single “Summary of previous tool calls” message at the earliest evicted position.
8. The retained raw tool calls provide current local state; the summary provides global task progress.

Configurations:

- `C1`: GPT-5 only, no user model, no context engineering; motivating ablation.
- `C2`: GPT-5 + GPT-4.1 user model, full context; baseline for context engineering.
- `C3`: GPT-5 + user model, last 5 tool pairs only.
- `C4`: GPT-5 + user model, last 5 tool pairs + summary window 3.

**Why it works**

The causal claim is that in tool-heavy workflows, full history is not just expensive; it can be harmful because older tool responses describe stale form states. Keeping them in context causes the agent to act on superseded balances, fields, or snapshots.

Pruning removes stale-state noise and focuses attention on the current form state and recent actions. Summarization restores the part pruning loses: task-level progress, such as which lines have already been added and whether reconciliation is near completion. The paper’s intended mechanism is therefore two-channel context:

- recent raw tool calls = current local state;
- compact summary = global task progress.

The failure taxonomy supports this mechanism directionally: stale-state references drop sharply under pruning, while premature termination rises under pruning-only and then drops under summarization.

**Preconditions**

This should transfer only if most of these hold:

- The workflow is single-session, tool-heavy, and long enough that tool responses accumulate.
- Tool responses are verbose and contain stale state snapshots.
- The next action depends mostly on recent state, not exact long-range transcript details.
- Older details can be safely summarized at task-progress level.
- There is an external verifier/read-back metric, not reliance on agent self-report.
- Tool call/response pairs are clean semantic units that can be evicted whole.
- The task has a hard completion criterion, here remaining amount exactly `$0.00`.
- The harness controls context construction before every inference.

It is weaker or non-transferable for tasks where old transcript evidence must remain exact, where the summary can erase legally/audit-relevant details, where long-range dependencies are semantically load-bearing, or where the “current state” is not reliably represented in recent tool outputs.

Primary benchmark: 50 hotel expense itemization tasks in D365 F&O, averaged across 5 independent runs, so 250 pooled task-runs for the main binary metric. Main agent: GPT-5. User model for C2-C4: GPT-4.1, which is a secondary non-frontier/control component relative to GPT-5 in the paper. Cross-model check: Claude Sonnet 4.5, without user model.

**Limitations / failure modes / non-transfer**

- Narrow workflow: D365 F&O expense itemization, not general agent autonomy.
- Internal enterprise environment; external reproducibility is limited from the provided text.
- The task has unusually clean verification: read saved form state, compare to ground-truth purchased items, require zero residual.
- C1 is not a valid context-engineering baseline because it also removes the user model.
- The GPT-5 stalling behavior is model-specific; Claude Sonnet 4.5 does not require the user model in their setup.
- Remaining failures are not solved by context engineering: wrong subcategory mapping, duplicate/skipped repeats, navigation errors, enum mismatches, arithmetic/residual errors.
- Free-form summarization can omit exact details; the paper’s summary is intentionally generic and does not compute a running balance.
- Summary window and pruning window were tuned for this task structure; `N=5,W=3` may not fit tasks with longer-range dependencies.
- Full-history summarization gets 92.0% like `W=5`, but costs more tokens than `W=3`; not worth adopting without a separate reason.
- Non-transfer to governance/audit contexts where old exact evidence is load-bearing. For OUR system, do not prune raw agentlogs, decisions, constitution evidence, or append-only memory; summarize only as an index over retained raw records.

**Integration into OUR system**

act-drain / blindspot loop: applicable as an anti-accretion mechanism, but not as a blanket rule-pruner. Bolt-on: when act-drain proposes rules/hooks from corrections, keep raw correction records in agentlogs, but present the operator with “last N relevant correction clusters + compact prior cluster summary” instead of an ever-growing flat policy maze. Use predict-then-falsify to require the summary to name which raw session IDs it condenses.

session-trace / agentlogs.db: directly applicable. Bolt-on: add a replay view that constructs trace context as recent tool spans plus a generated “prior tool/action summary” linked to raw span IDs. This should be a display/query layer only; never delete or mutate raw agentlogs. The paper’s semantic unit maps cleanly to our `tool_calls`/session spans.

skills/rules/hooks: applicable as a rule-surface design pattern. Bolt-on: path-scoped skills/rules should expose a recent/relevant working set plus condensed prior rationale, not load flat historical lists. Hook candidate: warn when an auto-loaded rule file grows by accretion without a generated index or scoped retrieval surface. Do not use the paper as evidence to delete governance text.

MEMORY: applicable, with caution. Bolt-on: make condensed memory entries first-class links to raw agentlog/session-trace evidence. The primer says the condensed→raw link is not first-class; this paper’s mechanism supports adding that link, not trusting summaries as standalone truth.

`/eval + ~/Projects/evals`: directly applicable. Bolt-on: run a local context-policy eval on frozen models over our own tasks: full trace vs last-N tool calls vs last-N + summary. Metrics should include task success, token cost, wall time, and mechanism-specific failure classes such as stale-state reference, over-ask, premature termination, and wrong-tool call. This belongs in `/eval` because the paper’s result is a harness claim, not a rule to import.

predict-then-falsify gate: directly applicable. Bolt-on: before any context-pruning harness edit lands, pre-register the intended mechanism: stale-state errors should drop without increasing premature termination beyond threshold; token cost should fall; raw trace recoverability must remain intact. Revert if the trace does not show the intended mechanism.

Workflow tool / file-bus just recipes: applicable for long-running pipelines and resume journals. Bolt-on: Workflow should pass scouts/workers a compact prior-step summary plus the last N file-bus events, while the file bus remains the source of truth. This can reduce stale resume context without losing auditability.

ToolSearch: applicable by analogy. Bolt-on: deferred tool surfaces should rank recent/relevant tool calls and expose compact capability summaries instead of loading large static tool inventories. The paper supports lazy semantic-unit retention; it does not support hiding available tools when exact tool affordances matter.

NOT-APPLICABLE surfaces: raw governance records, append-only decisions, constitution evidence, and audit ledgers. Those require exact historical evidence. The integration is summary-over-raw, never summary-instead-of-raw.
