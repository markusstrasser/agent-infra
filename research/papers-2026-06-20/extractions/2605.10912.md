**Mechanism**

1. Build a benchmark of 60 human-authored agent tasks across six categories: Productivity Flow, Code Intelligence, Social Interaction, Search & Retrieval, Creative Synthesis, Safety Alignment.
2. Package each task as a Markdown spec with YAML metadata, prompt, expected behavior, rubric, workspace path, optional skills/env vars, and an executable grading function.
3. Run each task inside an isolated Docker container initialized from a dedicated workspace.
4. Use real CLI agent harnesses rather than mock APIs: OpenClaw, Claude Code, Codex, Hermes Agent.
5. Give harnesses access to real tools: shell, browser/web, filesystem, email/calendar/chat services, image/video/audio tools, and optional task-specific skills.
6. Prevent leakage by mounting grading-only resources and ground truth after the agent exits.
7. Collect artifacts, conversation trace, runtime logs, tool calls, elapsed time, token/cost stats.
8. Grade with a hybrid protocol:
   - deterministic rule checks: file existence, schema/format, strings, numeric accuracy, byte-identical copies, required/forbidden patterns, workspace cleanliness;
   - environment-state audits: email/calendar/chat side effects, recipients, fields, attachments, safety refusals;
   - GPT 5.4 LLM/VLM judge only for semantic or visual checks that rule/state checks cannot resolve.
9. Filter candidate tasks by pilot discriminability: run a subset of frontier models, compute pairwise score gaps, retain only tasks with max pairwise gap at least `0.2`, then human-audit ambiguity, brittle grading, leakage, and reproducibility.
10. Analyze not just final scores but harness effects, time-budget effects, skill augmentation, tool-use profiles, bilingual gaps, variance across repeated runs, and failure modes.

**Why it works**

The causal claim is: agent capability is a joint property of model plus harness plus runtime plus tools plus grading protocol, not just a final answer from a model. Synthetic sandboxes and final-answer checks miss the actual failure channels in long-horizon agent work: wrong side effects, missing artifacts, timeout, toolchain/API disruption, unsafe command execution, plausible but semantically wrong outputs, and scaffold-specific recovery failures.

WildClawBench should therefore expose harder and more deployment-relevant failures because it forces agents to operate in native runtimes with real tools, long wall-clock horizons, multimodal assets, bilingual prompts, and auditable traces/artifacts. The paper’s harness-ablation result supports this mechanism: changing harness alone shifts the same model’s score by up to 18 points, so the scaffold materially affects measured capability.

**Preconditions**

- Tasks must be reproducible in isolated containers with pinned environment/tooling.
- Each task must have concrete artifacts or environment side effects to audit.
- Ground truth and grading assets must be unavailable during agent execution.
- Grading must combine deterministic checks with state audits; LLM/VLM judging should be limited to cases where exact checks are inadequate.
- Runtime traces must be retained: tool calls, logs, generated files, side effects, elapsed time, cost.
- Tasks must be long-horizon enough to stress orchestration; their reported budgets are 300-1200 seconds, mean 881 seconds.
- The harnesses must expose comparable tool-facing environments if model-vs-harness comparisons are intended.
- Human-authored rubrics and reference answers must be high quality; otherwise hybrid grading can just encode subjective or brittle errors.
- For score stability claims, repeated independent runs are required. The paper only reports this for four representative models with three runs each.

**Measured results**

- Benchmark size: 60 tasks; 36 English, 24 Chinese; 26 multimodal, 34 pure text.
- Categories: Productivity Flow 10, Code Intelligence 12, Social Interaction 6, Search & Retrieval 11, Creative Synthesis 11, Safety Alignment 10.
- Runtime/task length: time budgets 300-1200 seconds, mean 881 seconds. On Claude Opus 4.6, average wall-clock runtime is 8.5 minutes and 26 tool calls per task.
- Main OpenClaw evaluation: 19 models, 60 tasks. No CIs reported for Table 2.
- Best OpenClaw score: Claude Opus 4.7 at 62.2% overall, 58.5% multimodal, 65.0% pure text, 5.46 min/task, $1.29/task.
- Second: GPT 5.5 at 58.2% overall, 63.0% multimodal, 54.5% pure text, 4.37 min/task, $0.63/task.
- GPT 5.4: 50.3% overall, 40.2% multimodal, 58.0% pure text, 5.83 min/task, $0.33/task.
- Score range under OpenClaw: 19.3% to 62.2%, a 43-point spread.
- Harness comparison on four models:
  - GPT 5.4: OpenClaw 50.3, Claude Code 48.4, Codex 56.8, Hermes 50.7.
  - GLM 5: OpenClaw 42.6, Claude Code 31.0, Codex 38.9, Hermes 46.4.
  - MiMo V2 Pro: OpenClaw 40.2, Claude Code 29.9, Codex 35.3, Hermes 48.1. This is the cited 18.2-point swing from Claude Code to Hermes.
  - MiniMax M2.7: OpenClaw 33.8, Claude Code 32.0, Codex 35.8, Hermes 37.1.
- Skill augmentation, OpenClaw:
  - GPT 5.4 overall improves 50.3 → 55.5, while time falls 5.83 → 4.65 min and cost falls $0.33 → $0.30.
  - GLM 5 overall slightly regresses 42.6 → 42.5.
  - MiMo V2 Pro improves 40.2 → 43.9.
  - MiniMax M2.7 barely improves 33.8 → 33.9.
  - Skills improve Code Intelligence and Creative Synthesis for all four tested models, but hurt some categories, notably GPT 5.4 Social Interaction 87.6 → 39.1.
- Thinking-mode comparison for GPT 5.4 under fixed budget:
  - low: 6.07 min, $0.33, 50.4%, 4 timeout tasks.
  - medium: 6.94 min, $0.56, 52.6%, 7 timeout tasks.
  - high: 9.12 min, $0.81, 45.0%, 15 timeout tasks.
- Time-budget effect: halving budget sharply reduces scores; doubling gives diminishing returns. Exact reported example: GPT 5.4 improves from 50.3% to 56.5% with doubled budget.
- Tool-use profiles, average calls per trajectory:
  - Claude Opus 4.6: total 26.0, exec 13.5, process 3.2, web 3.8, author 2.3, image 1.7, read 1.5.
  - GPT 5.4: total 24.0, exec 11.8, process 3.1, web 1.5, author 0.7, image 0.8, read 6.0.
  - Kimi K2.5: total 28.7, exec 16.3, process 1.3, web 3.5, author 3.0, image 0.7, read 3.0.
  - MiniMax M2.7: total 31.4, exec 19.1, process 3.0, web 6.0, author 1.6, image 0.4, read 1.1.
- Failure-mode analysis: 300 OpenClaw runs across Gemini 3.1 Pro, GPT 5.4, Kimi K2.5, MiniMax M2.7, Opus 4.6; 169 failed runs, where failure means normalized score below 0.5. Failures often surface as wrong/partial artifacts rather than missing outputs. Process labels include safety-policy failure, time-budget exhaustion, code/debugging loop, toolchain/API breakdown, semantic/planning miss.
- Bilingual scores:
  - Claude Opus 4.6: overall 51.6, English 52.8, Chinese 49.8, gap +3.0.
  - GPT 5.4: 50.3, English 51.1, Chinese 49.0, gap +2.1.
  - Gemini 3.1 Pro: 40.8, English 41.1, Chinese 40.3, gap +0.8.
  - MiniMax M2.7: 33.8, English 36.8, Chinese 29.4, gap +7.4.
  - Kimi K2.5: 30.8, English 31.7, Chinese 29.5, gap +2.2.
- Repeated-run variance, OpenClaw, three independent runs:
  - Claude Opus 4.6: 51.6 ± 1.0 overall.
  - GPT 5.4: 50.3 ± 1.9.
  - Gemini 3.1 Pro: 40.8 ± 0.7.
  - MiniMax M2.7: 33.8 ± 0.9.
  - These are standard deviations, not confidence intervals.
- GPT judge validation: five LLM-as-judge tasks sampled; two independent human experts blind-scored outputs with same rubric; GPT 5.4 judge compared to human average. The paper reports deviations generally under 3 points, but no CI and very small sample. This supports local calibration only, not broad proof that GPT 5.4 is a reliable judge.
- Pre-frontier flag: main reported models are presented as 2026 frontier models in the paper. I would not label the main results pre-frontier as of the paper date, but they are still paper-reported vendor/model names and should be revalidated before using them as current model-ranking truth.

**Limitations / failure modes / non-transfer**

- Single-turn only: tasks start from one user instruction and do not model interactive clarification, mid-run correction, or follow-up.
- Coverage is limited: 60 tasks across six categories is useful for separation but thin versus real deployments. GUI-heavy desktop work and specialist biology/finance/law workflows are lightly represented or absent.
- The benchmark is bilingual English/Chinese, not multilingual broadly.
- Hybrid grading depends on rubric quality. The GPT 5.4 judge validation is narrow: five tasks, two human raters, no confidence intervals.
- LLM/VLM-as-judge remains a proxy. It is acceptable for bounded semantic criteria with rubrics, but not a ground-truth verifier for taste-heavy or high-stakes claims.
- Scores are harness-specific. The paper itself shows scaffold choice changes results, so WildClawBench numbers should not be treated as intrinsic model rankings.
- Some tasks use mocked participants/services for social interaction despite the “native runtime” framing; realistic enough for audit, but not real production email/calendar risk.
- Dockerized reproducibility may not transfer to local single-operator harnesses where host state, permissions, secrets, subscriptions, active peer agents, and long-lived repo dirtiness matter.
- Skill augmentation is not uniformly good. It can improve code/creative tasks but sharply regress other domains, so “add skills” is not a general solution.
- More internal reasoning can hurt under wall-clock constraints. This directly warns against defaulting to high-thinking modes for agent work with hard time budgets.
- The failure taxonomy is useful but coarse. Multi-causal failures are forced into priority labels for process view, so “toolchain/API disruption” versus “semantic miss” may hide interactions.
- Paper numbers should not be inflated: no CIs for main Table 2, only SDs for four repeated-run models, and many detailed per-task tables are single-run snapshots.

**Integration into OUR system**

- `/eval + ~/Projects/evals`: Applicable. Bolt-on: add a native-runtime eval template modeled on WildClawBench’s grading triad: deterministic artifact checks, environment-state/side-effect audit, and bounded semantic judge. Use our existing verifier-gated autonomy framing, but store per-run `score`, `elapsed_seconds`, `tool_calls`, `cost`, `timeout`, `artifact_paths`, and `failure_label`.
- `session-trace / agentlogs.db`: Applicable. Bolt-on: add a WildClaw-style run replay view over existing traces: final artifact outcome plus process labels such as `timeout`, `debug_loop`, `toolchain_api_disruption`, `semantic_planning_miss`, `safety_policy_failure`. This should be derived from raw transcripts/tool results, not hand-entered prose.
- `predict-then-falsify`: Strongly applicable. Bolt-on: before a harness/rule/skill change, pre-register the intended mechanism, e.g. “reduce over-ask by lowering clarification prompts in task class X without increasing wrong-artifact rate.” Accept only if session-trace shows the predicted mechanism moved, not just if aggregate score improves.
- `skills / rules / hooks`: Applicable but with caution. Bolt-on: evaluate skill additions by category and failure mode before promoting them. The paper’s skill table shows category regressions, so a new skill should have an eval card: where it helps, where it hurts, time/cost delta, and failure-mode delta. Do not globally load a skill because it improved one domain.
- `act-drain / blindspot loop`: Applicable. Bolt-on: change act-drain findings from flat “rules/hooks grow” proposals into benchmarkable hypotheses: each proposed rule/hook must name the failure label it should reduce and the trace signal that will falsify it. This directly attacks the primer’s measured accretion/policy-maze failure mode.
- `MEMORY`: Applicable. Bolt-on: first-class link from condensed lesson to raw trace/eval evidence. WildClawBench’s auditability point maps to our missing condensed→raw link. Store memory entries with pointers to `agentlogs` session ids, eval run ids, and artifact/check outputs; do not let MEMORY become unsupported summaries.
- `Workflow tool / file-bus just recipes`: Applicable. Bolt-on: add a reproducible eval recipe that runs one task pack through the same workflow path and emits a single run bundle: prompt, trace id, artifacts, checker output, failure label, cost, elapsed time. Keep single-writer-many-readers; no hosted service.
- `ToolSearch`: Applicable. Bolt-on: add a tool-surface eval subset where deferred tools are loaded lazily and grade whether the agent found the right tool, avoided irrelevant tools, and completed the task. Measure not just final answer but tool discovery trajectory and over-broad tool loading.
- `act-drain / blindspot loop` over_caution=63 / over-ask: Applicable. Bolt-on: add tasks where asking is explicitly unnecessary or harmful, then grade whether the agent acts directly. This imports the paper’s “side effects and trajectory matter” idea into our specific failure mode.
- `session-trace`: Applicable. Bolt-on: compute “wrong/partial artifact” separately from “missing artifact.” The paper’s key warning is that failures often look like plausible artifacts, so our trace review should not treat artifact existence as success.
- `skills/rules/hooks`: NOT-APPLICABLE for adopting OpenClaw/ClawHub as dependencies. The primer says we do not adopt frameworks as deps or stand up hosted runtimes. Pattern-extract the benchmark mechanics; do not import the ecosystem.
- `Workflow`: NOT-APPLICABLE for multi-agent hosted benchmark operation. Our system is single-operator local; the integration should be local eval harness recipes and trace bundles, not a benchmark service.
