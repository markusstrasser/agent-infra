**Mechanism**

EvoTrainer treats the trainer, not just the policy, as the object being improved.

1. It keeps a sequence of policy versions `v0...vn`. Each version produces artifacts: metrics, rollouts, configs, logs, and diffs.
2. A current training harness interprets those artifacts into a diagnosis, proposed intervention, and observed outcome.
3. It creates candidate branches from the current baseline, usually single-factor changes for attribution. Candidate changes can affect rewards, filtering, data, rollout settings, optimization, or tool-use behavior.
4. Branches are materialized as isolated worktrees, trained when resources permit, then compared.
5. Branches are kept, pruned, reverted, or merged. Failed and ambiguous branches remain as negative evidence.
6. The diagnostic harness also evolves when existing evidence cannot explain outcomes, distinguish hypotheses, or select the next intervention.
7. Harness upgrades occur through metric expansion, analyzer specialization, procedure revision, and external evidence retrieval.
8. Persistent memory stores version lineage, case memories, reusable skills, and search traces.
9. Validated skills can be retrieved later. Example: `StdGroupFilter`, developed in SWE for low-variance rollout groups, is reused in Math and Coding.
10. Humans bootstrap workspace/task/data/compute and approve costly or consequential actions; the trainer agent performs artifact analysis, harness updates, search/backtesting, and intervention proposals.

Concrete SWE instantiation: GRPO-style training with asymmetric Clip-Higher, weak KL to a fixed reference policy, group-relative advantages, and variance-aware group filtering. Final SWE reward is:

`1.0*CR + 0.1*IF + 0.1*SBE + 0.15*ETT`

where CR is hidden-test correctness, IF is frozen-judge instruction following, SBE is search-before-edit, and ETT is edit-then-test.

**Why it works**

The causal claim is that scalar score search is under-informative in agentic RL. Long-horizon agents can improve score for invalid reasons, regress while producing useful negative evidence, or expose new bottlenecks that earlier metrics could not see.

The paper’s theory is:

- Group-relative RL needs within-group variance; zero-variance groups consume compute without useful learning signal.
- Agentic SWE has behavior-level pathologies that score alone misses: Git leakage, echo traps, one-turn collapse, excessive repetition, no-edit trajectories.
- A training harness that evolves diagnostics, backtests proposed reward changes, and remembers validated mechanisms can make better branch-selection decisions than score-only iteration.
- Reusable operational skills transfer when they are abstracted at the right level. `StdGroupFilter` transfers because it depends on reward-standard-deviation structure, not SWE-specific reward semantics.

The strongest internal causal evidence is the natural-counterfactual table: score-only SWE-9B saturates at 33.33 BC%, while richer diagnostics/backtesting reach 38.16 BC%; Git-leak audit rejects an invalid 48.80 BC% branch; skill reuse changes Coding v8→v10.

**Preconditions**

- Runnable training versions with comparable artifacts: rollouts, metrics, configs, logs, diffs.
- A version-control workflow where candidate branches can be isolated and audited.
- Verifiable or semi-verifiable task feedback: Math judge, code execution, SWE hidden fail-to-pass tests.
- Enough rollout detail to compute signal and behavior metrics: reward variance, dead-group ratio, tool-use behavior, trajectory length, edit/test/search patterns.
- Trainer model must have strong long-context reasoning, repository/tool access, shell execution, and retrieval utilities.
- Humans remain in the loop for bootstrap and costly/consequential execution.
- Reward components must be backtestable or at least analyzable on historical rollouts.
- Persistent memory/skill storage must preserve not only prose lessons but operational mechanisms.
- Compute budget must tolerate iterative RL training plus large trainer-agent inference usage.

**Measured results**

Evaluation protocol: Avg@8 over 8 independent rollouts per item, single training seed 42. Math correctness uses frozen Qwen3.5-4B judge; Coding uses stdin/stdout execution; SWE uses BC%, the proportion of valid executions passing hidden fail-to-pass tests, excluding infrastructure failures.

Tasks/data:

- Math: train 6,429 BigMath-Hard problems; evaluate 78 problems: AIME 2024 n=30, AIME 2025 n=30, CNMO 2024 n=18.
- Coding: train 11,897 TACO-verified problems; evaluate 175 held-out LiveCodeBench-v6 AtCoder Beginner Contest problems.
- SWE: train 8,622 swe-rebench-v6 train instances; evaluate 77 held-out Python instances.

Main table:

- SWE-4B BC%: base 24.68, human RL 31.17, EvoTrainer 31.49.
- SWE-9B BC%: base 30.19, human RL 33.77, EvoTrainer 38.16.

Compute/accounting:

- Full workflow consumes about `4.0e8` trainer-agent tokens beyond RL training.
- SWE EvoTrainer retained versions: 15 total, 8 SWE-9B and 7 SWE-4B.
- SWE EvoTrainer training steps: about 3,000; GPU-hours about 92,800.
- Human-engineered RL: about 23 retained versions, 4,600 steps, 140,000 GPU-hours.
- Human used about 1.53x steps and 1.5x GPU-hours in SWE.

**Limitations / failure modes / non-transfer**

- Preprint, vendor-adjacent, and not independently replicated in the provided text.
- Trainer model is Claude Sonnet 4.6; results may not transfer to weaker or differently tooled trainers.
- Single training seed per version leaves training stochasticity under-measured.
- Humans still bootstrap the workspace and gate costly/consequential execution; this is bounded autonomy, not fully autonomous RL research.
- Runs span only 7 to 10 versions per domain; the paper explicitly leaves hundreds-of-version memory/skill-library pruning as future work.
- The framework is compute-heavy: RL training plus `4.0e8` trainer-agent tokens.
- Some baselines are not directly comparable because other autonomous experimentation systems target different search spaces/evaluators.
- Score improvements on SWE-4B and Coding do not statistically exceed human RL; they match it within CI.
- The Git-leak case proves diagnostics can catch one invalid promotion, but also shows the method is vulnerable if harness audits miss leakage.
- Reward shaping can create severe behavioral collapse: multiplicative efficiency reward drives SWE branches toward one-turn behavior and near-total dead groups.
- Non-transfer risk: mechanisms like group filtering transfer only when the underlying failure is structurally the same. A stored skill should not be applied just because names or domains match.

**Integration into OUR system**

Best integration: **predict-then-falsify gate** plus **session-trace / agentlogs.db**.

Concrete bolt-on: before accepting any harness/rule/hook/skill change, require a small “mechanism record” with:

- predicted failure class reduced,
- trace-level observable expected to move,
- exact query over `agentlogs.db` or session-trace spans,
- negative control,
- rollback criterion.

This directly maps EvoTrainer’s “intervention only counts if diagnostics/backtests support the mechanism” into our planned gate. It also attacks our known accretion failure: rules/hooks growing monotonically without proving the intended mechanism fired.

Second integration: **act-drain / blindspot loop**.

Concrete bolt-on: add retained negative-evidence cases, not only proposed improvements. When act-drain proposes a rule/hook, record sibling alternatives rejected and why, with a lightweight backtest against recent corrections. This pattern-extracts EvoTrainer’s failed-branch memory without adopting its framework.

Third integration: **skills / rules / hooks**.

Concrete bolt-on: convert reusable “operational skills” into typed skill objects with applicability predicates and validation probes. Example shape: `skill_id`, `failure_signature`, `required_artifacts`, `probe_query`, `accept_metric`, `known_bad_transfers`. This is better than a flat skill list because the paper’s useful transfer comes from structural match, not prose recall.

Fourth integration: **MEMORY**.

Concrete bolt-on: first-class condensed→raw links. The primer says this link is not first-class. EvoTrainer’s `Lver/Ccase/Sskill/Ssearch` argues that memory should point back to exact traces, diffs, and decisions. For us: every durable MEMORY lesson from act-drain should include agentlogs/session-trace ids and the query that recovers the raw evidence.

Fifth integration: **/eval**.

Concrete bolt-on: evaluate harness edits on a frozen trace corpus, measuring mechanism-specific deltas and token cost. This matches our “harness on a frozen model is the lever” principle. Do not use model-as-judge for taste; use it only where the trace observable is independently checkable.

Sixth integration: **Workflow / file-bus just recipes**.

Concrete bolt-on: add a version-ledger convention for workflow runs: candidate id, single-factor intervention, artifact paths, keep/prune/revert, and evidence query. Our file-bus already supports single-writer-many-readers; the missing piece is the branch/decision ledger.

Seventh integration: **ToolSearch**.

Concrete bolt-on: log deferred-tool retrieval traces as `Ssearch`-like records: query, tools surfaced, chosen tool, rejected tools, and downstream outcome. This would help distinguish “tool discovery worked” from “agent guessed a tool name” and would support later reuse.

NOT-APPLICABLE as a dependency: do not adopt EvoTrainer as a framework/runtime. The primer explicitly rejects hosted/runtime/DB stand-up adoption, and the transferable value is the mechanism: evolving diagnostics, branch lineage, negative evidence, skill applicability predicates, and trace-backed acceptance gates.
