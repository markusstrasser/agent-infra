**Mechanism**

Workflow-GYM is a benchmark construction and evaluation pipeline for long-horizon GUI agents:

1. Domain experts propose real professional workflows from daily work, not synthetic/public examples.
2. Tasks are filtered for realism, domain specificity, complexity, and verifiability.
3. The authors build reusable full-system VM environments for professional software versions, not containers or API mocks.
4. Each task injects task-specific files/configuration into a pre-launched software state.
5. Experts write a natural-language task instruction, expected final outcome, deterministic evaluation criteria, and hidden step-by-step atomic GUI procedure.
6. Tasks are validated by expert manual execution, expert + LLM instruction checks, and end-to-end agent trials to catch ambiguity/environment defects.
7. Agents receive only the task instruction, interact through GUI screenshots/actions, and have up to 400 interaction rounds.
8. Final evaluation is binary: produced artifact or final GUI state must satisfy criteria. Artifact tasks use rule-based or LLM-based checks; non-artifact GUI-state tasks use screenshots + VLM judging.
9. Failure analysis decomposes failures into outcome-level classes and process-level trajectory failures.

**Why it works**

The causal claim is that long-horizon professional GUI work stresses a different capability bundle than short GUI tasks: planning over many dependent steps, state tracking, software-specific procedural knowledge, visual grounding, and recovery from local mistakes.

The benchmark works as an evaluation because it tries to isolate agent behavior: shared reusable VM environments, task-specific initialization, hidden expert procedure, validated deterministic success criteria, and repeated trials. The paper’s theory is that professional workflows create tight inter-stage dependencies, so early small errors propagate; longer trajectories increase the chance of mis-clicks, omitted stages, drift, and unrecovered invalid states.

A second causal claim is about current GUI-agent architecture: snapshot observation-action loops are mismatched to human GUI manipulation. Humans use continuous visual feedback during drag/draw/align operations; current agents mostly see before/after screenshots, so they must guess, retry, and often loop.

**Preconditions**

Workflow-GYM’s claims depend on:

- Tasks being genuinely closed-world and solvable from the instruction plus GUI state.
- Expert procedures being correct and sufficient.
- Final criteria being deterministic enough for binary evaluation.
- VM environments faithfully preserving real GUI behavior and removing irrelevant blockers like login/auth.
- Judge models and rule checks matching the expert-defined criteria.
- Agent frameworks being reasonably adapted to each model’s action schema, coordinate system, and tool interface.
- The 400-round budget being adequate enough to compare agents without mainly measuring budget exhaustion.
- The benchmark task set being representative of economically meaningful professional GUI work.

For transfer into OUR system, the key precondition is different: our harness is mostly CLI/file/tool/workflow based, not GUI automation. So the benchmark does not directly transfer as a dependency or runtime, but the failure taxonomy and evaluation design transfer.

**Measured results**

Dataset:

- 338 tasks.
- 6 top-level domains, 23 fine-grained subdomains.
- 56 VM software environments.
- Initial candidate pool: over 1,000 tasks.
- Expert team: 71 members; 51 industry practitioners, 20 students/trainees.
- Difficulty by expert procedure length:
  - Easy: 30-44 steps, 129 tasks, 38.2%.
  - Medium: 45-60 steps, 159 tasks, 47.0%.
  - Hard: 61-110 steps, 50 tasks, 14.8%.

Main experiment:

- Models: Gemini-3.1-pro, Kimi-k2.6, GPT-5.4, Seed-2.0-lite, GPT-5.4-mini, Gemini-3-flash.
- Trials: 338 * 3 = 1014 trials.
- Max interaction rounds: 400.
- Judge for non-rule-based scoring: Seed-1.8.
- CIs: not reported.
- N per model: implied 1014 trials across 338 tasks, 3 trials each.
- Pre-frontier flag: the evaluated models are presented as current/frontier in the paper; no pre-frontier caveat for the main model results. Comparisons to older GUI benchmarks should not be treated as same-distribution evidence.

**Limitations / failure modes / non-transfer**

- No confidence intervals reported.
- Evaluation partly depends on LLM/VLM judges, even if rubrics are predefined.
- “Seed-1.8 judge bias is minimal” is asserted, not independently proven in the text.
- Results mix model and model-specific framework quality; the paper itself says GUI performance is tightly coupled to agent loop, coordinate schema, and tool interface.
- Not directly comparable to OS-World or other GUI benchmarks; those are different task distributions.
- The benchmark is GUI-centered. It does not directly measure CLI/tool/API agents like OUR primary harness.
- The video tutorial ablation is only 100 tasks and two models.
- Text/video tutorials reduce planning burden, so tutorial gains are not pure autonomous-workflow gains.
- Continuous-control tasks expose a current architecture bottleneck: before/after screenshots are too coarse for fine-grained manipulation.
- Failure modes:
  - workflow incompletion,
  - final-state but incorrect,
  - error propagation,
  - workflow stage omission,
  - objective drift,
  - software knowledge deficiency,
  - repetitive action looping,
  - inaccurate click localization,
  - premature termination,
  - coordinate replay when live UI diverges from tutorial frames.

**Integration into OUR system**

act-drain: bolt on the failure taxonomy as new blindspot labels for session corrections: `stage_omission`, `error_propagation`, `objective_drift`, `premature_termination`, `looping`, `final_state_incorrect`, `workflow_incompletion`. This is applicable because act-drain already mines human corrections; these labels would make long-horizon failure modes more inspectable. Do not import Workflow-GYM itself.

session-trace: add trajectory-level detectors over `agentlogs.db`: repeated identical tool/action calls, declared completion followed by missing artifact/state evidence, and long chains after an early failed command. This is the closest native analog to Workflow-GYM’s trajectory analysis.

skills/rules/hooks: use the mechanism as rule/hook design input, not as a new benchmark. Concrete hook candidate: a Stop advisory that flags “completion without final-state verification” when the agent claims done but no read/test/diff/check was run after the last edit/action. Another candidate: repeated-action loop detection for identical failed command/tool patterns.

MEMORY: NOT-APPLICABLE as a direct storage change. The useful lesson should first become act-drain/session-trace labels with raw links; only stable recurring findings should condense into MEMORY. The primer explicitly says condensed-to-raw links are weak, so do not add more unlinked prose.

/eval: build a small non-GUI “Workflow-GYM-shaped” eval for OUR harness: multi-step local workflows with hidden required stages, deterministic final artifact checks, and trajectory failure classification. Measure pass rate, premature completion, omitted stage, and token/tool cost. This fits our verifier-gated autonomy thesis better than standing up GUI VMs.

predict-then-falsify: use this paper’s taxonomy as pre-registered mechanisms. Example prediction: a completion-verification hook should reduce `final_state_incorrect` and `premature_termination` labels in session-trace without increasing over-ask. Accept only if traces show the hook fired at the intended failure point.

Workflow: integrate as a checklist in file-bus workflows: every long-horizon recipe should have explicit stage markers, final-state verifier, and retry/abort rule for repeated local failure. This is pattern extraction from Workflow-GYM’s hidden expert procedure, not adoption of their framework.

ToolSearch: low-priority bolt-on. Add taxonomy terms as searchable concepts for deferred tools/skills only if we already index skill metadata. Do not build new ToolSearch infra just for this paper.

Overall integration verdict: useful as a failure taxonomy and eval design pattern; not useful as a dependency or GUI benchmark for our current local agent harness. The strongest concrete transfer is trajectory-level classification in `session-trace` plus a small `/eval` benchmark for long-horizon file/tool workflows.
