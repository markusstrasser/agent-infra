Actual title in text: `Terminal-Bench: Benchmarking Agents on Hard, Realistic Tasks in Command Line Interfaces`

**Mechanism**

1. Define each task as an outcome-verified terminal environment:
   - instruction in `task.yaml`
   - Docker image/container state
   - tests that check final state, not transcript style
   - oracle `solution.sh`
   - time limit

2. Source realistic tasks from contributors:
   - 93 contributors created 229 tasks
   - 89 selected for Terminal-Bench 2.0

3. Verify task quality through a multi-stage audit:
   - oracle solution must pass
   - dummy/no-op solution must fail
   - contributor checklist for spec/test alignment and anti-cheating
   - LLM-assisted mistake checks
   - expert human review
   - model trajectory review after running Terminus 2
   - adversarial exploit agent tries to find shortcuts
   - final manual auditor inclusion decision

4. Run agents in containers:
   - evaluated six agent scaffolds: Claude Code, Codex CLI, Gemini CLI, OpenHands, Mini-SWE-Agent, Terminus 2
   - Terminus 2 is the neutral scaffold: single tool, headless terminal, Bash-only interaction

5. Score by test pass/fail on final container state:
   - each model/agent/task trial attempts the task
   - resolution rate = task success rate
   - task-level and model-level rates are averaged over repeated trials

6. Analyze failures:
   - trajectory-level taxonomy: Execution, Coherence, Verification
   - command-level judge labels command output failures
   - separate taxonomy for command failures: invocation, filesystem, runtime, REPL, etc.

**Why it works**

The causal claim is: realistic terminal tasks with executable final-state tests expose capability gaps that synthetic/code-only benchmarks miss, because agents must combine environment exploration, tool use, debugging, dependency handling, long-horizon planning, and verification.

The strongest mechanism is not the agent scaffold; it is the harness shape:
- containerized task state makes attempts reproducible enough to compare
- tests score outcomes rather than superficial command traces
- oracle solutions prove solvability
- adversarial/manual audits reduce benchmark flaws and shortcut paths
- repeated runs reveal stochastic success/failure, not one-off demos
- transcript-level failure analysis turns aggregate scores into actionable failure classes

The paper’s own evidence supports “harness and task construction matter,” but it does not prove that Terminal-Bench uniquely measures all valuable terminal work. It measures well-defined, testable terminal tasks.

**Preconditions**

- Tasks must have objective final-state tests.
- Instructions and tests must be mutually complete: every required behavior in tests is described, and every described behavior is tested.
- Oracle solution must pass.
- Dummy/no-op solution must fail.
- Environment must be reproducible enough: pinned packages, Docker images, dependencies in context.
- Tests must resist trivial cheating.
- Agent must be allowed to manipulate a terminal/container environment.
- Enough repeated trials are needed because agent runs are stochastic.
- Human/LLM audit capacity is required; paper reports roughly three reviewer-hours per accepted task.
- Internet access changes the threat model: useful for realism, but enables package/API drift and possible dataset/oracle discovery.

**Measured results**

Dataset:
- 229 contributed tasks from 93 contributors.
- 89 selected tasks in Terminal-Bench 2.0.
- Tasks manually verified by three human reviewers for correctness.
- Average accepted task received about three combined reviewer-hours.

Task time estimates:
- Expert estimates:
  - `<1 hour`: 36 tasks, 48.6%
  - `1 hour - 1 day`: 35 tasks, 47.3%
  - `1 day - 1 week`: 3 tasks, 4.1%
  - `>1 week`: 0 tasks, 0.0%
- Junior estimates:
  - `<1 hour`: 6 tasks, 8.1%
  - `1 hour - 1 day`: 53 tasks, 71.6%
  - `1 day - 1 week`: 12 tasks, 16.2%
  - `>1 week`: 3 tasks, 4.1%

Experimental setup:
- Six state-of-the-art agents.
- 16 frontier models.
- At least five runs for each supported model-agent combination.
- 32,155 total trials.
- Closed models through first-party APIs; open-weight models through Together.AI.
- Models with configurable reasoning effort used provider default, e.g. “medium” for Anthropic/OpenAI.

Headline resolution:
- GPT-5.2 + Codex CLI: 63% average resolution, best reported.
- Claude Opus 4.5 + Terminus 2: 58%.
- Gemini 3 Pro + Terminus 2: 57%.
- Kimi K2 Thinking + Terminus 2: 36%, best open-weight result reported.
- Paper states frontier models/agents resolve less than 65%; smaller models score around 15%.
- Error bars in Figure 1 are 95% confidence intervals, but the text file does not expose exact CI widths.

Cost/runtime:
- Running Terminal-Bench 2.0 costs roughly $1 to $100 depending on model price.
- Most trials finish under 20 minutes.
- Most Terminus 2 trials use fewer than 25 model calls.
- Most trials use fewer than 10M tokens.
- Extreme cases run up to 2 hours, make hundreds of API calls, and use nearly 100M tokens.
- Paper reports essentially no correlation between average turns per trial and success, and no necessary correlation between higher token count and better performance. Exact correlation coefficients are not in the provided text.

Human-vs-agent difficulty:
- Correlation between human-predicted and empirical difficulty: `r = 0.436`, `p < 0.001`.
- Of human-hard tasks:
  - 93.3% empirically hard
  - 3.3% empirically medium
  - 3.3% empirically easy
- Of human-medium tasks:
  - 54.5% empirically hard
  - 29.1% empirically medium
  - 16.4% empirically easy
- Empirical difficulty threshold:
  - Easy: Terminus 2 resolves with ≥66.7% of selected frontier models
  - Medium: 33.3%-66.7%
  - Hard: <33.3%

Failure analysis:
- Two failed trials per task per model sampled for trajectory-level analysis under Terminus 2.
- Human annotator calibration subset: 20 trials.
- Annotator agreement: 93% Cohen’s kappa.
- GPT-5 high-reasoning judge compared against 120 human-labeled traces:
  - 90% agreement
  - 92% precision
  - 90% recall
- Command-level failure detection:
  - GPT-5 medium-reasoning judge had 92.4% agreement with majority vote from three annotators over 66 pairs.
  - Command error rates range from 9.2% for Grok 4 to 26.7% for GPT-OSS-120B.
- Command failure taxonomy classification:
  - GPT-5 high-reasoning judge had 82.0% agreement with 50 author annotations.
  - 3,800 failures uniformly sampled.
  - Most frequent command failure: executable not installed or not in PATH, 24.1% of failures.
  - Next: failures when running executables, 9.6%.

Pre-frontier flag:
- The evaluated model set is mostly 2025 and January 2026 releases. For current 2026-06 system decisions, treat these as potentially stale/pre-frontier unless rerun on the live model mix. The methodology transfers more strongly than the absolute rates.

**Limitations / failure modes / non-transfer**

- Internet access makes the benchmark realistic but weakens reproducibility and allows possible dataset/oracle lookup.
- The authors say they have not observed oracle-solution cheating across tens of thousands of trajectories, but this is observational, not a guarantee.
- Public dataset can be trained on; Big-Bench canary helps accidental decontamination but not intentional contamination.
- External resources can drift: APIs, package downloads, package behavior, and stable-looking web resources may change.
- Container runtime and machine resource differences can affect effective task environment.
- Manual and LLM-assisted review reduces task flaws but does not eliminate underspecified tests or invalid tasks.
- The benchmark is restricted to tasks with executable verifiers. It does not validate taste, strategy, open-ended product judgment, or research synthesis unless those can be reduced to tests.
- Performance is scaffold-dependent. The paper tries to address this with Terminus 2, but headline “best scaffold per model” results still mix model capability with agent harness quality.
- LLM-as-judge failure analysis is useful but not ground truth. Judge agreement is measured, but taxonomy counts still inherit judge/model bias.
- The table/figure text available here does not expose full exact per-model CIs, so do not overquote exact leaderboard details beyond the prose-supported numbers.

**Integration into OUR system**

Primary bolt-on: `/eval + ~/Projects/evals`

Build a local “Terminal-Bench-shaped harness slice” for our own agent harness, not as a dependency on Harbor. Mechanism to extract:
- task envelope = instruction + sandbox/worktree + hidden verifier + oracle/reference repair when applicable
- score = final-state verifier, not transcript plausibility
- repeated runs per model/scaffold
- store per-trial tool calls, tokens, wall time, pass/fail, and failure class

Concrete implementation target:
- add an eval family for `agent-infra-terminal-tasks`
- seed with small local tasks drawn from our actual failure classes: hook confusion, git staging discipline, session-trace lookup, act-drain triage, ToolSearch routing, and checkpoint recovery
- require verifier scripts and dummy-fail checks before accepting a task
- report cost/token as first-class metrics

Secondary bolt-on: `session-trace / agentlogs.db`

Use the paper’s trajectory-level failure taxonomy as a starting schema for trace annotation, but adapt it to our surfaces:
- Execution: wrong command, missing dependency, bad path, bad git operation
- Coherence: loses current goal, repeats stale plan, mixes repos
- Verification: claims completion without principal check, weak smoke, skips cheap deciding probe

Concrete bolt-on:
- add derived labels over session-trace spans for `execution/coherence/verification`
- link each label to raw transcript spans, not only condensed MEMORY
- use this for forensic queries like “show over-ask sessions that also skipped cheap probes”

Secondary bolt-on: `act-drain / blindspot loop`

Use Terminal-Bench’s “audit before inclusion” discipline against our own proposed rules/hooks:
- oracle equivalent: demonstrate the hook/rule catches a known trace failure
- dummy equivalent: demonstrate it does not fire on a clean near-neighbor
- adversarial exploit equivalent: try to bypass it with a realistic agent action

Concrete bolt-on:
- before act-drain promotes a finding into a hook/rule, require a minimal `pass/fail/near-miss` evidence packet from agentlogs
- this directly targets the primer’s measured accretion/policy-maze risk

Secondary bolt-on: `predict-then-falsify`

Terminal-Bench’s key lesson is outcome verification. For harness edits:
- pre-register the failure class expected to move
- run a small trace-backed eval
- accept only if the intended mechanism fired
- revert if score moves for unrelated proxy reasons

Concrete bolt-on:
- use final-state checks over actual traces, not “rule was added” as progress
- example metric: reduce unsupported completion claims on held-out sessions, not merely increase hook firings

Secondary bolt-on: `skills / rules / hooks`

Use task contributor checklist ideas for governance surfaces:
- every new hook/rule should state what behavior it checks
- every checked behavior must map to a real observed failure or explicit risk
- every hook must have clean-case and dirty-case fixtures

Concrete bolt-on:
- hook fixture template modeled after Terminal-Bench task criteria:
  - `dirty input fails`
  - `oracle/clean input passes`
  - `instruction text matches enforced predicate`
  - `bypass attempt tested`

Secondary bolt-on: `Workflow tool / file-bus just recipes`

Terminal-Bench’s Harbor/Terminus separation maps to our file-bus recipes:
- keep orchestration separate from scoring
- workflow executes tasks; eval harness scores final state
- avoid judging by workflow logs alone

Concrete bolt-on:
- add a recipe that runs local eval tasks through Codex/Claude/Cursor and writes normalized trial records
- single-writer-many-readers fits our current file-bus model

Concrete bolt-on:
