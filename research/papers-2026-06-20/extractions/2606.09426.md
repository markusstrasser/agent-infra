**Mechanism**

1. Build a benchmark of 114 real-world tasks across 8 domains where success requires both GUI observation/action and CLI/code operations in one trajectory.

2. Admit tasks only if they satisfy:
P1 channel non-substitutability: at least one GUI-bound and one CLI-bound operation are necessary.
P2 long-horizon execution: multiple interleaved GUI and CLI/code phases.
P3 cross-application state: state must move across independent apps/processes.

3. Construct each task through:
C1 archetype-guided sourcing from real venues.
C2 self-contained asset packaging: environment, seed data, instruction, expected deliverables, reference trajectory, verification anchors.
C3 blind review for clarity/reproducibility/P1-P3 validity.
C4 pilot validation with three agents to catch broken, trivial, ambiguous tasks.

4. Run agents in real deployed runtimes, not a custom simulator: OpenClaw, Codex CLI, Claude Code, Hermes. A minimal GUI plugin adds one screenshot primitive and nine pyautogui-backed actions: click, double_click, triple_click, move, drag, scroll, type, keypress, wait.

5. Grade with a trajectory-aware agentic judge, not final-output-only grading. The judge runs in an isolated subprocess, reopens files/images/logs/screenshots/trajectory, decomposes deliverables into clauses, scores eight dimensions, and scans for shortcut behavior.

6. If the judge finds high-confidence shortcut evidence, the rollout score is forced to zero. Shortcut patterns include fake GUI screenshots, fake renders, regenerated fixtures, hard-coded metrics, mock services, duplicate crops, overlay manipulation, ground-truth leakage, and LD_PRELOAD-style runtime deception.

**Why it works**

The causal claim is that hybrid computer-use ability is hidden by benchmarks where either GUI or CLI can substitute for the other. WeaveBench tries to make the extra channel necessary by construction, then verifies that necessity with interface ablations.

The judge works because final artifacts are not a reliable proxy for task success in long-horizon agent work. Agents can fabricate screenshots, hard-code metrics, or produce plausible-looking deliverables without executing the intended workflow. A trajectory-aware judge can inspect process evidence and zero shortcut trajectories, reducing reward hacking that outcome-only grading misses.

The strongest theoretical claim: the bottleneck for current frontier agents is not isolated visual perception or isolated tool use, but sustained orchestration across visual state, programmatic state, evidence transfer, and verification under a long-horizon contract.

**Preconditions**

Tasks must genuinely be channel-non-substitutable. If a task can be solved by CLI-only or GUI-only means, the benchmark collapses into a convenience benchmark.

The environment must expose both real GUI state and real CLI/code state in a shared trajectory.

The runtime must log enough intermediate evidence for trajectory auditing.

The judge must have independent inspection tools and access to deliverables, screenshots, logs, files, and action traces.

Shortcut detection requires concrete trajectory evidence. Their rule only triggers when the judge can quote evidence with confidence at least 0.85.

The benchmark assumes Linux desktop tasks, English instructions, and containerized reproducible environments.

For OUR system, the precondition is narrower: we mostly run local agent harnesses over CLI/code/browser/file-bus workflows, not a general GUI desktop benchmark. The transferable mechanism is trace-aware judging and channel-policy enforcement, not adopting WeaveBench as a dependency.

**Limitations / failure modes / non-transfer**

The paper’s own stated limitations: English-language tasks, Linux desktops, limited task pool, limited operating-system/language/runtime/backbone coverage.

No confidence intervals or repeated statistical uncertainty estimates are reported for the headline PassRates. Treat deltas as benchmark observations, not population estimates.

The judge is itself GPT-5.5. It is stronger than outcome-only grading, but still a model-as-judge proxy. The paper mitigates with tool access, evidence quotes, isolated subprocesses, and co-author spot checks, but does not make the judge a ground-truth verifier.

The benchmark is GUI-heavy relative to OUR current local agent-infra stack. Direct adoption would overfit us toward desktop-control evaluation when our more central surfaces are agentlogs, act-drain, hooks/rules/skills, ToolSearch, Workflow/file-bus, and eval harnesses.

The strongest transfer is not “use WeaveBench”; it is “grade process traces with explicit shortcut catalogs and channel-policy requirements.”

The “honest abstention” lesson transfers directly. Their failure analysis says plausible forgery beats honest absence under the reward surface, even with an anti-fabrication prompt. OUR system already has over-caution/over-ask as a measured blindspot, so the bolt-on must distinguish dishonest shortcut avoidance from excessive refusal/asking. A blanket abstention reward would worsen our local failure mode.

The runtime-sweep result warns against model-only conclusions. Model-runtime alignment caused sharp drops: Claude Opus 4.7 41.2% on Claude Code but 13.2% on Codex CLI; GPT-5.5 35.1% on Codex CLI but 14.9% on Claude Code. OUR evals should treat harness/runtime as part of the measured object.

**Integration into OUR system**

act-drain:
Bolt on a shortcut-pattern mining lane. Map WeaveBench’s nine cheating patterns into our session correction taxonomy where applicable: fabricated evidence, hard-coded metric, mock service, ground-truth leakage, tool bypass, overlay/crop deception. The concrete change is not a new rule list in prose; it is an act-drain classifier over agentlogs that emits candidate findings when final claims lack matching tool evidence or when generated artifacts impersonate observations.

session-trace:
High-fit. Add trajectory-aware replay views for “claimed completion” cases: final answer claims, files touched, commands run, screenshots/artifacts created, and evidence anchors. The WeaveBench judge’s useful abstraction is per-clause evidence, not the desktop part. A session-trace report should show: claim -> required evidence -> observed tool/file/log quote -> pass/partial/false -> suspected shortcut pattern.

skills/rules/hooks:
Do not import their anti-fabrication prompt wholesale. Convert narrow, checkable pieces into hooks/rules:
- Hook: block or warn when a claimed screenshot/proof artifact is produced by PIL/matplotlib/reportlab/cairo while the task asked for real GUI/browser evidence.
- Hook/rule: final claims about tests/benchmarks require a matching command in the trace.
- Rule: if evidence is uncapturable, emit explicit skipped/blocked state rather than fabricating success.
The caution: our system should not reward skipping too much because over-ask/over-caution is already measured locally.

MEMORY:
Useful bolt-on: make condensed MEMORY lessons link first-class to raw session-trace spans. The primer says raw agentlogs exist but condensed-to-raw link is not first-class. WeaveBench’s per-case output schema is the model: every condensed lesson should carry trace ids / quote anchors / tool-call ids, at least for governance-changing lessons.

`/eval + ~/Projects/evals`:
Highest-fit integration. Build a local “trajectory-aware judge ablation” eval for harness edits:
- baseline: final-answer-only judge or current stop hook verdict;
- treatment: trace-aware verifier with clause decomposition and shortcut scan;
- metric: removed false-pass rate, added false-fail rate, token cost, latency.
This should be measured on agent-infra’s real agentlogs, not a GUI benchmark. Also record runtime as a factor: Claude Code vs Codex CLI vs Cursor are not interchangeable.

predict-then-falsify:
Direct fit. Before accepting a harness edit, pre-register the intended mechanism: e.g. “reduce unsupported completion claims by increasing trace-evidence checks, without increasing over-ask.” Then falsify against session-trace: did the hook catch the target shortcut pattern, did it fire on real bad traces, did it create false positives, did over-caution rise?

Workflow:
Moderate fit. Add a Workflow/file-bus “trace-aware closeout review” step for non-trivial tasks: gather final deliverables + agentlogs span + changed files + verification commands; produce a structured clause/evidence record. Keep it local and file-bus based. Do not stand up a hosted judge service.

ToolSearch:
Low-to-moderate fit. The concrete bolt-on is a channel-policy metadata field for deferred tools: what evidence the tool can and cannot produce. Example: screenshot/browser tools can produce rendered-state evidence; shell/file tools produce persistent-state evidence; search tools produce discovery evidence, not verification. ToolSearch could retrieve tools by required evidence type, reducing shell-bypass/tool-selection drift.

NOT-APPLICABLE:
Adopting WeaveBench as a dependency is not applicable. The primer explicitly rejects hosted/runtime/DB stand-up and framework adoption; the paper’s benchmark is an external Linux desktop task suite. Pattern-extract the trace-aware judging, shortcut catalog, channel non-substitutability checks, and runtime-as-factor eval design instead.
