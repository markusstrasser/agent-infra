**Mechanism**

ACDL is a descriptive DSL for specifying the exact structure of the context sent to an LLM at each agent step.

Step by step:

1. Model the LLM input as an ordered sequence of role messages: `S` system, `U` user, `A` assistant, `T` tool, and `N` for legacy unstructured completion prompts.
2. Replace prompt prose with symbolic content labels: templates like `INSTRUCTIONS`, dynamic variables like `env.user_input[@T]`, `sys.tool_history[@t]`, and previous response references like `resp.answer[@t]`.
3. Separate information sources into namespaces: `sys` for internal agent/system state, `env` for external/environment/user state, and `resp` for previous LLM outputs.
4. Index state by agent time: `@T` is current step, lower-case `@t` iterates history, and nested substeps like `@T.I` represent inner loops inside an outer turn.
5. Use control flow to describe context assembly: `ForEach` for replaying histories, `If/Else/Switch` for conditional inclusion, and `PromptEndsHere` for turn-dependent truncation.
6. Use pure functions for computed context pieces, e.g. retrieval or summarization, while leaving implementation external.
7. Use fragments to reuse repeated context structures, either as string fragments inside a role or role fragments that expand to full messages.
8. Use mark blocks to annotate rendered diagrams without changing semantics.
9. Render the ACDL spec into visual diagrams so variants can be compared by message placement, role, loop structure, and history-retention policy.
10. Apply the language to real systems by reverse-engineering prompt traces/code and writing the context construction as ACDL.

The language describes what the model receives, not how the agent computes state, executes tools, retrieves documents, or behaves.

**Why it works**

The causal claim is that agent behavior depends materially on context structure, not only on prompt wording. ACDL works by making the macro-structure of context explicit: what information is included, where it appears, what role it is assigned, how history is replayed, and how this changes over time.

The paper’s theory is mostly representational, not algorithmic: once context construction has a shared formal vocabulary, engineers and researchers can compare variants, reproduce systems, see hidden differences, and communicate context logic without reading code or relying on prose. The analogy is UML, neural-network box diagrams, plate notation, and Mermaid-style diagrams: the artifact becomes inspectable because there is a stable notation for it.

The strongest causal evidence in the paper is the MINT appendix: small changes in how tool-use history is retained and role-grouped change success rates. The rest is plausibility plus examples, not a controlled proof that adopting ACDL improves engineering outcomes.

**Preconditions**

ACDL assumes the system can be represented as discrete time steps, potentially nested.

Agent state must be externally maintained and addressable as history, because ACDL does not define state mutation or storage.

State values used during context construction must be effectively immutable during that construction. Systems whose state mutates while assembling the prompt are cumbersome to express.

The prompt must be representable as a linearized context, usually role messages. Provider-side hidden formatting, e.g. opaque `tools` parameters, is outside current ACDL except via comments/accompanying prose.

Computed pieces must be nameable as pure functions of explicit inputs. If retrieval depends on changing memory or databases, those changing sources need to appear as inputs.

The author must know the actual context structure. ACDL does not solve observability; reverse-engineered specs can be wrong if traces/code are incomplete.

For multi-agent systems, ACDL works best when agents have isolated clocks or a shared clock. Separate agent clocks plus shared mutable state are a known weak spot.

Adoption matters. A private ACDL spec helps one team, but the paper’s “standard language” benefits require enough people to use the notation.

**Measured results**

The only measured performance result is Appendix A, the MINT experiment.

Task setup: 7 context configurations with the same system message structure but different tool-use history retention and grouping. Evaluated on MINT benchmark tasks, excluding ALFWorld.

Reasoning task sources: GSM8K, HotpotQA, MATH, MMLU, TheoremQA.

Code-generation task sources: MBPP, HumanEval.

Model: GPT-4-Turbo. This is pre-frontier relative to the paper’s own framing and to our current model stack; the authors explicitly call it “relatively weak by current standards.” They also state stronger models such as GPT-5 or Claude Opus 4.6 were largely insensitive on MINT because MINT prompts are short and horizons limited. No raw N, confidence intervals, statistical tests, or per-task counts are reported in the text.

**Limitations / failure modes / non-transfer**

ACDL is a notation, not an execution framework. It does not validate that an agent behaves correctly, that retrieval is good, or that tool outputs are trustworthy.

It describes context construction, not state mutation, agent policy, tool implementation, retrieval mechanisms, or model behavior.

It is weak for systems with mutable state during prompt construction.

It lacks a clean model for multi-agent systems with unsynchronized clocks and shared mutable state.

It currently leaves provider-specific non-message fields, especially `tools`, outside the formal context description unless represented in comments or accompanying prose. That matters for our stack because tool surfaces and deferred tools are central.

The empirical result is small, under-specified, and pre-frontier. No N/CIs. No statistical significance. GPT-4-Turbo is not representative of current frontier agents. The authors themselves say stronger models are insensitive to the tested distinctions on MINT.

The benchmark is short-horizon. The paper speculates that real long-horizon systems would show larger context-structure effects, but does not measure that.

Reverse-engineering OpenCode/OpenClaw contexts from code and proxy traces is useful but not guaranteed exact. The DeepSeek appendix explicitly says some role assignments are inferred because the tech report omitted them.

ACDL could become another documentation layer that drifts from implementation unless generated from traces or checked against actual logged contexts.

**Integration into OUR system**

Best integration: `session-trace / agentlogs.db`.

Concrete bolt-on: add an offline `context-shape` extractor over `agentlogs.db` that emits an ACDL-like normalized trace for each LLM call: role sequence, tool-call grouping, summary/compaction boundaries, injected reminders, system/developer/user/tool segmentation, and deferred-tool surfaces. This should be derived from actual transcripts, not hand-authored docs. Output can be used in `session-trace <uuid-prefix>` as a “context layout” pane or artifact.

Second integration: `predict-then-falsify`.

Concrete bolt-on: require harness edits that change context shape to declare an expected ACDL-level mechanism before acceptance, e.g. “tool results move from user-role to tool-role,” “condensed MEMORY gains raw transcript links,” “skills are injected later and only when ToolSearch selects them.” The falsifier checks session traces after the change to confirm the intended structural difference actually occurred.

Third integration: `/eval + ~/Projects/evals`.

Concrete bolt-on: create a small context-shape eval where variants are not prose prompts but structural variants: retain/drop reasoning traces, group/split tool calls, inject reminders at end vs beginning, include condensed memory with/without raw links, eager-load vs ToolSearch-load skills. Measure task success, token cost, tool errors, over-ask rate, and correction class. Do not import the MINT numbers as expected effects; they are only prior evidence that shape can matter.

Fourth integration: `skills / rules / hooks`.

Concrete bolt-on: use an ACDL-inspired schema in rules/hooks for context-affecting changes. A hook should block or warn on documentation-only claims about prompt/context behavior unless backed by a trace-derived context-shape artifact. This addresses the drift failure mode directly. Do not add hand-written `.acdl` docs as yet another stale file unless they are generated or trace-checked.

Fifth integration: `MEMORY`.

Concrete bolt-on: represent condensed-memory-to-raw-session links as first-class context references. The paper’s `sys/env/resp` distinction maps well: `MEMORY` entries are `sys.memory`, raw transcript spans are `resp/tool/session-trace` evidence. This is useful only if the link is mechanical and queryable; a prose “see session” note is too weak.

Sixth integration: `ToolSearch`.

Concrete bolt-on: describe deferred tool loading as context shape: tools absent from base context, then selected by ToolSearch query, then injected into the callable/tool surface. ACDL itself does not model provider `tools` fields cleanly, so use the mechanism but extend the schema for non-message tool surfaces.

Seventh integration: `Workflow tool / file-bus just recipes`.

Concrete bolt-on: add context-shape summaries to workflow run reports for fan-out/loop-until-dry sessions: parent context, scout context, returned-file stub, and merge/review context. This is a good fit because our system is single-writer-many-readers and context handoff structure matters.

Not-applicable as dependency: do not adopt ACDL as a runtime framework or hosted tool. The primer says we pattern-extract and reject hosted/runtime/DB stand-up. The useful piece is the representation: trace-derived, local, generated, and falsifiable.
