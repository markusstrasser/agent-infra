**Mechanism**

HarnessBridge is a learned plug-in harness controller around a frozen generator. It does not train the agent model itself; it trains a small harness policy that mediates both directions of the agent-environment interface.

Step by step:

1. Keep the raw trajectory `Ht` as the authoritative record: task, prior model outputs, tool calls, observations, code snippets, retrieved evidence, execution results, and harness reminders.

2. Before the generator sees context, run **observation projection** `Pobs(s, q, Ht)`.

3. `Pobs` emits:
   - an **active-state index** `Ut`, placed before history, containing unresolved errors, open constraints, established facts, pending goals, and decision variables;
   - per-history-unit exposure decisions `zi ∈ {PASS, COMPRESS, DROP}`.

4. For each history unit:
   - `PASS`: keep original unit.
   - `COMPRESS`: replace with a short grounded summary.
   - `DROP`: omit from generator-visible context.
   The raw unit is still retained outside the projected view.

5. The frozen generator receives `(system prompt, task, projected history)` and proposes action `at`.

6. Before action execution, run **action projection** `Pact(s, q, Ht, at)`.

7. `Pact` emits `dt ∈ {Pass, Reject}` plus feedback `ρt` when rejecting.

8. If `Pass`, the action executes normally in the environment.

9. If `Reject`, no environment step occurs. The harness returns trajectory-grounded feedback to the generator:
   - `concern`: what is wrong;
   - `evidence`: specific trajectory evidence;
   - `suggestion`: concrete revision.

10. Critical guard: if the action projection cannot provide trajectory-grounded evidence, it defaults to `Pass`.

11. Training unifies both directions as instruction-following SFT on a small Qwen3.5-0.8B controller. Inputs are trajectory/task/action records; outputs are structured projection decisions.

12. Supervision is generated from solved trajectories and filtered with LLM judges. For the main HarnessBridge:
   - action-projection set: `2,682` examples, balanced `50:50` Pass/Reject;
   - observation-projection set: `2,723` examples;
   - total retained SFT examples: `5,405`.
   HarnessBridge-D uses DeepSeek-generated supervision:
   - observation examples: `3,575`;
   - total retained examples: `5,287`.

**Why it works**

The causal claim is that long-horizon agent failures are partly harness-interface failures, not only model-capability failures.

The paper’s theory:

- Agents do not act on the real environment state; they act on the harness-serialized view of accumulated trajectory.
- Long trajectories accumulate stale errors, redundant exploration, superseded hypotheses, verbose logs, and repeated low-value commands.
- A learned observation projection should improve reasoning by making current decision state explicit while hiding noise.
- A learned action projection should prevent wasted environment steps when the trajectory already shows that the proposed action is unproductive.
- Keeping raw history authoritative avoids irreversible compression errors; only the generator-visible view is projected.
- Requiring evidence for rejection reduces false blocking and keeps exploration possible.
- Training a lightweight controller on successful trajectories distills interaction-control patterns that can transfer across larger frozen generators.

Skeptical read: the plausible mechanism is not “learnable harnesses in general”; it is narrower: a learned summarizer plus learned pre-action veto can reduce context bloat and repeated bad turns on coding benchmarks, if the learned policy has good evidence grounding and a low false-reject rate.

**Preconditions**

Must hold for this to work:

- Tasks are long-horizon enough for context bloat, stale state, or redundant actions to matter.
- There is a raw trajectory store the harness can retain independently of the projected context.
- The harness can insert an active-state block before history.
- The harness can intercept proposed actions before execution.
- Rejected actions can be returned as feedback without corrupting the environment state.
- The action space has recognizable “wasteful but syntactically valid” actions.
- The system can tolerate a local controller model call before observation/action flow.
- There is enough solved-trajectory data to train projection behavior.
- Compression summaries can be grounded in raw spans.
- False rejects are costly enough to require conservative behavior; the paper’s prompt explicitly defaults to `PASS`.
- Benchmark success must be measurable from environment outcomes, not model self-report.
- For transfer claims, the controller’s training trajectories must capture interaction-level patterns rather than quirks of a single generator.

Preconditions that are weak or unproven in the paper:

- Non-coding transfer is asserted but not empirically shown.
- Single-operator local harness transfer is not tested.
- Multi-tool lazy-loading systems like ToolSearch are not directly tested.
- Human-supervision metrics such as over-asking, act-drain quality, or policy-maze accretion are not measured.

**Measured results**

Benchmarks: Terminal-Bench 2.0 and SWE-bench Verified. Metrics: success rate `SR (%)` and average input tokens in millions. Models: Qwen3.5-35B-A3B, GLM-4.7-Flash, GPT-5.4-Nano, GPT-5.4, DeepSeek-V4-Flash, DeepSeek-V4-Pro, Claude-Opus-4.7. Qwen/GLM open models served with SGLang at temperature `0.6`; commercial models via APIs. No CIs reported. The paper says evaluation is single-run due to cost. Treat all deltas as noisy.

**Limitations / failure modes / non-transfer**

- Single-run results; no confidence intervals, no repeated seeds, no variance estimates.
- Coding-only evaluation. Non-coding long-horizon claims are speculative.
- Uses solved trajectories for supervision, which may bias toward post-hoc successful behavior and underrepresent recovery from real messy failures.
- LLM-as-judge filtering is central; judge errors can become training labels.
- Action projection can over-reject. The paper’s own turn-agnostic curation recipe made performance worse than Terminus 2 on DeepSeek-V4-Pro and DeepSeek-V4-Flash.
- Strict rejection mode hurts SR: e.g. SWE `61.5%` tolerant vs `56.7%` strict; TB `30.3%` tolerant vs `25.8%` strict.
- The harness still spends controller tokens. The paper argues compute-weighted overhead is small, but that is a proxy, not a measured wall-clock/cost benchmark for our local stack.
- Observation compression can lose critical detail if summaries are unfaithful; raw preservation mitigates but does not eliminate bad projected-state decisions.
- Active-state extraction can hallucinate, over-prioritize stale hypotheses, or encode wrong “unresolved” items.
- The method adds a second model whose errors can steer the main model.
- Transfer to frontier commercial models is measured only through the paper’s APIs and benchmark setup; not validated against our Claude Code/Codex/Cursor local harness.
- Their action categories are command-syntax based. Our system has richer tool surfaces, deferred tools, app connectors, file-bus workflows, and governance hooks; simple command categories will miss semantic failures.
- The paper optimizes benchmark task success and token count, not our primary governance metrics: declining supervision, fewer over-asks, fewer policy-maze additions, better act-drain proposals, or verified predict-then-falsify mechanism firing.
- The reported result “HarnessBridge jointly improves success rate and reduces token consumption” is too broad: on Qwen SWE, HarnessBridge uses fewer tokens but lower SR than Terminus 2; on GLM SWE, it improves SR slightly but token savings are tiny.

**Integration into OUR system**

Concrete integration: **predict-then-falsify + session-trace + act-drain**, not a dependency adoption.

Bolt-on:

- Surface: `session-trace / agentlogs.db`.
  - Add an offline “projection replay” experiment over raw transcripts. For each turn, derive:
    - candidate active-state index;
    - `PASS / COMPRESS / DROP` decisions for older turns;
    - `PASS / REJECT` decision for the next action with concern/evidence/suggestion.
  - Do not execute rejections live at first. Replay only.

- Surface: `predict-then-falsify`.
  - Pre-register expected movement before any live hook:
    - fewer repeated read/search loops after relevant file/function already identified;
    - fewer over-ask corrections;
    - no increase in false-blocked productive tool calls;
    - token/context reduction without lower task completion.
  - Accept only if session-trace shows the intended mechanism: a projected rejection must cite prior trajectory evidence and the next successful path must differ in the suggested direction.

- Surface: `act-drain / blindspot loop`.
  - Use act-drain correction labels as supervision candidates for action projection, especially `over_caution=63 / over-ask`, repeated exploration, premature completion, and contradicted-path failures.
  - Counterweight against policy-maze accretion: learned or replayed projection should replace repeated new prose rules only when it measurably catches a recurring class.

- Surface: `skills/rules/hooks`.
  - Immediate low-risk extraction: add no learned controller yet. Pattern-extract the action-projection prompt into an advisory hook template for high-evidence cases only:
    - `WASTEFUL_EXPLORATION`: identified file/function/mechanism + 3 further untargeted reads/searches.
    - `CONTRADICTED_PATH`: current plan ignores a recent test/error.
    - `PREMATURE_SUBMISSION`: completion claim with unaddressed failure evidence.
  - Default must be `PASS`, and any `REJECT`/advice must include direct quoted evidence plus a concrete next command.

- Surface: `MEMORY`.
  - Do not integrate raw compressed summaries as MEMORY. The useful pattern is a first-class link from condensed lesson to raw session spans. HarnessBridge’s “raw trajectory preservation” maps directly to “MEMORY entry must point to raw agentlogs spans,” not overwrite history.

- Surface: `/eval + ~/Projects/evals`.
  - Build an eval before enforcement:
    - dataset: prior sessions with human corrections and known bad turns from agentlogs;
    - labels: whether a proposed action should pass or be challenged;
    - metrics: false reject rate, caught-waste rate, downstream correction reduction, token savings, wall-clock overhead.
  - Include a held-out transfer split by repo/vendor. Do not count in-sample replay as progress.

- Surface: `Workflow / file-bus just recipes`.
  - Add projection replay as a file-bus stage in audit mode only: raw transcript in, projected active state / veto candidates out, no live action mutation.
  - Useful for `debug-until-dry` and `operator-status-briefing` as a “where did the agent drift?” artifact.

- Surface: `ToolSearch`.
  - Observation projection can help ToolSearch by emitting an active-state index containing unresolved capability needs and already-loaded tools. But do not train a controller here first.
  - Concrete bolt-on: ToolSearch query generation should read active-state fields like `needed_capability`, `already_tried`, `blocked_by`, and `exact_surface`, reducing repeated or irrelevant tool discovery.

NOT-APPLICABLE:
- Hosted runtime / server / DB adoption: not applicable. Primer says reject hosted runtime/server/DB stand-up. HarnessBridge should be pattern-extracted, not adopted as a framework dependency.
- Live learned action blocking now: not applicable until `/eval` demonstrates low false-reject rate. The paper itself shows over-rejection can degrade success sharply.
