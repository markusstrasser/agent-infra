**Mechanism**

Socratic-SWE is a closed trace-skill-task training loop for SWE agents.

1. Start with a shared policy used in two roles: Generator and Solver.
2. Run the Solver on a seed task/curriculum in real repositories.
3. Collect full solving traces: repository inspection, edits, command execution, tests, success/failure.
4. Split traces into successes and failures.
5. Distill traces into an Agent Skill Registry. Each skill has name, description, applicability conditions, and ordered operations.
6. Deduplicate skills by semantic similarity and filter by trace coverage.
7. For each iteration, sample a repository and a skill.
8. The Generator proposes a repair task plus verifier/tests, conditioned on repository context, skill, and Solver evidence.
9. Candidate tasks pass a staged verifier gate:
   - format: task/verifier parse and are syntactically valid
   - grounding: referenced artifacts exist
   - execution: verifier runs and is stable across repeated runs
   - semantics: verifier distinguishes broken from fixed state and at least one valid repair exists
10. For accepted candidates, estimate the Solver gradient induced by training on that task.
11. Compare that candidate gradient to a held-out trusted validation-gradient direction using cosine similarity.
12. Reward Generator by `Valid(task) * cos(candidate_gradient, validation_gradient)`.
13. Train Solver on accepted tasks using executable feedback reward:
   - full-suite pass
   - partial repair rate
   - regression avoidance
14. Use GDPO to normalize the Solver’s heterogeneous reward components.
15. Updated Solver produces new traces, which refresh the skill registry and next curriculum.

**Why it works**

The causal claim is: historical traces expose the current model’s capability boundary better than static synthetic tasks do. Failures show recurring gaps; successes show reusable repair behaviors. Turning those into skills makes task generation model-aware.

The gradient-alignment claim is stronger: not every hard task is useful. A generated task is useful if training on it moves the Solver in the same direction as improvement on trusted held-out validation tasks. Cosine similarity is used to prefer directional alignment while avoiding bias toward large gradients from long or complex patches.

In the paper’s terms: traces become skills, skills generate targeted executable tasks, executable validation filters junk, and gradient alignment selects tasks whose induced update is likely to improve validation performance.

**Preconditions**

Requires:

- Rich historical agent traces with tool use, edits, command outputs, and verification outcomes.
- Real repositories in sandboxes.
- Executable verification signals: tests or commands that are deterministic enough to rerun.
- A task generator capable of repository inspection and controlled bug/task construction.
- A skill extractor/distiller model.
- A trusted held-out validation task set representative of the target deployment distribution.
- Enough compute to roll out candidate tasks and validation tasks repeatedly.
- On-policy or near-on-policy gradient estimates for the Solver.
- Tasks where pass/fail, partial repair, and regression avoidance are meaningful.
- Stable repository pools or enough repository diversity to avoid curriculum saturation.

Does not naturally apply where there are no reliable tests, no deterministic verifier, no sandbox, or no task-level validation.

**Limitations / failure modes / non-transfer**

The paper’s own limitations:

- Closed-world fixed seed repository pool.
- Skill registry saturates; later iterations find fewer novel gaps.
- Depends on held-out validation set quality.
- Alignment reward may fail if validation distribution is not representative.
- Assumes executable verification and sandboxed repository interaction.
- May not transfer to settings without reliable tests, deterministic execution, or task-level validation.
- Broader transfer across languages, repository styles, and workflows remains unproven.

Additional skeptical reads:

- Gradient alignment optimizes toward the validation set. It is useful only if the validation set is a good proxy and protected from leakage/Goodharting.
- The claimed gains are pass-rate deltas without CIs. On small benchmark N, some smaller differences may be noise.
- Main model is Qwen3.5-9B; frontier-agent traces may have different failure distributions.
- The method is training-heavy. Our system is a local harness and subscription-dispatch environment, not an 8xA100 RL lab.
- The paper’s “skill” object is broad natural language; quality depends on extraction fidelity and dedup.
- The Generator prompt looks close to bug-injection/task-synthesis. For our system, generating artificial bugs is less directly useful than mining real human corrections and real failed sessions.
- It uses task generation for model post-training. Our immediate lever is harness/rules/hooks/workflows, not model-weight updates.

**Integration into OUR system**

Concrete integration: yes, but pattern-extract only. Do not adopt the framework as a dependency.

Best bolt-on: `act-drain / blindspot loop`.

- Add a trace-derived skill/task object pass over daily correction clusters.
- Convert repeated human corrections into structured “Agent Skill” candidates with fields matching the paper’s useful minimum:
  - name
  - applicability conditions
  - failure evidence from agentlogs/session-trace
  - ordered operations
  - verifier/hook candidate if applicable
  - expected metric movement
- Feed those into existing `GROW_COVERAGE / RAISE_AUTONOMY / REDUCE_ERROR` classification.
- Use this as an anti-accretion filter: a new rule/hook only lands if tied to trace coverage and a predicted metric.

Second bolt-on: `predict-then-falsify`.

- Use the paper’s validation-gradient idea as a local non-RL analogue: every proposed rule/hook/skill must name the trace-derived mechanism it should affect.
- Accept only if later `session-trace` shows that mechanism fired: fewer over-asks, fewer repeated failures, fewer unsupported completion claims, etc.
- This maps to “alignment with validation gradient” without needing policy gradients.

Third bolt-on: `session-trace / agentlogs.db`.

- Make condensed MEMORY and skills link back to raw trace spans as first-class provenance.
- The primer says this link is currently not first-class. Socratic-SWE’s core insight is that trace-derived artifacts should remain grounded in trace coverage.
- Concrete surface: store `agentlogs` span ids/session ids on skill/rule proposals and MEMORY entries.

Fourth bolt-on: `skills / rules / hooks`.

- Replace flat skill/rule accumulation with a trace-derived registry view:
  - skill/rule name
  - when/applicability
  - operations
  - source traces
  - coverage count
  - last observed failure
  - retirement condition
- This directly targets our measured “policy maze” accretion failure.

Fifth bolt-on: `/eval + ~/Projects/evals`.

- Build a small held-out validation set of historical sessions/tasks where we know the desired agent behavior.
- Score candidate harness edits against this set before globalizing them.
- Not policy-gradient training; just harness-level validation: did the candidate hook/rule/skill improve replayed decisions without increasing false positives?

Sixth bolt-on: `ToolSearch`.

- NOT-APPLICABLE for the main paper mechanism. ToolSearch is lazy capability discovery, not task curriculum.
- Small transferable idea: trace-derived “when to load tool” skills could improve ToolSearch queries, but this is secondary.

Seventh bolt-on: `Workflow tool / file-bus just recipes`.

- Use trace-derived skills to generate Workflow checklists for recurring failure classes.
- Good fit for bounded, repeatable procedures like commit hygiene, debug-until-dry, review dispatch, and trace forensics.
- Do not generate artificial SWE tasks here; generate workflow probes/checks from real failed traces.

Bottom line: the useful import is not “self-evolving SWE RL.” It is trace-grounded skill extraction plus validation-gated curriculum selection. For OUR system, the concrete move is: turn act-drain’s daily correction mining into a structured Skill/Rule proposal registry with raw trace provenance and predict-then-falsify acceptance.
