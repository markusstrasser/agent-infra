**Mechanism**

SING is an active retrieval layer for large tool libraries. It replaces “inject every tool schema” or one-shot embedding search with an offline intention graph plus online state-conditioned retrieval.

Step by step:

1. Build a corpus of MCP servers/tools.
   The paper crawls MCP sources, then filters to `779` deployable servers and `7,471` tools.

2. Synthesize tool-use queries for each tool.
   For each tool, an LLM sees parent server info, tool description, and schema, then generates natural-language instructions plus concrete tool calls and arguments.

3. Filter synthetic queries.
   They remove trivial/paraphrase-like samples using embedding similarity and LLM-as-judge quality filtering.

4. Expand single-tool queries into multi-tool chains.
   Candidate next tools are selected by normalized input/output type compatibility and LLM judgment about whether the next tool naturally extends the current chain. The LLM rewrites the query into a more complex multi-step task.

5. Extract atomic intentions.
   For each tool, an LLM extracts concise verb-object intentions from the synthesized queries and schema, e.g. context-independent goals the tool supports.

6. Normalize/deduplicate intentions.
   Similar intentions are merged across tools and servers, producing shared intention nodes.

7. Construct a heterogeneous graph.
   Nodes: servers, tools, intentions.
   Edges:
   `server -> tool` via `has_tool`;
   `tool <-> intention` via `has_intention`;
   directed `tool_next` edges from synthesized chains;
   undirected `tool_cooccur` edges for tools in the same chain.
   Repeated collaboration edges get log-scaled weights: `log(1 + count)`.

8. At runtime, use a dynamic ReAct loop.
   The agent can choose `DISCOVER`, `INVOKE`, or `RESPOND`. On `DISCOVER`, it converts the current request/history/action content into a query and retrieves more tools; the accessible tool set grows over time.

9. Server discovery combines two channels.
   Direct semantic matching: max embedding similarity between global/subtask queries and server summaries.
   Graph propagation: extract query-side intentions, match to intention nodes, seed those plus relevant tool nodes, then run Personalized PageRank.

10. Tool reranking happens only inside retrieved servers.
   Tool score combines description similarity, intention similarity, and graph relevance/PPR score.

11. Return a small set of discovered servers/tools to the agent.
   The paper’s central claim is that this exposes enough schema for action while avoiding full-library prompt bloat.

**Why it works**

The causal claim is: user tasks and subtasks are usually goal-level, while tool schemas are low-level and often incomplete. Adding an intermediate “intention” abstraction aligns retrieval queries with what the user is trying to do, not just with literal tool descriptions.

The graph adds two useful structures:

1. Shared intention nodes connect functionally similar tools across servers, even when names/descriptions differ.

2. Tool collaboration edges capture prerequisite/follow-up relationships, so retrieval can surface tools needed for multi-step chains, not just tools matching the initial wording.

The paper’s own failure analysis supports a narrower claim: SING mainly reduces upstream retrieval/discovery failures, especially in large noisy pools. It does not solve downstream parameter binding, call ordering, output parsing, or final reasoning.

**Preconditions**

SING needs:

1. A large enough tool surface where full schema injection is costly and one-shot retrieval is lossy.

2. Structured tool metadata: server names/descriptions, tool names/descriptions, schemas.

3. An offline LLM pipeline capable of generating synthetic queries, chains, normalized I/O types, atomic intentions, and quality judgments.

4. Embeddings good enough for query/server/tool/intention matching. The paper uses `Qwen3-Embedding-8B`.

5. A graph store or equivalent local structure supporting weighted edges and PPR-style propagation.

6. Runtime orchestration that allows tools to be discovered during execution, not only before the first model call.

7. Evaluation traces where “right tool was retrieved vs not retrieved” can be separated from downstream tool-use failures.

8. For transfer to OUR system: the tool metadata and use traces must be local and non-hosted. This matches the primer constraint; adopting a hosted MCP/runtime framework would be non-transfer.

  `MCP-Universe`: `206` tasks.

**Limitations / failure modes / non-transfer**

The main limitation is that SING improves discovery, not execution. The paper explicitly leaves parameter filling, malformed calls, wrong call order, output misinterpretation, premature stopping, forgotten constraints, and final-answer construction as remaining bottlenecks.

The method is LLM-synthesis-heavy. If the synthetic intentions are bad, too generic, or biased toward the generator model’s phrasing, the graph can encode the wrong abstraction. The appendix suggests same-family DeepSeek decomposition aligns better with DeepSeek-generated intention nodes, which is a transfer risk.

The downstream evaluation is noisy and expensive: live MCP servers, changing external content, tool availability, generated arguments, and LLM judges all add variance. The paper reports no CIs or statistical tests, so the small MCP-Bench overall gains, e.g. `67.6 -> 68.4`, should not be overread.

The corpus is filtered to deployable/public MCP servers and excludes private workspaces, non-text inputs, deprecated/platform-managed servers, and unstable deployments. That improves reproducibility but narrows the claim.

The schema-token reduction is real for large tool libraries, but it compares against all-tools-in-context, which is a weak baseline for any mature lazy-loading harness. For OUR system, the relevant baseline is existing `ToolSearch`, not full schema injection.

Non-transfer: do not adopt SING as a hosted framework or MCP runtime. The transferable part is the mechanism: intention graph + collaboration edges + PPR reranking + trace-based eval.

**Integration into OUR system**

ToolSearch: applicable. Concrete bolt-on: add an offline local intention graph behind deferred tools. Nodes should be `tool`, `skill`, `workflow recipe`, possibly `hook/rule` only when callable or decision-relevant. Edges: `has_intention`, `co_used_after`, `co_used_with`, and `requires_context`. At query time, keep BM25/metadata search as one channel, then rerank with intention-node matching plus graph propagation. This directly targets the primer’s “large tool surface loaded lazily by query.”

session-trace / agentlogs.db: applicable. Concrete bolt-on: mine successful and corrected traces for real collaboration edges instead of relying only on synthetic chains. Store, or derive, edges like `tool_search -> read_skill`, `rg -> sed`, `ToolSearch -> connector tool`, with outcome labels. Principal check should remain raw transcript replay, not only the graph.

act-drain / blindspot loop: applicable. Concrete bolt-on: when act-drain classifies over-ask or missed-tool failures, emit candidate intention aliases and missing collaboration edges into the ToolSearch graph. This is a better fit than adding more prose rules because the measured blindspot is tool/capability discovery under evolving task state.

skills/rules/hooks: partially applicable. Concrete bolt-on: extract stable verb-object intentions from skill frontmatter/descriptions and rules, but do not make hooks enforce SING behavior. Hooks could only validate that the graph build has not drifted from skill metadata. Do not add another flat rule saying “use the right tool”; the paper’s own lesson is to externalize retrieval structure.

MEMORY: applicable but cautiously. Concrete bolt-on: make condensed MEMORY entries link first-class to raw agentlogs/session-trace evidence and optionally to intention nodes. Do not let MEMORY become the retrieval corpus of truth; use it as high-level aliases and prior context, with raw trace as verifier.

`/eval + ~/Projects/evals`: applicable and necessary before adoption. Concrete eval: compare current ToolSearch BM25/lazy loading vs ToolSearch+intention graph on held-out agentlogs tasks. Metrics: Recall@5 for eventually-used tool/skill, “needed tool discovered before user correction,” downstream task success, schema/token exposure, and cost. Include trace-derived negative cases where the user corrected tool choice.

predict-then-falsify: applicable. Concrete gate: before shipping the graph reranker, pre-register the expected mechanism, e.g. “missed-tool corrections fall because the correct tool appears in top-5 before first failed attempt.” Accept only if session traces show the correct candidate was retrieved earlier, not merely if final task success improves.

Workflow / file-bus just recipes: applicable. Concrete bolt-on: nightly local job builds the intention graph from installed tool metadata, skill docs, just recipe metadata, and recent successful traces; writes a derived, gitignored artifact. Keep generator + source tracked, output ignored.

act-drain plus Workflow is the best first integration path: generate a local ToolSearch graph from real traces, run an eval against historical missed-tool/over-ask episodes, and only then expose graph reranking in live ToolSearch.

Not-applicable surfaces: generic hooks as primary enforcement. A hook cannot semantically know the right tool for an evolving task without becoming an expensive flaky judge. The mechanism belongs in retrieval/eval, not blocking policy.
