**Mechanism**

1. Store project memory as an append-only local log: `.projectmem/events.jsonl`.

2. Every log entry is one typed event. Core event types are `issue`, `attempt`, `fix`, `decision`, and `note`.

3. `attempt` events carry an outcome: `worked`, `failed`, or `partial`.

4. Writes come from multiple capture paths: git hooks, a file watcher, the `pjm` CLI, and MCP write tools.

5. All writes funnel through one append path, `storage.append_event`, which normalizes timestamp, redacts secrets, appends the JSONL event, and considers global-memory promotion.

6. Derived files are regenerated deterministically from the log:
   `summary.md` for compact agent-readable memory, `PROJECT_MAP.md` for detected repo structure, per-issue files for token-efficient reads, and optional dashboard output.

7. The MCP server exposes 14 typed tools: 9 read tools and 5 write tools. Read tools include summary, search, token-budgeted context, global gotchas, and `precheck_file(path)`. Write tools mirror the event schema.

8. The judgment gate uses the same log. Before an agent or git hook touches a file, `precheck_file(path)` looks for failed attempts, open issues, and churn tied to that path.

9. If history says the file or approach is risky, the gate returns an advisory warning such as “you tried this 2 days ago — it failed.”

10. Cross-project lessons are promoted to `~/.projectmem/global` when they look like library-level gotchas. Later projects with matching detected stacks receive those gotchas with source-project attribution.

11. For non-MCP clients, a Markdown bridge / wrapper injects bounded context assembled from active warnings, recent decisions, relevant fixes, and project map slices.

**Why it works**

The causal claim is architectural, not model-capability-based: agents repeat mistakes because prior project state is not durable, not because the model cannot reason within a single session.

The paper’s mechanism works if three claims hold:

1. Repeated failures are often file-, issue-, library-, or approach-local enough to be recognized from structured history.

2. A deterministic warning before action is cheaper and more reliable than hoping the agent reads passive memory and remembers to apply it.

3. Plain-text append-only logs are easier to audit, diff, regenerate, and trust than mutable summaries or LLM-extracted vector memories.

The paper names this “Memory-as-Governance”: memory does not merely answer retrieval queries; it acts on the next proposed action. The strongest transferable idea is not the MCP server. It is the conversion of historical failure records into a deterministic pre-action gate.

**Preconditions**

The system needs:

1. A project-local event log with enough real history. Cold start weakens the gate; git-history backfill only partially mitigates this.

2. Event records that distinguish failed attempts from successful fixes. If failures are not logged or are logged vaguely, the gate has little usable signal.

3. Stable enough file paths, issue IDs, or stack/library identifiers to match future actions to prior failures.

4. Hook/tool-call integration before the risky action. Commit-time warnings are later and weaker than pre-tool-call warnings.

5. A tolerance for advisory false positives. The paper explicitly keeps warnings advisory because old failures may no longer apply.

6. Local filesystem access and developer willingness to keep memory artifacts in or near the repo.

7. Secret redaction before append, because plain-text logs may be committed.

8. For cross-project memory, reasonable stack detection from manifests such as `package.json`, `pyproject.toml`, `Cargo.toml`, or `go.mod`.

9. For our system specifically: a typed projection from raw `agentlogs.db` / session transcripts into failure-attempt-fix records. Raw transcripts alone are too unstructured for the proposed deterministic gate.

**Measured results**

Implementation claims:

- Three runtime dependencies.
- Python package, Python `>=3.10`.
- Installed via `pip install projectmem`; initialized with `pjm init`.
- Three console entry points: `projectmem`, `pjm`, and `pjm-mcp`.
- 14 MCP tools: 9 read, 5 write.
- 19 CLI commands.
- 37 automated tests.
- CI on Python 3.10-3.12.
- Footprint under 5 MB.
- Storage is file-based; no database engine and no network client in the core path.

Token-cost estimates:

- MCP mode: roughly 800-1,500 tokens loaded per session via `get_summary()` and related calls.
- Markdown bridge: roughly 2,500 tokens.
- No memory layer: estimated 5,000-20,000 tokens per session to reconstruct context.
- Claimed reduction: exceeding 50% per session.
- Important caveat: these are usage estimates over ranges, not a controlled benchmark.

Self-study:

- Duration: roughly two months, Mar 30-May 29, 2026.
- Projects: 10 real projects.
- Events: N = 207 real logged events.
- Event composition:
  - Notes / gotchas: 126, 61%.
  - Decisions: 52, 25%.
  - Attempts: 11, 5%.
  - Issues: 10, 5%.
  - Fixes: 8, 4%.
- Project distribution shown anonymized, largest project had 97 events.
- The paper explicitly does not claim causal productivity improvement from the self-study. It claims only that structured memory accumulated in realistic use.

Compatibility validation:

- Client/model names are not specified as a controlled eval.
- No model performance benchmark is reported.

Baselines:

- Token baseline: no-memory context reconstruction estimate of 5,000-20,000 tokens.
- Capability comparison baseline: table compares design properties against memory and guardrail systems, but not task accuracy.

N / CIs:

- No confidence intervals.

**Limitations / failure modes / non-transfer**

The big limitation: the paper has a good mechanism but weak empirical validation. It does not yet show that the gate prevents repeated failed fixes at a measured rate.

Specific limitations:

1. Cold start: with no events, the judgment gate has no history.

2. Logging quality bottleneck: if agents or hooks do not record failed attempts precisely, the deterministic lookup cannot help.

3. False positives: a prior failure on a file may not apply to a new, valid change.

4. Advisory-only gate: because false positives are expected, the gate warns rather than blocks. That reduces enforcement power.

5. File-level matching is coarse. A file can contain unrelated areas; future work admits hunk-aware judgment would be better.

6. No semantic retrieval by design. This improves determinism and cost, but sacrifices fuzzy recall.

7. Single-user local system. Team synchronization is only future work.

8. Token savings are estimated, not benchmarked.

9. Capability table is design comparison, not accuracy comparison.

10. Self-study is author-instrumented and not causal evidence.

11. The event distribution is mostly notes and decisions; only 11 attempts and 8 fixes feed the core repeat-failure gate. That is thin evidence for the paper’s strongest claim.

12. Non-transfer: the full package is less relevant to our system because we already have `agentlogs.db`, `MEMORY`, hooks, session tracing, and append-only-ish governance surfaces. The transferable part is the typed event projection plus deterministic pre-action warning, not adopting `projectmem`.

**Integration into OUR system**

Best integration: `session-trace / agentlogs.db` + `skills/rules/hooks` + `predict-then-falsify`.

Concrete bolt-on:

1. `session-trace / agentlogs.db`: add a deterministic projection from raw sessions into typed memory events:
   `issue`, `attempt_failed`, `attempt_partial`, `fix_worked`, `decision`, `note`.
   Each projected event must carry raw transcript span IDs, repo, path, command/tool, timestamp, and optional commit hash. This addresses our primer’s gap: raw agentlogs exist, but the link from condensed memory to raw is not first-class.

2. `skills/rules/hooks`: add a pre-tool advisory hook for `Edit`, `Write`, `apply_patch`, and risky `Bash` commands. The hook queries the typed failure projection for:
   same repo + same path,
   same command family,
   same named subsystem,
   same error signature,
   or same failed-fix text fingerprint.
   Output should be a concise warning with the raw `session-trace` link, not a long memory dump.

3. `act-drain / blindspot loop`: use daily correction mining to populate the typed projection. Map existing classes:
   `GROW_COVERAGE`, `RAISE_AUTONOMY`, `REDUCE_ERROR` into durable events only when they include an action/failure/fix triple. This avoids accreting another flat rule list.

4. `MEMORY`: do not duplicate projectmem’s `summary.md`. Instead add first-class backlinks from each condensed MEMORY lesson to exact `agentlogs.db` session spans and typed events. Memory remains condensed; session-trace remains evidence.

5. `/eval + ~/Projects/evals`: build the paper’s missing benchmark before trusting the gate. Metric:
   `repeat_failure_prevented_rate = warnings fired before seeded repeated failed action / seeded repeats`.
   Also measure false-positive rate, over-ask increase, token overhead, and whether the warning changed the action.

6. `predict-then-falsify`: every new memory-gate rule must pre-register the intended mechanism:
   “When a future agent attempts the same failed edit/command/path pattern, the hook fires before tool execution and the subsequent trace avoids the repeated failure.”
   Accept only if session traces show the hook fired at the intended moment. Revert or demote if it mostly fires on irrelevant edits.

7. `Workflow / file-bus just recipes`: add a recipe that renders the typed failure neighborhood for a repo or path, probably adjacent to `just session-trace <uuid-prefix>` and `operator-status-briefing`. This should be read-only and derived from `agentlogs.db`.

8. `ToolSearch`: NOT-APPLICABLE as a primary integration. The paper’s mechanism is not lazy tool discovery; it is local failure-history gating. ToolSearch could expose the query surface later, but it is not where the mechanism belongs.

9. `act-drain` accretion guard: this paper could worsen our measured “policy maze” failure if naively translated into more rules. The safe integration is a structured event substrate plus one generic pre-action lookup, not many bespoke warnings.

Verdict: complement, do not adopt wholesale. The mechanism is directly aligned with our harness thesis: verifier-gated autonomy through architecture. The empirical numbers are too weak to justify vendor-level confidence, but the design suggests a precise next bolt-on: typed failure events over `agentlogs.db` feeding a deterministic pre-tool warning, evaluated with predict-then-falsify.
