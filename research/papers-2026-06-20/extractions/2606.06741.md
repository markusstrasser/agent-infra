**Mechanism**

1. Input is a target task instruction `Ii` and execution environment `Ei`; hidden target tests `TiGT` are excluded during skill construction.
2. Stage 1 retrieves open-world knowledge:
   - `D(Ii, K)` retrieves task/domain knowledge: docs, APIs, repos, tutorials, best practices.
   - A skill planner converts that into a skill plan `pi`, including 1-4 skills, responsibilities, procedures, and domain rules.
   - `Dv(Ii, K)` separately retrieves verification anchors: reference values, dataset invariants, cross-validation procedures, expected output formats.
3. Retrieval queries are sanitized to remove benchmark names and identifiers that could leak target tests.
4. Stage 2 generates an initial skill set from `Ii`, `Ei`, `pi`, and retrieved knowledge.
5. A separate “Independent Verifier” LLM session generates deterministic `pytest` surrogate tests from the task/environment plus verification anchors, not from hidden GT tests.
6. The current skill is executed against surrogate tests. A non-LLM parser computes virtual pass rate `r̃ = passed / total`.
7. If `r̃ < 1.0`, the system emits structured diagnostics: failed assertions, root cause, revision suggestions.
8. A classifier labels failures as:
   - `SELF-FIXABLE`: implementation bug; revise from verifier feedback.
   - `NEEDS-DR`: knowledge gap; run targeted search and inject the new result.
9. Refinement repeats up to `J = 3` surrogate-failure retries, exiting only when surrogate pass rate reaches `1.0` plus auxiliary checks, or when budget/stall limits trigger.
10. Stage 3 freezes the final in-place skill state and evaluates it zero-shot on the hidden target tests. Ground truth enters only here.

**Why it works**

The causal claim is: agents can improve without target-task supervision if open-world resources provide both the skill content and independent verification anchors.

The paper’s theory is not “self-feedback is enough.” It claims the useful loop comes from two externalizations:

1. Open-world retrieval supplies missing domain/API/procedural knowledge that the model’s parametric memory lacks.
2. Verification anchors create a practice environment whose tests are grounded in independently checkable facts rather than hidden benchmark answers.

The transferable artifact is the explicit skill file, not updated weights. That makes the learned behavior inspectable and reusable across target models.

Skeptical read: the mechanism depends heavily on surrogate verifier quality. The paper measures correlation/coverage, but the verifier is still noisy: 56.9% precision and 60.7% agreement are meaningful but not strong enough to treat surrogate pass as truth.

**Preconditions**

- There must be accessible open-world sources relevant to the task: docs, repos, standards, tutorials, known reference values, or reproducible examples.
- The target task must allow useful surrogate assertions from observable inputs and public facts.
- The environment must be executable enough for generated tests and skill scripts to run.
- Hidden target tests/solutions must be isolated from the skill creator and verifier.
- Verification anchors must be disjoint from target-answer leakage.
- The task must tolerate a `pytest`-style verifier, or at least deterministic assertions. The paper admits this breaks for non-standard tasks like CVE patches, build-system fixes, and proof assistants.
- The skill artifact must be consumable by the target agent as context/procedure.
- Cost/latency must be acceptable: skill creation is expensive relative to simple skill generation.

**Measured results**

Models used:
- Target agents: `Opus 4.6 (Claude Code)` and `GPT 5.2 (Codex)`.
- Retrieval: Gemini Deep Research `deep-research-pro-preview-12-2025`; verification/targeted retrieval: `gemini-3.1-flash-lite`.
- Transfer targets: Haiku 4.5, Qwen 3 Coder, DeepSeek V3, Mistral Large 3.
- I would not flag these as pre-frontier inside the paper’s June 2026 framing, but the exact model identities are paper claims, not independently verified here.

- Evaluation: 5 independent zero-shot runs per constructed skill set.
- CIs: not reported.

- N = 84.
- Proxy/GT table:

  - 1 iteration: 81.2%
  - 3 iterations: 82.7% peak
  - 5 iterations: 79.9%
  - 10 iterations: 78.0%

Cost:
- Per SkillsBench task, Opus 4.6:
  - Skill creation total: ~749K tokens, ~39 min.
  - GT evaluation: ~400K tokens, 91.5 min.
  - End-to-end: ~1.14M tokens, ~131 min.

  - Skill creation: 31.4 API-hours and ~47M tokens.
  - Full end-to-end: 140 hours and ~97M tokens.

**Limitations / failure modes / non-transfer**

- Web/repo sources can be noisy, stale, or contradictory; the paper itself says provenance tracking and source validation are required.
- Surrogate verifier is not a ground-truth verifier. Precision is only 56.9%, agreement only 60.7%.
- False positives are common: 25/84 proxy-pass cases failed GT. Causes:
  - 12 high-accuracy near misses, mean accuracy 0.81, failed all-or-nothing reward.
  - 11 partial-correctness cases, mean accuracy 0.52, structurally valid but semantically incomplete.
  - 2 genuine misalignment cases, accuracy 0.0, involving chemical similarity search and code translation.
- False negatives: 8/84 proxy-fail cases passed GT.
  - 3 near-pass surrogate failures at 89-97%.
  - 5 verifier infrastructure failures where pytest-style validation was unsuitable.
- More refinement can hurt: SocialMaze drops from 82.7% at 3 iterations to 78.0% at 10, consistent with overfitting to surrogate tests.
- Manufacturing stayed 0.0% for all automated SkillsBench methods, including OpenSkill.
- Gains on SocialMaze and ScienceWorld are small, +0.9 to +2.2 over strongest baseline, so the broad benchmark claim is directionally positive but not uniformly large.
- The “88.9% GT intent coverage” uses an LLM judge and only 15 sampled tasks; useful but not a hard measurement.
- The isolation audit is process/prompt/container based, not a formal proof.
- Cost is high: ~1.14M tokens and ~131 min per task end-to-end in the SkillsBench Opus setup.
- Non-transfer risk to OUR system: the paper uses hosted Gemini Deep Research and commercial retrieval. The primer explicitly rejects adopting hosted runtimes/frameworks as dependencies; only the mechanism should transfer.

**Integration into OUR system**

Concrete integration: **predict-then-falsify gate + skills/rules/hooks + session-trace + ToolSearch**.

Bolt-on:

1. Add an `OpenSkill-lite` harness-edit verifier for proposed skill/rule/hook changes.
2. Before accepting a new or modified skill/rule/hook, require:
   - a retrieved evidence pack from existing local surfaces first: `ToolSearch`, repo `rg`, `session-trace / agentlogs.db`, and `MEMORY`;
   - a generated deterministic virtual test/check derived from independent anchors, not from the desired final outcome;
   - a pre-registered prediction: which trace metric or failure class should move.
3. Run the candidate against historical `session-trace` slices:
   - positive cases: prior failures the edit claims to prevent;
   - negative cases: nearby sessions where the edit should not fire.
4. Accept only if the intended mechanism fires and the false-positive rate is tolerable; otherwise reject or narrow.
5. Store the condensed lesson in `MEMORY` with a first-class link back to raw agentlogs evidence, because the primer says this link is currently not first-class.
6. Use `act-drain / blindspot loop` as the source of candidate failure classes, especially over_caution / over-ask. The paper’s verifier loop maps well to “don’t just add a rule; build a surrogate replay check that the rule would have changed the past trace.”
7. Use `Workflow tool / file-bus just recipes` for orchestration, not a hosted service:
   - `gather anchors`
   - `generate surrogate checks`
   - `replay trace`
   - `score prediction`
   - `emit accept/reject packet`
8. Use `/eval + ~/Projects/evals` for benchmark storage and cost accounting. Track token/time cost because the paper’s method is expensive and OUR system treats token cost as first-class.

Do not integrate as:
- A hosted OpenSkill dependency.
- A general deep-research-before-every-skill workflow.
- A flat skill-generation loop that adds more rules/hooks without deletion pressure.

Most valuable narrow transplant: **surrogate verifier from independent anchors for harness edits**. It directly addresses OUR “policy maze” risk: every new rule/hook must prove, on past traces, that it catches the intended failure without broad collateral firing.
