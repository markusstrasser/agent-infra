**Mechanism**

1. Start with a multi-agent orchestrator that emits an orchestration plan `z` for input `x`: roles, role descriptions, collaboration structure, interaction graph.
2. Execute the plan with subagents to get intermediate responses `Y` and final answer `a`, forming trajectory `τ = (x, z, Y, a)`.
3. Mine existing MAS-Orchestra artifacts rather than collecting human labels:
   - `specialized-over-base`: prefer plans from a trained orchestrator `πθ` over plans from the backbone `π0`.
   - `correct-over-incorrect`: for the same input, prefer orchestrations whose full rollout produced a correct final answer over ones that produced an incorrect answer.
4. Convert these into pairwise plan-level comparisons `(x, z_w, z_l)`.
5. Fine-tune a reward model initialized from `Skywork-Reward-LLaMA-3.1-8B` using Bradley-Terry loss so it scores the preferred orchestration higher:
   `-log σ(r(x,z_w) - r(x,z_l))`.
6. Use the trained orchestration reward model in two places:
   - Test-time scaling: sample `N` candidate orchestrations, score plans before subagent execution, execute only the highest-scoring plan.
   - Orchestrator training: use reward-model scores over sampled orchestrations to compute GRPO-style normalized advantages, avoiding full rollout correctness rewards.

**Why it works**

The causal claim is that orchestration quality is a bottleneck separable from full subagent execution. If a plan’s roles, decomposition, and interaction graph are better, downstream agents are more likely to produce correct final answers. Therefore a reward model trained on plan-level contrasts can learn a proxy for “will this orchestration lead to success” before paying for the expensive rollout.

The efficiency claim is stronger than the accuracy claim: scoring `z` is cheaper than executing all candidate `Y` rollouts. The method wins when plan-level features are discriminative. The paper’s own HotpotQA/GPQA results suggest the mechanism weakens when candidate orchestrations are structurally similar or when domain transfer is required.

**Preconditions**

- You have stored orchestration artifacts: prompt/input, candidate orchestration plans, final correctness labels, and preferably checkpoints or base-vs-trained plan samples.
- Final-answer correctness must be cheaply knowable for at least some training data. The method bootstraps from correctness labels; it is not magic supervision.
- The system must expose orchestration as a structured object `z`, not just opaque transcript prose.
- Candidate plans must vary enough for a plan-level reward model to separate good from bad. Low orchestration diversity reduces signal.
- Domain-specific reward models are assumed in the paper. A single cross-domain model is explicitly unresolved.
- Requires GPU training resources in the reported setup: `2 x RTX PRO 6000 96GB`, batch size `16`, actor rollout `8`, LoRA rank/alpha `32/32`, all linear target modules.
- The paper’s setup is hosted/lab-scale MAS training, not a single-operator local harness. Direct dependency adoption is not appropriate for OUR system.

**Limitations / failure modes / non-transfer**

- Plan-level reward only helps if plan-level differences matter. HotpotQA and GPQA show smaller or non-winning gains.
- Reward model is trained domain-specifically; unified cross-domain reward modeling is future work, not demonstrated.
- Training data depends on existing orchestrator artifacts and sampled trajectories. Bad or narrow artifacts cap the reward model.
- Correct-over-incorrect labels are only as good as the final-answer verifier. If final correctness is noisy, the reward model learns that noise.
- It can Goodhart on orchestration style: plans that look like historically successful plans may score high even when the actual task needs a different mechanism.
- It does not solve subagent reasoning quality. A good plan with weak tools/models still fails.
- It is not directly transferable to OUR single-operator local harness because the paper assumes many sampled orchestrations, GPU reward-model training, and MAS-Orchestra-style structured plan objects.
- The paper has OCR/table ambiguity and at least one substantive data-mix inconsistency, so exact ablation interpretation should be treated cautiously.
- No CIs or uncertainty estimates are reported; gains on small tests such as AIME `N=60` may be unstable.

**Integration into OUR system**

- `/eval + ~/Projects/evals`: APPLICABLE. Build a small eval for orchestration-plan selection, not full Orch-RM training. Use existing session tasks with known outcomes, sample 3-8 candidate workflow plans, score via cheap deterministic/LLM rubric, then execute/select. Measure accuracy, token cost, and whether the selected plan changed the outcome.
- `session-trace / agentlogs.db`: APPLICABLE. Add an extraction view over traces: `(task_id, input_summary, orchestration_plan, surfaces_used, subagents/tools_called, outcome_label, human_correction_type, token_cost)`. This is the local analog of their artifact mining.
- `predict-then-falsify`: STRONGLY APPLICABLE. Before any reward/scorer bolt-on, pre-register: “plan-level scorer should reduce over-ask or improve accepted autonomous actions without increasing correction rate.” Accept only if traces show the mechanism fired: scorer selected a different plan, and the selected plan improved the target metric.
- `Workflow tool / file-bus just recipes`: APPLICABLE. Add a plan-selection gate before expensive fan-out: generate candidate workflow plans, score only the plan artifact, then run the selected plan. Do not train a model first; start with a transparent scorer over plan features and retrospective labels.
- `act-drain / blindspot loop`: APPLICABLE. Use the loop to create pairwise preferences from human corrections: plans that led to `over_caution=63 / over-ask` lose against plans where the agent acted and passed verification. This directly targets OUR measured blindspot.
- `skills / rules / hooks`: APPLICABLE, but not as a broad hook maze. Add one narrow hook/rule surface: require structured plan objects for multi-agent fan-out so traces contain a scoreable `z`. Do not add a reward-model hook until `/eval` proves it changes outcomes.
- `MEMORY`: APPLICABLE. Store condensed lessons with first-class links back to raw trace IDs. The paper’s useful pattern is not reward modeling itself; it is using intermediate artifacts as supervision. MEMORY currently lacks first-class condensed-to-raw linkage per primer.
- `ToolSearch`: PARTIALLY APPLICABLE. Use plan scoring to choose deferred tool loads only when there are multiple candidate tool surfaces. Concrete bolt-on: log ToolSearch query, selected tool, rejected alternatives, task outcome; later mine win/loss pairs. Do not put a learned scorer in front of ToolSearch yet.
- `act-drain` accretion risk: this paper does not solve policy maze growth. Any integration must compete against the null: a simple retrospective SQL/rubric may get most of the benefit without a trained reward model.
- NOT-APPLICABLE as dependency: do not adopt Orch-RM/MAS-Orchestra as a framework. It likely requires hosted/lab-scale training assumptions and a different MAS architecture. Pattern-extract only: artifact-level pair construction, plan-before-rollout scoring, and trace-verified selection.
