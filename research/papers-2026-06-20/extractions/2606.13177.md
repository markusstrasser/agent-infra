**Mechanism**

MEMREFINE is an offline, post-construction memory-store compressor.

1. Start with an already-built memory store `M0`, where each entry has text, an embedding, and optional links/timestamps/metadata.
2. Set a target budget `B = rho * size(M0)`, with tested budgets of 70%, 60%, 50%, 40%, and 30%.
3. While current size exceeds `B`, choose the most similar unresolved pair of memory entries by cosine similarity over embeddings.
4. Send that pair to an LLM judge.
5. The judge returns one of three actions:
   - `DELETE`: remove one redundant entry.
   - `MERGE`: ask a merge LLM to synthesize one shorter entry preserving distinct facts from both.
   - `PRESERVE` / `nothing`: leave both entries unchanged and cache that pair so it is not revisited.
6. For graph memories, deletion prunes dangling links; merging inherits the union of links and recomputes the merged embedding.
7. Stop when the budget is met or when no unjudged pair can be compressed without violating factual preservation.

It does not change retrieval or memory construction. It sits between memory construction and future retrieval.

**Why it works**

The causal claim is that memory value is relational, not per-entry. A memory that looks important may be redundant because another node already contains the fact; a memory that looks low-value may be needed because it complements another node.

Similarity is used only as a proposal mechanism: it finds pairs likely to overlap. The LLM judge is supposed to decide factual relation: redundant, complementary, or distinct. That separation is the paper’s central bet. Fixed similarity or graph centrality can find related nodes, but cannot reliably decide whether the relationship implies delete, merge, or preserve.

The theoretical framing is query-agnostic max-min preservation: because future queries are unknown, safe compression should remove only facts that are redundant or non-factual, rather than pruning based on a current query.

**Preconditions**

- The memory store must already exist and be decomposed into entries/nodes.
- Entries need embeddings so similar pairs can be proposed cheaply.
- The store must contain redundancy or fragmentation; already-consolidated stores have less headroom.
- An LLM judge must be good enough to distinguish redundant, complementary, and distinct factual content.
- The memory domain must tolerate offline maintenance passes.
- For destructive use, the system needs audit logs, soft deletion, or provenance links, because delete/merge operations persistently alter memory.
- It assumes pairwise local judgments are a decent surrogate for global future-query utility. That is plausible but not proven.
- It is tested mostly on conversational memory, not tool-use traces, codebase governance rules, or multi-agent operational logs.

**Measured results**

Models and evaluators:
- Candidate embeddings: `all-MiniLM-L6-v2`.
- Main judge and merge model: `gpt-5-mini`.
- Compression-model comparison: `Qwen3-8B` as judge/merge, retrieval and QA fixed.
- LongMemEvalS automatic judge: `GPT-4o-mini`, which is pre-frontier by current 2026 standards.
- Scaled dataset generation: personas/events with `gpt-5-mini`, dialogues with `gpt-4o-mini` pre-frontier.
- All results are single compression/evaluation runs. The paper explicitly reports no confidence intervals or error bars.

Datasets:
- LoCoMo: 10 samples, 1,986 questions across single-hop, multi-hop, temporal, open-ended, counterfactual.
- Scaled LoCoMo-style 3x: 5 samples, 400 sessions, 8,000 turns, 2,720 QA pairs.
- Scaled LoCoMo-style 10x: 5 samples, 1,350 sessions, 27,000 turns, 9,180 QA pairs.
- LongMemEvalS: 60 questions, 10 per type.

**Limitations / failure modes / non-transfer**

- Single-run results only; no CIs, no error bars, no variance across compression seeds.
- Benchmarks are conversational memory, not real deployed longitudinal agent logs.
- Scaled LoCoMo-style datasets are synthetic stress tests, not real user histories.
- The method depends on LLM judgment; weaker judges degrade under tight budgets.
- Pairwise compression can miss global dependencies: a fact may look redundant pairwise but be needed as provenance, contradiction history, or temporal sequence evidence.
- Delete/merge is dangerous for append-only institutional memory unless applied only to derived views.
- It does not address policy-rule accretion directly; compressing memory entries is not the same as safely deleting governance rules or hooks.
- It may fail on adversarial, legal, audit, or scientific memory where exact wording and source lineage matter.
- It assumes budget pressure is important. In OUR system, raw `agentlogs.db` storage is cheap; retrieval quality and policy maze are the real constraints.
- Hosted/runtime adoption is not relevant; only the mechanism is useful.

**Integration into OUR system**

Best fit: `MEMORY` plus `session-trace`, as a derived compression layer, not destructive mutation.

Concrete bolt-on: build a `MEMORY-refine` maintenance pass that operates over condensed MEMORY entries and their links to raw `agentlogs.db`. It proposes `DELETE_FROM_RETRIEVAL_VIEW`, `MERGE_IN_DERIVED_VIEW`, or `PRESERVE`, but never deletes append-only MEMORY or raw transcripts. Output is a budgeted retrieval view with provenance pointers back to raw session IDs. This directly addresses the primer’s missing first-class condensed-to-raw link.

`act-drain`: applicable. Add a weekly/daily “policy maze” pass over rules/hooks/lessons surfaced by blindspot loop. Candidate pairs are similar rules, duplicated cautions, or overlapping hook advisories. The LLM judge labels redundancy/complementarity/distinctness. Action should be “propose consolidation” rather than auto-delete, because governance edits have semantic risk.

`session-trace`: applicable. Use session-trace as the audit substrate for every merge/delete recommendation: each compressed MEMORY entry must retain raw transcript spans or session IDs. This avoids turning compression into unverifiable summary drift.

`skills/rules/hooks`: applicable only as a reviewer, not an auto-mutator. Use MEMREFINE-style pair review to identify duplicate flat rules and hook advisories. Do not let it directly edit `CLAUDE.md`, rules, or hooks.

`MEMORY`: applicable with strict append-only semantics. Canonical MEMORY stays append-only. Compression produces a derived retrieval index or “active memory view,” not canonical deletion.

`/eval`: applicable. Evaluate before adoption with a predict-then-falsify test: prediction should be lower retrieval noise or lower duplicate-rule surfacing at fixed recall of known correction cases. Metrics should include recall of prior high-value lessons, retrieval precision, token cost, and false merges.

`predict-then-falsify`: strongly applicable. Pre-register: “At 60% derived-memory budget, top-k retrieval over historical correction queries preserves >= baseline answerability while reducing duplicate/near-duplicate retrieved entries by X%.” Reject if the trace shows gains come from evaluator leniency or in-sample overfitting.

`Workflow`: applicable as an offline maintenance recipe. Add as a file-bus job that reads MEMORY/session-trace, writes candidate compression reports, then requires human or review-gate approval before changing any canonical surface.

`ToolSearch`: partially applicable. ToolSearch already lazily loads large tool surfaces. MEMREFINE’s candidate-pair/judge pattern could deduplicate tool descriptions or cluster near-equivalent tools, but this is lower priority than MEMORY/rules because ToolSearch is already budgeted by query.

Not applicable as a framework dependency. The paper offers a mechanism, not an infrastructure dependency worth adopting wholesale. The useful extraction is: similarity proposes candidates; an LLM judges factual redundancy/complementarity; canonical history remains intact; compressed views are derived and auditable.
