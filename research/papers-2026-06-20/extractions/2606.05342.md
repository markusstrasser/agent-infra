(2) **Mechanism**

SentinelBench is a benchmark, not a new agent architecture.

Step by step:

1. Build 10 synthetic web environments: MicroMail, MicroChat, MicroDin, MicroFy, MicroGram, MicroHood, MicroHub, MicroLendar, MicroScholar, MicroTube.
2. Populate them with synthetic personas, entities, text catalogs, and media assets, so web pages look stateful and coherent without hitting live services.
3. Define 100 monitoring scenarios, 10 per environment.
4. For each task, specify:
   - starting page
   - prompt
   - scheduled event timeline
   - `condition_at`
   - `kill_at` / end time
   - SQL success evaluator
   - passive / active / no-op type
   - absolute / relative criterion type
5. The harness calls `/init`, loads the database state and event schedule, then starts the agent at `/redirect`.
6. When the agent reaches `/redirect`, simulation time starts and events replay into the app database/UI.
7. The agent must monitor the page, act if required, and signal done by opening `/contact`.
8. The server cancels remaining events on `/contact`, then `/evaluate` runs the SQL success query and records timing.
9. Metrics are computed: success, completion time, reaction time, token usage, tool calls, and monetary cost if `costs.json` is provided.
10. The paper compares a baseline `sleep(time)` tool against `wait_for(condition, timeout)`.

`wait_for` mechanism:

1. Capture textual page snapshot as baseline.
2. Once per second, capture a new textual page snapshot.
3. Compute a unified diff with Python `difflib`.
4. Drop diff blocks already seen.
5. Ask the LLM whether the new changed blocks satisfy the natural-language condition.
6. Return when condition is judged true or timeout expires.
7. Periodically reload static pages and rate-limit to avoid thrashing.

(3) **Why it works**

The causal claim is that many long-running tasks are not bottlenecked by more agent action. They are bottlenecked by external state changes. Continuous action causes wasted tokens, longer trajectories, premature termination, and cost growth. A monitoring primitive lets the agent suspend expensive deliberation while a cheaper watcher checks for relevant state changes.

The benchmark works, in their claim, because it makes waiting first-class and measures the three-way tradeoff that ordinary web-agent benchmarks mostly miss: task success, reaction latency, and resource cost. No-op tasks also expose false-positive “declare success near the end” strategies.

The `wait_for` improvement works when a task’s trigger is visible as page-state change and can be detected from textual diffs. It reduces repeated full model/browser loops, so cost scales less with elapsed wall time than short-interval polling through `sleep`.

(4) **Preconditions**

For SentinelBench validity:

- The task must be representable in a synthetic web app with deterministic replay.
- Success must be checkable by SQL or by absence of `/contact` for no-op tasks.
- The agent must be invokable by shell command and exit when done.
- Token/cost metrics require cooperative self-reporting through `costs.json`; otherwise success/timing still work but cost accounting is incomplete.
- The synthetic environments must cover the UI path the agent actually takes. The authors explicitly warn that divergent trajectories may hit untested environment edges.
- Timing must be controlled enough for reproducible replay.

For `wait_for` transfer:

- Relevant state changes must appear in the current page text snapshot or after periodic reload.
- The condition must be expressible in natural language and judgeable from a diff block.
- The LLM diff judge must not miss subtle, visual-only, off-page, or context-dependent triggers.
- Polling cadence must be acceptable. Their implementation checks once per second, which is fine in synthetic apps but may be too aggressive or too weak depending on local tool surface.
- The system must tolerate waiting. Some agent loops and CLIs assume continuous tool progress or time out.

(6) **Limitations / failure modes / non-transfer**

- No confidence intervals, repeat counts, or statistical tests are reported. Treat the numeric deltas as baseline measurements, not settled effect sizes.
- Synthetic web environments are facsimiles. They may not capture real web flakiness, auth, anti-bot behavior, dynamic rendering quirks, notification systems, or rate limits.
- Event timing is artificial: target times are sampled and other event timings are LLM-generated. A real monitoring agent could exploit realistic update distributions; this benchmark does not measure that.
- Benchmark debugging was greedy: manual inspection plus baseline-run log review. Remaining environment bugs are likely on trajectories unlike tested ones.
- Most criteria are objective and persistent. Subjective triggers and ephemeral opportunities are underexplored.
- `wait_for` is text-diff-based. It may fail on visual-only changes, non-visible state, pages needing navigation, or changes requiring memory of a prior baseline beyond the current page.
- `wait_for` still uses an LLM as a condition judge, so it can miss events or false-trigger. The paper notes wait_for is slightly more prone to missing events and terminating late in the 40-minute GPT-5.4 plots.
- Passive success can be gamed by late false positives; no-op tasks reduce but do not eliminate benchmark-gaming risks.
- Cost measurements depend on self-reported token usage and May 15, 2026 prices. They are useful for relative shape, not durable absolute cost.
- GPT-4o results are pre-frontier for current frontier behavior. Do not use them to infer current flagship model rates.
- Direct transfer to our harness is partial: our system is local, file-bus/session-log/hook oriented, not a hosted browser-monitoring service. The benchmark mechanism transfers more than the web environments.

(7) **Integration into OUR system**

/eval + `~/Projects/evals`: concrete bolt-on. Add a “sentinel wait-vs-poll” eval lane for our own harness edits. Use synthetic local tasks built from agentlogs/file-bus states, not their hosted web environments. Metrics should be exactly the SentinelBench triad: success, reaction latency, token/tool cost. Include no-op tasks to catch premature “done” claims. This belongs in `/eval` because the paper’s real contribution for us is a measurement shape, not a dependency.

Workflow / file-bus just recipes: concrete bolt-on. Add a `wait_for_filebus(condition, timeout)` primitive for long-running workflows that currently poll logs, status files, or job outputs. Implementation should be deterministic first: file mtime/event stream/SQLite query delta, then optional LLM judge only for semantic conditions. This maps directly to the paper’s `wait_for`, but our observation source is files/SQLite/transcripts, not browser page text.

session-trace / agentlogs.db: concrete bolt-on. Add trace-level fields or derived metrics for “waiting behavior”: idle wait duration, poll count, wake trigger, premature termination, no-op survival, reaction time after external event. SentinelBench’s lifecycle maps well to `session-trace`: external event time, agent completion time, and tool/cost trajectory should be visible in replay.

predict-then-falsify gate: concrete bolt-on. For any harness change claiming “less over-ask,” “less spin,” or “better long-running monitoring,” require pre-registered predictions such as: poll tool calls down, reaction time not worse than threshold, no-op false positives not up, cost down at equal success. Accept only if traces show the intended wait/trigger mechanism fired. This is a stronger integration than adding another rule.

act-drain / blindspot loop: concrete bolt-on, but narrower. Use the paper’s no-op and premature-termination categories as new mining labels for long-running sessions: “gave up before condition,” “kept polling despite no new state,” “missed external trigger,” “asked human instead of monitoring.” This should not become more flat rules; it should feed measured loop proposals because the primer already flags policy-maze accretion.

skills / rules / hooks: concrete bolt-on. Add a path-scoped rule or skill note for long-running work: when progress depends on external state, prefer event/watch primitives over continuous action or repeated sleeps. Hook only if a deterministic predicate exists, e.g. repeated identical status polling without state delta. Do not add a broad semantic stop hook; that would worsen the existing flat policy maze.

MEMORY: NOT-APPLICABLE as primary integration. The paper does not solve condensed-to-raw memory linking. It can contribute a lesson after implementation, but MEMORY should not be the first landing zone.

ToolSearch: concrete but small bolt-on. For deferred tools, add “monitor/wait/watch” as retrievable capability vocabulary so agents can discover existing wait primitives before inventing polling loops. This is useful only if a real wait primitive exists in Workflow/file-bus; otherwise it is catalog theater.

Best skeptical integration: implement the measurement first in `/eval` and `session-trace`, then build the Workflow wait primitive only where the eval shows polling/spin/premature completion in our own traces. The paper’s numbers argue that harness tools can dominate model choice on waiting tasks, but they do not justify importing SentinelBench as a dependency or standing up its web environments.
