**Mechanism**

The paper proposes a five-phase methodology for building custom AI agents.

1. P1, Substrate: treat the LLM as a software component. The engineer must understand tokenization, context windows, alignment defaults, cost, hallucination, context pressure, latency, and prompt-cache structure. The paper’s concrete cache model is `tools -> system -> messages`, with tools most stable, system stable per session, and messages append-only.

2. P2, Building blocks: learn the primitives before adopting frameworks. The listed blocks are function calling, MCP, CLI surfaces, the “liteshell” pattern, agent loops, skills, characters, instruction sets, hooks, and scaffolding. Security belongs in deterministic host-side scaffolding, especially pre-tool hooks, not in prompt text.

3. P3, Prototype with a general-purpose agent: use Claude Code, OpenCode, or Cursor as a pair-programmer and reconnaissance tool against the real platform. The point is not just coding; it is discovering missing APIs, usable tool surfaces, and the correct security boundary.

4. P4, Harvest/fold/ship as CLI: harvest tools, allow-lists, skills, characters, and instructions from the prototype; fold them into a small agent loop with session persistence and pre-tool-use hooks; ship the agent as a CLI with stable invocation, session IDs, replay/trace, parseable output, and working `--help`. The paper calls this the Turtle pattern.

5. P5, Agent-tests-agent: use a general-purpose CLI agent to drive the custom CLI agent through scenario tests. Inputs are scenario, CLI invocation, and evaluation rubric. Output is structured pass/fail evidence from transcripts/tool traces. This complements unit/integration/E2E tests rather than replacing them.

The methodology then cycles: `P3 -> P4 -> P5 -> P3`. P1/P2 are preconditions; P3/P4/P5 are the recurring practice.

For orchestration, the paper’s concrete mechanism is CLI composition: one agent calls another agent’s CLI the same way it calls `gh`, `kubectl`, or a shell script. Multi-agent topology is treated as ordinary subprocess composition plus session traces, timeouts, depth budgets, and resource limits.

**Why it works**

The causal claim is that custom-agent quality comes from fitting the agent to one job and exposing it to behavioural pressure from other agents.

The paper’s main theory has several parts:

1. Stable substrate lowers iteration cost. If tools and system prompts are stable and messages are append-only, prompt caching makes repeated iteration cheaper. This makes repeated P3/P4/P5 cycles practical.

2. Framework-free small loops are more inspectable. The paper claims many failures live in dispatch, persistence, auth, and security scaffolding rather than in the loop itself; keeping the loop small makes failures easier to locate.

3. CLI surfaces exploit model priors and reduce context pollution. Models have strong learned competence with shell-like interfaces, and shell composition allows filtering before large outputs enter context.

4. Host-code hooks are reliable where prompts are not. Security and authorization must be deterministic gates because prompt instructions only steer behavior probabilistically.

5. Agent-tests-agent catches behavioral defects classical tests miss. Unit tests catch deterministic plumbing failures; scenario-driving agents catch vocabulary leaks, display bugs, prompt/parser mismatches, multi-turn drift, and user-facing failures.

6. The Turtle CLI shape makes agents composable. Once each agent is a CLI with `--help`, session IDs, parseable output, and traces, orchestration becomes subprocess composition rather than a special multi-agent framework problem.

Skeptical read: the causal story is plausible and well-aligned with our harness philosophy, but the paper mostly offers methodology plus internal case evidence, not controlled causal proof.

**Preconditions**

The paper’s own preconditions:

1. Engineer understands LLM substrate enough to diagnose usage/cost records and cache shape.

2. Engineer understands function calling, MCP, CLI/liteshell, agent loops, skills, characters, hooks, and scaffolding.

3. Real platform/tool surface exists. P3 requires building against the actual application, not a mock-only design.

4. Agent can be shipped as a CLI or CLI-like facade. P5 depends on another agent being able to drive the artifact.

5. Security boundary can be enforced in host code. If authorization lives only in prompts, the methodology’s safety model fails.

6. Scenario suite and rubric can be written. P5 requires behavioral scenarios with pass/fail criteria and transcript evidence.

7. Session traces/tool traces are observable enough to inspect. Without traces, agent-tests-agent loses its evidence channel.

8. For CLI multi-agent composition: subprocess timeouts, depth budgets, resource caps, and output discipline must exist. The paper explicitly notes shared-host resource isolation is not free.

OUR-system preconditions for adoption:

1. Use existing `session-trace / agentlogs.db` as the trace substrate.

2. Use existing `skills/rules/hooks` as the instruction/enforcement substrate.

3. Use `Workflow tool / file-bus just recipes` for CLI composition, not a hosted orchestrator.

4. Use `/eval + ~/Projects/evals` for behavioral scenario suites.

5. Use `predict-then-falsify` to prevent methodology cargo-culting: preregister what mechanism should improve before accepting a harness change.

**Measured results**

This is not a controlled benchmark paper. Results are mostly internal deployment evidence, practitioner benchmark citations, and illustrative calculations.

Claimed/internal deployment evidence:

1. AAC build time: built over roughly ten days, from 28 March to 6 April 2026, by one developer with an AI pair-programmer.

2. Deployment: in production at two universities since April 2026.

3. Users: UPC about 150 educator-creators; UPV/EHU about 50 educator-creators.

4. P5 bug finding: internal documentation logs “seven bugs”; paper reports four representative cases:
   - confirmation loop: numbered approval option caused repeated re-asking;
   - jargon leak: educator saw internal pipeline/debug vocabulary;
   - internal fields exposed: e.g. Group ID surfaced to educator;
   - session resume showed internal `[System: Skill startup]` message.

5. Nature of seven bugs: all seven were naming, format, vocabulary, or display defects at the human-system interface; none was a crash or timeout. This is a useful qualitative result, not a statistical measurement.

6. Production usage of P5-like testing: at UPC, nearly half of about 150 creator-users now build tests this way. Exact numerator is not given. No CI.

Transfer evidence:

1. A non-author developer applied the methodology to another LAMB subproject, building a Moodle-CLI integration and rubric-based evaluation agent.

2. Status: in progress, pending publication and undergraduate defense in late June 2026. Treat as forthcoming corroboration, not completed evidence.

3. Planned larger test: Barcelona Supercomputing Center course, June-July 2026. Not a result yet.

Token/cost figures and benchmark citations reported by paper:

1. MCP vs CLI: controlled matched-task benchmark reports about 35x more tokens via MCP than CLI, with hard-scenario task completion dropping from 100% to 72%. Source cited by paper: MindStudio 2026. The paper does not provide N, CI, model, task set details, or reproduction details in the provided text.

2. GitHub language-check example: about 1,365 tokens via `gh` versus about 44,026 via matching MCP server. Source cited by paper: Vensas 2026. No N/CI in text.

3. GitHub MCP registry overhead: 93 exposed tools add about 55,000 tokens at session start versus about 200 for `gh` equivalent. Source cited by paper: Reinhard 2026. No N/CI in text.

4. Prompt-cache illustrative calculation: stable prefix about 20K tokens, fresh work about 2K tokens, ten iterations:
   - no cache discipline: about 220K input tokens;
   - cached prefix at about 0.1x: about 60K effective input tokens.
   This is explicitly illustrative, not measured.

5. Cache pricing: cache-read/context-caching discounts are described as often close to one tenth of base input cost for Anthropic/OpenAI/Gemini entries, and substantially lower for DeepSeek cache-hit pricing. The paper warns provider pricing is model-specific and should be cited from current provider docs. I did not verify live vendor pricing because the task constrained me to local file tools.

Models used / frontier status:

1. AAC prototype/testing used Claude Code as the general-purpose agent. Exact model/backbone/version is not specified.

2. The paper references Claude Code, OpenCode, Cursor, Aider, Anthropic, OpenAI, Google Gemini, DeepSeek, LangChain/LangGraph, AutoGen, CrewAI, DSPy, etc., but does not provide a controlled model comparison.

**Limitations / failure modes / non-transfer**

1. Single-case origin. The core case is AAC, built by the methodology’s originators. The paper itself concedes this is the obvious reviewer objection.

2. Internal evidence. Build logs, issue tracker, and deployment records are primary sources, but the provided paper text does not expose raw logs, scenarios, transcripts, or reproducible benchmark artifacts.

3. No CIs, Ns, or controlled ablations for the key methodology claims. The seven-bug result is useful but not statistically characterized.

4. P5 is judge-agent dependent. A general-purpose agent driving scenarios can miss failures, overfit to rubric wording, or hallucinate evaluations unless grounded in transcript quotes and deterministic checks.

5. CLI composition leaks under durable workflow needs. The paper names cases where frameworks/workflow engines may be better: typed shared state, streaming partial results, durable suspend/resume, typed handoff schemas, unified observability, and recursion-depth budgets.

6. Resource isolation is not automatic. Subprocess isolation prevents some fault propagation, but shared CPU/RAM/file descriptors still need caps. Unbounded shell fan-out can kill the host.

7. “Framework-free” can become under-instrumented plumbing. If a team needs durable retries, idempotency, streaming, or graph observability, rebuilding them locally may create worse maintenance burden than using a framework.

8. CLI-over-MCP token claims are workload-sensitive. Large registry MCP setups look bad; small, well-scoped MCP tools can be reasonable. Conversely, noisy CLI stdout can exceed MCP cost.

9. Security posture claim is directional, not measured. The paper argues fewer dependencies reduce attack surface, but explicitly leaves matched dependency/CVE comparison to future work.

10. Liteshell pattern may not transfer where shell-like interaction is a poor user/model affordance, where strict typed APIs are essential, or where stateful interactive tools are better modeled by MCP/browser sessions.

11. “Agent-tests-agent every change” can become expensive or flaky unless backed by stable scenario suites, deterministic transcript capture, and acceptance thresholds.

12. OUR system already has many of these surfaces. Blind adoption risks renaming existing architecture instead of improving it.

**Integration into OUR system**

act-drain: applicable. Bolt-on: add a “policy maze / accretion” classifier that detects when repeated blindspot fixes only add rules/hooks without retiring or consolidating old ones. The paper’s useful input is not “add more methodology”; it is the P5 loop discipline: every new rule/hook should have a scenario failure it prevents and a trace proving it fired.

session-trace: strongly applicable. Bolt-on: make condensed MEMORY or improvement-log entries first-class links back to raw `agentlogs.db` spans. The primer says this link is not first-class. The paper’s P5 requires evidence quotes from transcripts/tool traces; session-trace is the exact substrate.

skills/rules/hooks: applicable, but with caution. Bolt-on: split flat skill/rule/hook lists into three explicit roles: steering content, deterministic enforcement, and scenario-test coverage. Add a convention that a prompt rule repeatedly violated graduates to a hook or host-code check. Do not add a new framework.

MEMORY: applicable. Bolt-on: append-only lessons should include `source_trace_id` / `session_trace` references where possible. The paper’s “documentation generation as side effect” maps to MEMORY only if examples retain provenance to raw traces.

`/eval`: strongly applicable. Bolt-on: create behavioral scenario suites for harness changes: over-ask, unsupported completion, stale-context claims, wrong-tool routing, and hook-routing failures. Evaluate the harness as a CLI-driven agent system, not just individual hooks. Include model/backbone labels and token cost.

predict-then-falsify: strongly applicable. Bolt-on: before accepting a new hook/rule/skill, preregister:
- predicted failure class,
- trace metric expected to move,
- mechanism expected to fire,
- rollback condition if it does not fire or causes accretion.
This is the paper’s P5 loop made falsifiable for OUR system.

Workflow: applicable. Bolt-on: treat file-bus just recipes as Turtle CLIs. Require `--help`, parseable output, trace IDs, session IDs where relevant, and depth/concurrency caps for recursive orchestration. This matches OUR existing single-writer-many-readers architecture.

ToolSearch: applicable. Bolt-on: treat deferred tools as the antidote to MCP-style registry bloat. The paper’s tool-registry-cost argument supports lazy loading by query. Concrete test: measure token/tool-call cost and task success for flat exposed tools versus ToolSearch-mediated deferred loading.

NOT-APPLICABLE: adopting the paper’s named multi-agent taxonomy. The “Ninja Turtles” roles are illustrative and culturally named; OUR system already has better exact surfaces: orchestrator model, scouts, Workflow/file-bus, `/debug`, `/orchestrate`, and just recipes. Pattern-extract CLI composition and depth budgets; do not import the taxonomy.

NOT-APPLICABLE: adopting a hosted runtime/server/DB. The primer explicitly rejects hosted runtime/server/DB stand-up. The paper’s strongest mechanisms fit local CLI/file-bus/session-trace surfaces already present.

Most useful concrete integration: build P5-style scenario evals over `session-trace` and `/eval`, wired to `predict-then-falsify`, with every accepted governance change linking back to a raw trace and a measured mechanism firing. This complements OUR current act-drain/blindspot loop by adding falsifiable behavioral regression tests and by countering the existing accretion failure mode.
