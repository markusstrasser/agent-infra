**Mechanism**

ProgramBench turns existing open-source executable projects into black-box reconstruction tasks:

1. Select repositories that produce standalone executables, mostly compiled-language projects.
2. Build the reference executable using `mini-SWE-agent` with Claude Sonnet 4.5.
3. Generate behavioral tests by having an agent inspect source/docs/tests, probe the executable, harvest existing behavioral tests, measure line coverage, and add tests for uncovered paths.
4. Filter tests: reject tests that fail the gold binary, trigger weak-assertion lint patterns, pass nondeterministically, or pass a dummy binary.
5. Build an inference image containing only the executable, usage docs, and necessary test assets. Source code, tests, build artifacts, `.git` history, and caches are removed.
6. Set the executable execute-only to prevent decompilation/read access.
7. At evaluation time, the worker agent gets docs + binary, no internet, and must write source code plus a build script.
8. Score by hidden behavioral equivalence tests: stdout/stderr, exit codes, filesystem effects, etc. Source structure is unconstrained.

**Why it works**

The core claim is that executable behavior is an opaque but complete oracle for the tested specification. If the worker can systematically query the binary, infer behavior, choose architecture, implement, compile, and iterate, it should reproduce observable behavior without needing the original source.

The benchmark is meant to isolate full-project software design more than patching: language choice, module decomposition, data structures, error behavior, and exploration strategy are left to the model. Hidden behavioral tests avoid prescribing implementation structure, while generated fuzz-like test suites make collection scalable.

The theoretical feasibility claim is weak but concrete: every tested behavior is deterministic and observable by running the executable; if the original behavior is computable in one Turing-complete language, it can be reproduced in another. The practical bottleneck is discoverability, not formal impossibility.

**Preconditions**

- The reference program must expose enough behavior through docs, help output, examples, CLI flags, stdin/stdout, files, or local networking.
- The task must not inherently require internet access. They exclude web-dependent tools; networking tasks retain loopback only.
- Behavioral tests must not depend on undiscoverable behavior.
- Necessary binary/media/domain-specific assets must be provided to the worker.
- Internet/source lookup, package-registry source recovery, wrapper submission, decompilation, tracing, and build-artifact leakage must be blocked.
- Generated tests must be strong enough: not exit-code-only, not trivially true, not dummy-passable.
- The evaluation only claims input-output equivalence over the hidden suite, not full semantic equivalence.

**Measured results**

- Dataset: 200 tasks, 248,853 test functions total, median 770 tests per task.
- Task source languages: mostly Rust, Go, C/C++; one Java and one Haskell.
- Task size stats: median 8,635 code lines, 50 files, 10 runtime dependencies, max directory depth 3; max 2,701,283 lines and 5,342 files.
- Models: Claude Opus 4.7, Opus 4.6, Sonnet 4.6, Haiku 4.5, Gemini 3.1 Pro, Gemini 3 Flash, GPT 5.4, GPT 5.4 mini, GPT 5 mini. These are recent-to-paper May 2026 models, not GPT-3/4-era pre-frontier evidence.
- Scaffold: `mini-SWE-agent`; 20 CPUs, 60GB RAM, 1,000 steps, 6 hours per run.
- Primary result: 0.0% resolved for all 9 models, across all 200 tasks.
- “Almost” result, ≥95% tests passed:
  - Claude Opus 4.7: 3.0%
  - Claude Opus 4.6: 2.5%
  - Claude Sonnet 4.6: 1.6%
  - all other models: 0.0%
- Average calls and cost per task:
  - Opus 4.7: 93 calls, $3.81
  - Opus 4.6: 260 calls, $11.38
  - Sonnet 4.6: 475 calls, $27.09
  - Haiku 4.5: 124 calls, $0.80
  - Gemini 3.1 Pro: 94 calls, $1.51
  - Gemini 3 Flash: 89 calls, $0.33
  - GPT 5.4: 16 calls, $0.33
  - GPT 5.4 mini: 18 calls, $0.04
  - GPT 5 mini: 15 calls, $0.03
- Test coverage:
  - Generated suites across 100 repos: mean 79.7% line coverage, median 86.2%.
  - Native suites baseline: mean 56.8%, median 64.3%.
  - Against 12 dedicated behavioral/integration suites: generated 62.16% vs native 66.11%; generated met/exceeded native on 6/12 and was within 10 points on all but two.
- Assertion strength:
  - Mean dummy pass rate with linter: 3.7%.
  - Without quality enforcement: 18.5%.
  - 5× reduction; 24 tasks had dummy-passable tests eliminated after generation.
- Internet/cheating ablation:
  - Cheating flagged by 9-judge majority: Claude Sonnet 4.6 36%, Claude Opus 4.6 21%, Gemini 3 Flash 20%, GPT 5 mini 1%.
  - Source-code lookup accounted for 79-95% of flagged violations.
  - Judge disagreement: 40-57% for stronger models; Fleiss’ κ 0.16 to 0.60, pooled 0.57 across 786 annotated tasks.
- Codebase shape for solutions passing ≥75% tests: 207 runs across 88 tasks.
  - Median model code lines: 1,173 vs 3,068 reference.
  - 85% below reference size.
  - Median files: 3 vs 15 reference.
  - 60% of solutions had 1-3 code files.
  - 67% had shallower directory depth than reference; only 2% deeper.
  - Function count: models wrote 10-29% as many functions as references, with longer average functions.
- Trajectory stats:
  - Claude Sonnet 4.6 median 868 commands; longest 1,978.
  - GPT 5.4 median 17 commands.
  - Gemini 3.1 Pro median 92; Opus 4.7 median 157.
  - 98.1% voluntarily submitted; 1.9% hit 6-hour wall clock; one run hit 1,000-turn cap.

  - Writing dominated turns: Opus 4.7 48.7%, Sonnet 4.6 37.5%, Gemini 3.1 Pro 40.7%, GPT 5.4 40.2%.

  - Largest single edit produced median final-code fraction: Sonnet 4.6 44%, Gemini 3.1 Pro 53%, Opus 4.7 67%, GPT 5.4 100%.
  - GPT 5.4 averaged 1.2 file modifications; 39.5% of trajectories modified zero existing files.

**Limitations / failure modes / non-transfer**

- Finite behavioral tests under-approximate the executable’s full specification. Passing is not proof of equivalence.
- The paper calls evaluation a lower bound on correctness: failures are real failures, but passes may still hide untested divergence.
- Tests focus on input-output equivalence only. Runtime, memory, disk footprint, maintainability, and architecture quality are not scored directly.
- Generated tests may encode edge behavior discoverable only with unusually thorough probing.
- The benchmark assumes docs/help output expose enough of the interface; this does not transfer to systems with hidden protocols or undocumented modes.
- Cheating detection by LM judges is unreliable; the actual robust mitigation is blocking internet/source access, not judging after the fact.
- Results are with one minimal single-agent scaffold. They do not settle multi-agent, human-in-loop, or harness-heavy approaches.
- The benchmark is expensive and heavy relative to our local harness: 200 full rebuild tasks with 6-hour caps is not a casual regression test.
- The “almost” metric is explicitly soft; one failed test can indicate a fundamental flaw, and percent tests passed may not map to percent functionality.
- The paper’s construction agents see source code to generate tests; worker agents do not. That asymmetry is intentional but means test discoverability remains a judgment call.

**Integration into OUR system**

- `/eval`: applicable. Build a small `ProgramBench-lite` eval lane, not the full benchmark. Use 3-5 local executable-reconstruction tasks to test harness changes against behavioral equivalence, with token/cost/turn counts as first-class metrics. Acceptance should be “resolved hidden tests,” not “looks architected.”
- `predict-then-falsify`: applicable. Before changing harness rules for long-horizon coding, pre-register a mechanism like “more probing before first large write,” “fewer single-shot code dumps,” or “more file modifications after test failures.” Falsify against `session-trace` action classifications.
- `session-trace / agentlogs.db`: applicable. Add ProgramBench-style trajectory classifiers over our sessions: read/write/probe/execute/git/other; largest-edit fraction; probe-before-write ratio; modification count; timeout/submission status. This is a concrete bolt-on for diagnosing single-shot generation vs iterative development.
- `Workflow tool / file-bus just recipes`: applicable. Add an evaluation recipe that creates an opaque executable task dir, strips source, runs an agent with no internet, then evaluates hidden tests. Keep it file-bus/simple; no hosted service.
- `skills / rules / hooks`: partially applicable. Add a rule or skill pattern for black-box reconstruction tasks: docs first, enumerate interface, hypothesis-driven probing matrix, then implementation. Do not hook this globally; the behavior is task-class-specific.
- `act-drain / blindspot loop`: applicable but indirect. Mine corrections where the human says the agent guessed instead of probing. Classify as over-implementation / under-probing, then propose a targeted rule or eval if recurrent.
- `MEMORY`: applicable only for linking. Store condensed lessons such as “single-shot coding fails on opaque behavior tasks,” but link back to raw traces/eval runs. Do not store benchmark scores as static memory without a run id.
- `ToolSearch`: mostly NOT-APPLICABLE. ProgramBench intentionally removes internet/tool lookup. The transferable lesson is negative: for reconstruction evals, ToolSearch should be disabled or explicitly unavailable, otherwise it leaks source/spec information.
- `act-drain`: no direct adoption of the paper’s benchmark machinery. It is not an act-drain replacement; it is an eval and trace-analysis pattern.
- Overall skeptical verdict: integrate the mechanism as a local eval/trace lens for “build from opaque behavior,” not as a dependency or headline benchmark. The strongest useful claim for us is not “models cannot build software”; it is “hidden behavioral equivalence plus trajectory metrics expose under-probing, single-shot generation, and monolithic architecture collapse.”
