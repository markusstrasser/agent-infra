**Mechanism**

1. Define a benchmark target: “Generalist Computer-Use Agents” that can combine LLM reasoning, GUI perception, orchestration, tool calls, shell/file/runtime access, and long-horizon context management.

2. Build an industry/task taxonomy from SOC 2018 and O*NET, excluding non-digital physical work and clustering software-mediated occupations into **13 domains** and **55 subdomains**.

3. Source tasks from practitioners rather than synthetic benchmark authors. Experts submit past projects that took days or weeks, including the task description, input files, target software, expected deliverable, and evaluation specification.

4. Pass tasks through staged gates: expert sourcing, submission/editing, first-pass review, engineering implementation, dry-runs, and final expert committee QC.

5. Convert accepted tasks into executable benchmark instances. Each task has a `main.py`-style lifecycle:
   `load()` declares description and compute requirements; `start()` provisions a deterministic VM; `evaluate()` scores output artifacts against hidden references/rubrics.

6. Run agents in a remote VM with a fixed directory contract:
   `input/` read-only assets, `software/` installed applications, `output/` writable target, `reference/` hidden ground truth.

7. Extend CLI-native agents with GUI capability through **GUI-as-Tool**: a CUA MCP bridge exposes desktop actions as ordinary tools so one model reasons over shell output and screenshots in the same loop. GUI-as-SubAgent is reserved for models without native vision.

8. Score heterogeneous deliverables via task-specific automated evaluators: exact/hash checks, numeric/tabular tolerances, geometry distances, visual yes/no probes, behavioral state under fixed trajectories, free-text rubrics, and gate-and-score compositions.

9. Keep most tasks private to reduce contamination: **150 public**, **1,017 private**, **323 unverified pending QC**, total **1,490** instances.

**Why it works**

The causal claim is: benchmark pressure only transfers to economic deployment when the benchmark measures the real workflow, not proxy QA or toy interaction. ALE tries to close the “benchmark success vs GDP impact” gap by combining three properties that existing evaluations usually trade off:

Representativeness: tasks come from real professional work and real software.

Complexity: tasks are end-to-end deliverables, not isolated UI actions.

Verifiability: outputs are scored by deterministic or narrow rubric-based artifact checks rather than broad human judgment or open-ended LLM judging.

The paper’s theory is that once economically valuable workflows are captured by a broad, verifiable, repeatable benchmark, optimization pressure can target the missing capabilities directly: domain knowledge, tool choice, GUI/CLI integration, and long-horizon execution.

**Preconditions**

The task must be digital or software-mediated enough to run in a VM/container.

The workflow must produce an observable artifact: file, spreadsheet, report, model, toolpath, scene, game state, screenshot, etc.

The artifact must admit deterministic checking or a narrow, evidence-anchored rubric. If the only path is “ask a model if it looks good,” the task is rejected or re-engineered.

The task must be representative of professional practice, including domain software where appropriate.

Expert contributors and reviewers must be available to provide references, evaluation criteria, and QC.

Agents need access to both CLI and GUI surfaces for the full benchmark. CLI-only agents are restricted to ALE-CLI.

The benchmark’s private pool must stay uncontaminated. The paper’s rolling-release strategy depends on private tasks not leaking into training or public optimization.

**Limitations / failure modes / non-transfer**

The benchmark is expensive: one frontier-agent task costs **$3-10** on average and takes tens of minutes to hours.

The private/public split is essential but creates reproducibility limits. Public leaderboard work sees only a small slice of the task pool.

The paper’s table extraction has count inconsistencies: public set count, tier counts, and ALE-CLI tier counts do not cleanly reconcile in the text we have.

Automated evaluation is only as good as task-specific evaluator design. Gate-and-score can zero out useful partial work if gates are too brittle.

LLM-as-judge is minimized but not eliminated. Visual/rendered outputs still use narrow model probes in some cases.

The benchmark measures task completion in controlled VMs, not organizational deployment: no human stakeholder negotiation, ambiguous requirements, production access controls, or ongoing maintenance burden.

The task pool is broad but not necessarily weighted by economic value, frequency, or marginal deployability.

The main bottleneck found is often domain understanding/approach, not just harness mechanics. Therefore “add GUI tools” does not transfer by itself.

Do not import the headline ALE numbers into OUR evals as expected local rates. Their tasks, agents, budgets, and model set are different; the useful transfer is the benchmark architecture and failure taxonomy.

**Integration into OUR system**

/eval: concrete bolt-on. Add an **ALE-shaped task-spec protocol** for our harness evals: each eval case should have `load/start/evaluate` equivalents, hidden references, explicit writable output paths, and evaluator mode tags. This is directly applicable because OUR system already treats harness-on-frozen-model as the lever.

predict-then-falsify: concrete bolt-on. Before accepting a harness edit, require a pre-registered mechanism label matching ALE’s failure families: Understanding, Approach, Execution, GUI, Format, Implementation Bug, Hallucination, Incomplete. Accept only if session traces show the intended failure mode moved, not merely aggregate score noise.

session-trace / agentlogs.db: concrete bolt-on. Add trace-derived fields for ALE-like analysis: tool-call mix by taxonomy (`bash`, `file`, `GUI`, `web`, `planning/subagent`), timeout, full-pass, partial score, gate failed, and root-cause label. This maps cleanly to our transcript forensics.

act-drain / blindspot loop: concrete bolt-on. Use ALE’s failure taxonomy as a candidate schema for correction mining, but do not replace our existing supervision taxonomy wholesale. The direct use is to distinguish “agent asked too much” from “agent chose wrong workflow/software” and “agent lacked domain knowledge.”

skills/rules/hooks: concrete bolt-on. Add a rule/hook pattern for eval tasks: every task with heterogeneous output must declare evaluator mode and gate semantics before consumers are written. This mirrors ALE’s “validate scoring shape before benchmark use” lesson.

MEMORY: concrete bolt-on. Store condensed eval lessons with first-class links back to raw session-trace rows and evaluator artifacts. ALE’s contamination/private-pool logic reinforces our existing gap: MEMORY currently condenses lessons, but the condensed-to-raw link is not first-class.

Workflow: concrete bolt-on. Build a file-bus workflow for eval runs with explicit phases: materialize task, run agent, collect output, evaluate, classify failure, write trace summary. ALE’s decoupled task/agent/environment design is a good mechanism for our single-writer-many-readers recipes.

ToolSearch: partial / skeptical bolt-on. ALE argues for large tool surfaces loaded into the agent loop only when needed. For OUR deferred tools, the transfer is not “give agents 14 GUI tools”; it is “log whether ToolSearch exposed the right tool and whether the agent used it.” Add ToolSearch hit/use/miss fields to eval traces.
