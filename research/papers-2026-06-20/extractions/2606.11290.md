**Mechanism**

FlowBank treats workflows as a reusable portfolio, not as a single best artifact.

Step by step:

1. Define each agentic workflow `ω` as a computation graph of LLM calls. For each query `q`, record both task performance `e(ω, q)` and token cost `c(ω, q)`.

2. Build a raw workflow pool with **DiverseFlow**, an MCTS-based workflow search procedure.
   First, it runs a performance warm-up for `N0` rounds, sampling parent workflows by aggregate training performance.

3. After warm-up, DiverseFlow switches to complementarity-oriented expansion.
   It upweights training queries that the current pool does not solve well. Query weight is inversely related to current pool coverage: if no workflow solves `q`, its weight is maximal. Parent workflows are then scored by weighted performance on under-covered queries.

4. Each MCTS round samples a parent workflow, asks an optimizer LLM to propose a new workflow in code space, executes it on `Dtrain`, records per-query effect and token cost, and stores success/failure feedback.

5. The final raw pool `Ωraw` is augmented with a ScoreFlow-style dynamic workflow candidate, represented by its query-wise outputs and costs.

6. Curate the raw pool with **CuraFlow**.
   For each subset size `k`, enumerate workflow subsets and select the one maximizing set coverage:
   `Coverage(Ω) = average over queries of max workflow performance on that query`.

7. Choose the smallest `k` whose best subset reaches saturation threshold `τ * Coverage(Ωraw)`. In experiments, `τ = 0.96`; raw pool size is `31` (`30` DiverseFlow rounds + `1` ScoreFlow candidate). They also pass `k - 1` as an alternative portfolio size.

8. Train a query-adaptive matcher.
   Build a bipartite graph between training queries and curated workflows. Query nodes use query-text embeddings; workflow nodes use embeddings of GPT-4o-generated workflow descriptions.

9. Define edge supervision as a utility mixing normalized performance and normalized cost:
   `v(q,ω) = (1 - λ) * normalized_effect + λ * (1 - normalized_cost)`.

10. Train a heterogeneous 2-layer GNN encoder plus MLP decoder to predict masked edge values.

11. At inference, embed the new query, connect it to every workflow in the portfolio, run one GNN forward pass, select the workflow with highest predicted utility, and execute only that workflow. Ties break toward lower-cost workflows.

**Why it works**

The causal claim is portfolio complementarity.

The paper argues that workflow search produces many workflows that are not globally best but solve different subsets of queries. A single deployed workflow throws away that set-level value. Query-level workflow generation recovers adaptivity but spends online tokens designing a fresh workflow per query. FlowBank’s claim is that much of this adaptivity can be moved offline: discover diverse workflows once, curate away redundancy, then learn a cheap query-to-workflow router.

The theoretical support is the coverage objective. Coverage is a monotone submodular set function when per-query performance is nonnegative, so marginal gains diminish as more workflows are added. This justifies compact curation and gives the greedy variant a `(1 - 1/e)` approximation guarantee for fixed budget `k`. The GNN selector is justified as a pairwise edge-value predictor rather than a flat classifier, so it can represent multiple workflows as equally good for a query and use query-workflow relational structure.

**Preconditions**

The mechanism needs:

- A workflow space where different workflows genuinely have complementary per-query strengths.
- A representative training split with enough queries to estimate per-query workflow performance and cost.
- Cheap enough offline execution to run every candidate workflow over `Dtrain`.
- Stable task evaluators that produce per-query scores, not just aggregate leaderboard numbers.
- Workflow candidates that can be serialized/described enough for a router to compare them.
- A deployment setting where workflow choice is repeated often enough that offline search/curation amortizes.
- A task distribution close enough to training that the learned selector’s query embeddings and workflow descriptions transfer.
- A cost model where token cost is a meaningful proxy for deployment cost.
- For their exact method: embeddings, GPT-4o-generated workflow descriptions, and a small GNN training loop. This is already more machinery than a local harness should adopt blindly.

**Limitations / failure modes / non-transfer**

The paper references Appendix F for limitations, but Appendix F is not present in the provided text. So the limitations below are inferred from the method and reported setup, not copied from an appendix.

- Selector training may overfit small training splits. MATH has only `119` training examples, MBPP `86`; that is thin supervision for query-workflow routing.

- No CIs or seed variance are reported. The gains could be sensitive to random seeds, workflow-search stochasticity, training/test split, or optimizer model behavior.

- The task universe is benchmark-style QA/math/code/reading. Transfer to messy local agent operations is not established.

- The measured executor is GPT-4o mini, not current frontier. Workflow complementarity may shrink or change with stronger single agents.

- FlowBank depends on a reliable per-query evaluator. Many of OUR session-quality outcomes are delayed, partial, semantic, or human-labeled; that weakens the training signal.

- The method uses online embeddings plus GNN routing. For OUR system, that is probably too much machinery as a first move unless `/eval` shows a simple router fails.

- Workflow descriptions are generated by GPT-4o. If descriptions are incomplete or misleading, the graph selector learns against a proxy for workflow behavior rather than the behavior itself.

- The raw candidate pool is only 31 workflows and portfolio saturation is at `k ≤ 6` in their setting. Larger, messier tool/skill surfaces may not remain exhaustively curatable.

- The oracle results show large unrealized headroom, but oracle uses test labels. The real question is whether the learned selector closes enough of that gap. Their ablation shows redundancy can produce high oracle but lower actual performance.

- Cost is token-cost-centric. OUR harness cares about supervision cost, interruption cost, false confidence, hook noise, and maintenance burden, not just tokens.

**Integration into OUR system**

Best integration: **/eval + predict-then-falsify gate**.

Concrete bolt-on: create a FlowBank-inspired evaluation for reusable harness workflows, but start with a simple portfolio/router, not their full GNN. Use `agentlogs.db` / `session-trace` to assemble historical query/task cases, label each case by which existing workflow surface would have handled it best, and pre-register the expected mechanism: “router selects a lower-supervision workflow without raising correction rate.” Accept only if trace replay shows the selected workflow changed on the intended cases and reduced over-ask or correction burden. This maps directly to OUR planned predict-then-falsify gate.

Second integration: **Workflow tool / file-bus just recipes**.

Concrete bolt-on: treat existing recipes such as `operator-status-briefing`, `adversarial-debug-scout`, `debug-until-dry`, `verification-gate-runner`, and commit-slice planning as reusable portfolio members. Add a lightweight selector layer that chooses among already-existing recipes for a session/request class. Do not generate new workflows per query. The paper’s actionable mechanism is “precompute-and-reuse,” not hosted multi-agent orchestration.

Third integration: **ToolSearch**.

Concrete bolt-on: maintain a small curated portfolio of deferred tool bundles by task class, then route by query features and historical outcomes. Example: paper extraction should load paper/corpus/research tools; GitHub PR work should load GitHub skills/tools; library docs should load context7. This is almost exactly FlowBank’s matching stage, but OUR version can begin as logged deterministic routing plus eval replay before any learned selector.

Fourth integration: **skills / rules / hooks**.

Concrete bolt-on: use FlowBank’s coverage objective to prune flat skill/rule/hook lists. Instead of “keep every rule that ever helped,” compute which rules/hooks cover distinct failure classes in agentlogs. Use curation to find the smallest set that preserves, say, 96% of observed correction coverage. This directly attacks the primer’s known accretion / policy-maze failure mode.

Fifth integration: **act-drain / blindspot loop**.

Concrete bolt-on: when act-drain proposes new rules/hooks, require it to state whether the proposed item adds marginal coverage over the existing portfolio. If it only duplicates an existing guard, retire or merge instead of accreting. This is a high-value paper transfer: use set coverage, not individual plausibility.

Sixth integration: **session-trace / agentlogs.db**.

Concrete bolt-on: add per-session replay features needed for portfolio evaluation: task type, selected workflow/skill/tool bundle, human correction class, over-ask events, hook triggers, token/time cost, and outcome. The paper’s whole method depends on a query-workflow matrix; session-trace is the right place to derive OUR version of that matrix.

Seventh integration: **MEMORY**.

Concrete bolt-on: use the paper’s “bank of reusable assets” idea only for linking condensed lessons to raw evidence. MEMORY should not become a workflow selector. The useful transfer is first-class links from condensed memory entries to the raw agentlogs/session-trace examples that justified them, so curation can later measure whether a memory item adds distinct coverage.

Eighth integration: **act-drain / over_caution=63 / over-ask**.

Concrete bolt-on: train or rule-fit a selector for “act vs ask vs defer” from historical corrections. This is the closest local analog to query-adaptive matching. But keep it behind `/eval`: the failure mode is confidently acting across taste/irreversible boundaries.

Not applicable: adopting FlowBank as a framework dependency.

Why: the primer explicitly rejects hosted runtime / server / DB stand-up and prefers pattern extraction. The paper’s full stack includes workflow code generation, exhaustive candidate execution, GPT-4o workflow descriptions, embeddings, GNN training, and GPU sweeps. OUR system should extract the mechanism: complementary reusable portfolio + coverage-aware curation + query-adaptive routing, validated by trace replay.
