**Mechanism**

1. Model the harness as bounded context/infrastructure `C = φ(Ht)` built from prior task history `Ht`, where history contains prior tasks, rewards, and trajectories.
2. Split harness failure into two losses:
   - evolution loss: the evolver cannot construct the right capabilities from history.
   - adaptation loss: one committed dense harness is wrong for heterogeneous incoming tasks.
3. Replace single-agent harness mutation with a persistent four-phase evolver:
   - `Analyze`: inspect recent failures and maintain a task board.
   - `Research`: parallel agents test hypotheses and record research logs.
   - `Build`: implement prompt/skill/tool/memory changes.
   - `Verify`: gate the changes with tests before they enter the solver workspace.
4. Use temporal-reveal feedback: labels/outcomes are hidden until their real resolution time, so evolution gets streaming feedback without future leakage.
5. Persist cross-cycle state: task board, research logs, verifier notes, tests, README/architecture notes.
6. Organize solver harnesses as a tree of git branches, each branch carrying regime-specific prompt/skills/tools.
7. At solve time, use a router agent to inspect branch metadata and route the task to a branch; the solver checks out that branch and runs.
8. Add HITL hooks only when history lacks signal:
   - task-board steering after analysis.
   - research-phase assistance when credentials/access/source knowledge blocks research.

**Why it works**

The causal claim is that open-ended streams break a single dense harness for three reasons: history grows past context limits, tasks are heterogeneous, and distributions shift. The paper formalizes this as regret against an oracle bounded harness and decomposes expected regret into `Levo + Ladapt`.

- Multi-agent evolution should reduce `Levo` because specialized agents with persistent state can construct capabilities a single prompt editor cannot.
- Harness-tree routing should reduce `Ladapt` because per-task branch selection avoids loading irrelevant or conflicting skills into every solve.
- HITL should help only when required signal is absent from trajectories, e.g. credentials, source access, novel endpoints.

This is plausible for our system because our surfaces are currently flat and accretive: skills/rules/hooks/MEMORY grow, but solve-time selection and condensed-to-raw provenance are not first-class.

**Preconditions**

- Tasks arrive chronologically, with enough repeated structure for historical failures to inform future harness changes.
- There is reliable feedback, or at least delayed labels, that can be revealed without leakage.
- Task heterogeneity clusters into regimes where specialized harnesses outperform one shared harness.
- The evolver can mutate real harness artifacts, not just prose.
- Verification exists for built changes; otherwise the multi-agent loop just automates drift.
- Routing metadata must be good enough for task-to-branch selection.
- For HITL, human input must be source/access guidance, not answer leakage.
- The system must tolerate extra solver cost and branch/workspace complexity.

**Limitations / failure modes / non-transfer**

- `Levo` and `Ladapt` are analytical quantities, not directly estimated oracle losses.
- Results cover only three task streams; not shown for normal software maintenance, code-review harnesses, local single-operator workflows, or non-benchmark agent ops.
- Evolver-side token cost is missing, so total optimization cost is underreported.
- Routing is only partly solved: FutureX Adapt underperforms Naive by `-5.2`, showing branch selection can hurt when the binding bottleneck is source acquisition rather than task category.
- Harness branches add governance complexity. Without strong branch retirement and drift checks, this can become a policy maze with git branches instead of flat rules.
- HITL can leak answers unless constrained to source/access guidance. The paper claims this guard, but the mechanism depends on audit discipline.
- The paper’s strongest numbers come from benchmark-specific evolution and replay analyses; do not generalize them to our live harness without a predict-then-falsify evaluation.
- Model names and baselines are paper-internal claims here; I did not verify vendor availability or parity externally.

**Integration into OUR system**

- `skills/rules/hooks`: concrete bolt-on: add a branch/regime metadata layer over flat skills/rules/hooks. Not a full git-branch solver checkout; lighter first step is a machine-readable `When to route here` block per skill/rule bundle plus a router that selects a bounded subset before solve/review.
- `ToolSearch`: concrete bolt-on: extend deferred tool loading from query-only search to regime-aware retrieval. The router should select tool families by task class and load only relevant tools, reducing flat surface accretion.
- `MEMORY`: concrete bolt-on: make condensed memory entries link back to exact `session-trace` spans. Paper’s cross-cycle workspace maps directly to our missing condensed-to-raw link.
- `session-trace`: concrete bolt-on: add replayable branch-selection traces: task, candidate regimes, selected regime, loaded skills/rules/tools, outcome. This is necessary to falsify whether routing helped or merely added overhead.
- `act-drain`: concrete bolt-on: classify blindspot findings into `Levo` vs `Ladapt` vs `HITL-needed`. Example: missing tool/source capability = `Levo`; wrong rule loaded for task = `Ladapt`; credential/source access = `HITL-needed`.
- `/eval`: concrete bolt-on: create an eval slice for flat-all-context vs routed-subset harness on historical agentlogs tasks. Primary metric should include correctness plus token/tool-call cost, because our primer treats token cost as first-class.
- `predict-then-falsify`: concrete bolt-on: before adding a routed harness layer, pre-register: “for task class X, routing will reduce irrelevant rule/tool loads by Y and improve or preserve verified outcome rate.” Accept only if `session-trace` shows the intended loaded-surface reduction and no outcome regression.
- `Workflow`: concrete bolt-on: mirror the paper’s four phases only where we already have workflow/file-bus structure: Analyze from act-drain/session-trace, Research as scout outputs, Build as scoped patch, Verify as harness-eval. Do not import their full framework.
- `act-drain / blindspot loop`: concrete bolt-on: add retirement pressure. The paper motivates specialization, but our measured failure is accretion; every new routed branch or regime bundle needs decay/merge/delete criteria.
- NOT-APPLICABLE: hosted runtime/server/DB adoption. The primer explicitly rejects framework dependencies and hosted stand-up; pattern-extract only.
- Skeptical recommended integration: start with `session-trace + /eval + ToolSearch` routing measurement, not git-branch harness trees. The deepest useful representation for us is probably “task-regime -> loaded surfaces -> trace outcome,” because it is inspectable and falsifiable without multiplying solver workspaces.
