**IDs**

- arXiv: `2606.14302v1`, dated `12 Jun 2026`.
- Actual title from text: `Retrospective Progress-Aware Self-Refinement for LLM Agent Training`.
- Mismatch: none between file id and text. Note: the method name is `RePro`, but the title says `Self-Refinement`; the abstract/body call the framework `Retrospective Progress-Aware Training`.

**Mechanism**

1. During task execution, the agent produces an online progress estimate `p̃t` plus the next action `at` from history `ht`.
2. The environment runs the action until a terminal outcome/reward is known.
3. After completion, the agent replays the full trajectory plus final outcome and retrospectively assigns per-step progress values `p1...pT`.
4. The original trajectory is rewritten with retrospective progress estimates replacing noisy online estimates.
5. Phase 1, `Retrospection Warmup`: successful trajectories are labeled by external `DeepSeek-V4` at temperature 0, then the target model is SFT-trained to emit actions and retrospective progress.
6. Phase 2, `RePro-PO`: RL uses a composite reward:
   - sparse environment reward,
   - progress shaping from `pt+1 - pt`,
   - online-retrospective alignment from closeness between `p̃t` and `pt`,
   - format/boundary penalties.
7. Optimization uses hierarchical advantages: episode-level normalized return plus step-level advantage among repeated anchor observations, then PPO-style clipped objective.

**Why it works**

The causal claim is that long-horizon agents need a task-progress state, not just local action optimization. Online self-assessment is noisy and disrupts action choice, but hindsight progress is anchored by known outcome and trajectory length, making it a better supervisory signal. Training on retrospective progress supposedly internalizes a progress estimator that improves credit assignment under sparse terminal rewards and helps the policy allocate effort across the episode.

The paper’s key asymmetry supports this: prompting agents to assess progress online hurts, while retrospective demonstrations help. The plausible mechanism is not “more reflection text is good”; random progress and naive progress rewards underperform, so the claim is specifically about outcome-grounded retrospective labels.

**Preconditions**

- Tasks must be episodic, long-horizon, and have a final outcome/reward.
- Full trajectories must be logged with actions, observations, and terminal outcome.
- There must be enough completed trajectories to label or self-label.
- Progress must be meaningfully monotonic or at least outcome-correlated; Sokoban gains are smaller where process rewards already exist.
- A stable progress-output format must be extractable.
- Warmup appears important for smaller models; without warmup, 1.5B/3B variants are `NA` in ablation.
- The training setup assumes parameter updates; inference-only systems get only the pattern, not the claimed model gains.
- External labeling uses `DeepSeek-V4`; the result depends on label quality.

**Measured results**

Pilot study on WebShop:
- Models: `DeepSeek-V4`, `GPT-5.1`.
- Baseline success: DS-v4 `35.9%`; GPT-5.1 `44.1%`.
- Online progress prompting: DS-v4 `33.6%`; GPT-5.1 `29.3%`; average `-8.6%`.
- Random progress: DS-v4 `31.2%`; GPT-5.1 `32.4%`.
- Retrospective demonstrations: DS-v4 `44.1%` (`+8.2`); GPT-5.1 `51.6%` (`+7.5`); average `+7.9%`.
- Random demonstrations: DS-v4 `37.9%` (`+2.0`); GPT-5.1 `48.4%` (`+4.3`).
- Demo source: completed trajectories from a `100-sample` training set; `3` demos sampled at test time.

Main trained evaluations:
- Benchmarks: WebShop, ALFWorld, Sokoban.
- Test size: `256` test samples.
- Metrics: success rate and environment score.
- Models: `Qwen2.5-1.5B`, `Qwen2.5-3B`, `Qwen2.5-7B`, `Qwen3-4B`. These are not frontier models; transfer to frontier agents is unproven.
- No confidence intervals reported. No statistical significance tests reported.

WebShop, RePro average vs Meta Prompt baseline:
- Qwen2.5-1.5B: SR `76.13`, `+8.98`; score `87.56`, `+2.29`.
- Qwen2.5-3B: SR `79.73`, `+11.57`; score `90.75`, `+6.37`.
- Qwen2.5-7B: SR `80.47`, `+5.82`; score `89.13`, `+4.04`.
- Best WebShop RePro: `81.64`, `83.59`, `84.38` SR across 1.5B/3B/7B.

ALFWorld / Sokoban, RePro average vs Meta Prompt:
- ALFWorld Qwen2.5-1.5B: SR `96.02`, `+17.54`; score `7.94`, `+3.47`.
- ALFWorld Qwen2.5-7B: SR `97.54`, `+6.17`; score `8.90`, `+2.41`.
- Sokoban Qwen3-4B: SR `81.64`, `+7.58`; score `5.10`, `+1.18`.
- Best gains cited in prose: ALFWorld `+11.72` SR for 1.5B, `+4.69` SR for 7B, Sokoban `+3.12` SR for Qwen3-4B.

Ablations, WebShop best:
- RePro best: 1.5B `81.25`, 3B `83.98`, 7B `84.77`.
- Warmup Only: 1.5B `0.00`, 3B `28.52`, 7B `61.72`; much worse despite format accuracy.
- Warmup + GiGPO: 1.5B `75.00`, 3B `78.91`, 7B `79.69`.
- Without warmup: 1.5B/3B `NA`; 7B `80.08`.
- Variants `L1+Reshaping`, `L1+Reweighting`, `L1+Grouping` all trail RePro.

Progress metrics:
- Primary metric: Intermediate Discrimination, mean final progress gap between successful and failed trajectories.
- Baseline IntermDisc: `1.86` for 1.5B, `1.11`/`-1.07` shown across table columns, weak or negative.
- RePro IntermDisc: `6.37` for 1.5B, `31.62` for 3B, `11.14` for 7B.
- Format extraction is near-perfect: RePro `100.00` for success/failure across sizes.

Training details:
- SFT: learning rate `5e-6`, batch size `8`, `3` epochs.
- RL: `8` trajectories per batch, WebShop horizon `15`, PPO clip `0.2`, gamma `0.95`, KL coefficient `0.01`, learning rate `1e-6`, `150` iterations.
- Framework: `veRL`; paper says training on `PPU`.

**Limitations / failure modes / non-transfer**

- No confidence intervals, no seeds disclosed in the extracted text, and no significance testing.
- Benchmarks are limited: WebShop, ALFWorld, Sokoban. No GUI automation, open-ended coding, real tool ecosystems, or multi-day local agent harnesses.
- Uses verbalized numeric progress. Latent or structured state representations are unexplored.
- No objective ground-truth progress labels; progress quality is evaluated indirectly.
- External `DeepSeek-V4` labels are a dependency in warmup, even if continuous external supervision is avoided later.
- Inference-only prompting can hurt badly; adopting “ask the agent for progress every step” is contraindicated.
- Gains on Sokoban are smaller, suggesting lower value when process rewards already exist.
- The trained models are small Qwen-family agents, not frontier Claude/Codex/GPT agents. Treat rates as pre-frontier/non-frontier evidence; the method may transfer, the measured gains do not.
- The paper’s system trains policies. OUR system is a single-operator local harness with subscription dispatch; we should pattern-extract, not adopt `veRL` or the framework as a dependency.

**Integration into OUR system**

- `session-trace / agentlogs.db`: applicable. Add derived retrospective progress annotations over raw sessions: per turn `online_progress_if_present`, `retrospective_progress`, `terminal_outcome`, `progress_delta`, and link to transcript span. Do not require agents to emit online progress during live work by default; the paper shows that can hurt.

- `act-drain / blindspot loop`: applicable. For each correction episode, compute a retrospective “where did the session go off-track?” progress curve from raw transcript plus final human correction. Use it to classify whether the failure was early misframing, mid-run drift, or late false completion. This attacks the known accretion/over-ask issue by grounding rule proposals in trajectory shape rather than adding another flat rule.

- `predict-then-falsify gate`: high-fit bolt-on. Before a harness edit, require a predicted mechanism trace: “this change should reduce over-ask by causing action at step class X.” After sessions, retrospectively label whether the intended mechanism fired. Accept only if final outcome and retrospective trace agree; revert if the metric moved for the wrong reason.

- `MEMORY`: applicable but only as links, not prose inflation. Store condensed lesson plus first-class raw-trace pointer and retrospective failure/progress segment. This directly addresses the primer’s “condensed→raw link is not first-class” gap.

- `skills / rules / hooks`: applicable with caution. Do not add a generic “report progress every step” rule. Instead add a post-hoc hook or analysis script that extracts progress/failure phase from completed transcripts. If a skill has repeated stall points, encode the retrospective phase markers into the skill procedure.

- `/eval + ~/Projects/evals`: applicable. Build an eval for harness edits where the scored unit is not just final task success but trajectory-progress discrimination: can the harness distinguish successful vs failed sessions before the final correction? Track token cost as a first-class axis.

- `Workflow tool / file-bus just recipes`: applicable. Add optional retrospective checkpointing to loop recipes: after a completed run, write a progress/failure curve artifact beside the journal, then feed it to act-drain. Keep single-writer-many-readers.

- `ToolSearch`: partial. Use retrospective traces to learn which tool surfaces were needed at which task phase, then improve lazy tool query routing. Do not make ToolSearch ask for progress online unless an eval shows benefit.

- Hosted runtime / training framework adoption: NOT-APPLICABLE. The concrete `RePro-PO` training stack requires model fine-tuning and RL infrastructure. OUR system should not stand up `veRL`/PPU or adopt the framework as a dependency. The useful mechanism is retrospective, outcome-grounded trajectory labeling plus eval-gated harness changes.
