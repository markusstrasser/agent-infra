**Mechanism**

Meta-Team is an experience-driven evolution loop for a multi-agent system.

1. Define the MAS as agents plus orchestration: `M = (A, O)`, where each agent has a scaffold, and orchestration is split into inter-agent protocol `P` and shared team scaffold `S`.

2. Run a task and record an experience `e = (x, τ, r)`: task input, interleaved multi-agent trajectory, and result/evaluator score.

3. Preserve each agent’s local trace `τ_i` instead of flattening the whole trajectory into one analyzer context.

4. After task completion, each agent reflects on its own execution chain and receives the final result.

5. Agents exchange post-task summaries/evidence: how their own outputs affected others, where handoffs failed, what downstream agents depended on, and which local observations contradict a global diagnosis.

6. Apply three evolution scopes:
   - L1 agent-level: update individual agent behavior/scaffold, including what to observe, verify, report, or avoid.
   - L2 interaction-level: update teammate profiles and pairwise collaboration notes, not just a binary communication graph.
   - L3 team-level: update roster, organization, shared constitution, coordination rules, and shared team scaffold.

7. Commit validated updates into reusable scaffold artifacts: agent patches, teammate profiles, collaboration notes, and shared constitution changes.

8. Implementation details: open-roster orchestration with candidate agent pool, active subset selected per task, append-only message bus, primitives like `LIST_POOL`, `STARTAGENT`, `STOPAGENT`, `FINALIZE`, `TERMINATE`, editable agent dirs with `prompt.md` and `config.yaml`, evolving files under `evolution/`, and progressive-disclosure skills under `skills/<name>/SKILL.md`.

9. Before committing updates, Meta-Team checks role consistency, tool availability, formatting validity, and budget constraints. Retries are allowed only if budget remains and retry cost is counted.

**Why it works**

The causal claim is architectural: MAS execution distributes context and responsibility across agents, but prior evolution methods often collapse the distributed trace into one centralized analyzer. That reintroduces the single-context bottleneck MAS were meant to avoid.

The paper’s claim is that collaborative evolution works because it preserves local fidelity while recovering cross-agent awareness. Local-only reflection has high-fidelity local traces but cannot see how decisions affected the team. Global-only analysis sees everything but suffers on long, interleaved traces even when the context window is technically large enough. Collaborative analysis lets each agent keep its own trace, exchange targeted evidence, and trace dependencies across handoffs.

The theoretical support is mostly cognitive-load/context-bottleneck reasoning plus organizational “team reflexivity”: teams improve by jointly inspecting behavior, coordination, and organization rather than being diagnosed entirely from outside.

**Preconditions**

Meta-Team needs:

- A multi-agent system with separable local traces, messages, handoffs, and shared artifacts.
- Full event logging: LLM calls, tool calls, messages, inter-agent communication, and task outcomes.
- A task evaluator or at least a final outcome signal. The method relies on post-task feedback.
- Editable scaffolds: prompts, behavioral patches, skills, teammate profiles, coordination rules, roster, or constitution.
- Repeated/evolution tasks from the same or related distribution, with held-out evaluation to avoid overfitting.
- Enough budget for post-task reflection and cross-agent discussion.
- Agents that can produce useful self-audits; the method is still LLM-reflection-driven.
- A MAS setting where coordination and context pressure matter. For simple tasks or single-agent-dominant tasks, the mechanism is less compelling.
- Verifiable or at least scored outputs. Without an outcome/evaluator, the “evolution” target is underdetermined.

**Limitations / failure modes / non-transfer**

The paper’s explicit limitations:
- It evolves scaffolds and organization only: behaviors, collaboration patterns, coordination rules.
- It does not adapt execution infrastructure: tool APIs, environment harnesses, verifiers, or memory backends.
- It does not update underlying LLM parameters.
- It relies on post-task reflection and explicit scaffold updates, which are interpretable but may not internalize recurring behavior into the model.

Additional skeptical read:
- Results are Claude Sonnet 4.6-specific. Behavioral rates may not transfer to other models or later releases.
- Reflection quality is assumed; bad self-diagnosis can commit bad scaffold changes.
- The method needs good trace structure. If local traces, messages, artifacts, and outcomes are not cleanly separated, the core mechanism degrades.
- The method is MAS-specific. It does not directly apply to a single-operator harness unless we treat separate sessions/tools/agents as “agents” with local traces.
- Strongest claims are on long-horizon, coordination-heavy benchmarks. Smaller-margin columns are explicitly inconclusive.
- Figures 3 and 4 support scalability/cost claims visually, but the text extraction does not provide all exact point values; do not overstate them.
- “Best average across nine columns” is unweighted arithmetic mean across heterogeneous metrics.
- Evolution set is small, about 20 instances per benchmark/subset; useful, but still vulnerable to benchmark-specific scaffold tuning.
- Cost claims are relative and experimental; Figure 4 gives trade-off curves but not full tabulated exact costs in the extracted text.
- It assumes scaffold edits are safe to commit after local validation; in real harnesses, scaffold/rule accretion is a known failure mode.

**Integration into OUR system**

act-drain: applicable. Concrete bolt-on: replace centralized “daily correction mining proposes rules/hooks” with a collaborative evidence pass over session roles/surfaces. For each correction, preserve the local context of the surface that produced it: prompt/rule/hook/tool/session segment. Then require cross-surface evidence exchange before proposing a rule. Example: a Stop hook failure, a user correction, and an uncommitted-warn event each produce local summaries; act-drain aggregates only short summaries and cited trace spans. This directly targets our measured accretion/policy-maze failure by making proposals name the failing surface and downstream effect.

session-trace: applicable. Concrete bolt-on: add a distributed failure-attribution replay mode over `agentlogs.db`: split a session into local chains by actor/surface such as Codex, Claude, tool calls, hooks, subagent, user corrections. Each chain emits `(i_erred, step, confidence, evidence_span)`, then a collaborative merge ranks candidate failure steps. This is the closest paper-to-system mapping and should be evaluated against human correction points.

skills/rules/hooks: applicable, but narrowly. Concrete bolt-on: add “teammate profiles” as surface profiles, not agent-personas: hook profile, skill profile, rule profile, ToolSearch profile. Each profile records when the surface is reliable, when it overfires/underfires, and what evidence it needs. Do not add a new flat rules list. The paper’s L1/L2/L3 maps to skill/rule/hook patch, interaction contract/profile, and shared governance/index change.

MEMORY: applicable. Concrete bolt-on: make condensed-memory entries link first-class to raw session-trace spans and local evidence summaries. The primer says this link is not first-class today. Meta-Team’s useful mechanism is not “more memory,” but preserving local trace provenance while summarizing only what crosses into team-level learning.

`/eval`: applicable. Concrete bolt-on: create an eval for collaborative attribution vs centralized attribution on historical agentlogs corrections. Metric: can the system identify the corrected surface and decisive step? Baselines: current act-drain central synthesis, local-only per-surface diagnosis, collaborative per-surface diagnosis. Measure accuracy, token cost, false rule proposals, and downstream accepted/reverted governance edits.

predict-then-falsify: applicable and necessary. Concrete bolt-on: before accepting any Meta-Team-inspired harness edit, pre-register the mechanism: “distributed attribution should reduce over-broad rule proposals” or “surface profiles should reduce over-ask corrections.” Accept only if session-trace shows the intended mechanism fired. Otherwise revert. This prevents importing the paper as another policy-growth engine.

Workflow: applicable. Concrete bolt-on: add a file-bus recipe for “collaborative postmortem”: gather trace slices, run local surface audits, write summaries, then run a team-level merge. Keep single-writer-many-readers: local auditors write evidence files; only the parent merge writes the final proposed scaffold/rule/hook change.

ToolSearch: applicable. Concrete bolt-on: treat deferred tools as an open roster. Store tool profiles from actual usage: query classes where the tool helped, failed, cost too much, or hallucinated. ToolSearch retrieval should use these profiles to select tools, not just metadata. This is an L2 teammate-profile analogue.

NOT-APPLICABLE: hosted MAS framework adoption. The primer explicitly rejects hosted runtime/server/DB stand-up and framework dependencies. Meta-Team should be pattern-extracted, not adopted as a dependency.

Most promising integration: `/eval` plus `session-trace` first. Build a small attribution benchmark from existing human corrections, compare centralized vs local vs collaborative diagnosis, and only then wire successful pieces into act-drain. The paper’s core claim is about attribution quality under distributed traces; that is testable in our harness before adding any new governance machinery.
