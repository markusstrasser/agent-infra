**Mechanism**

StreamMemBench is an evaluation benchmark for agent memory, not a new memory architecture.

Step by step:

1. Start from EgoLife lifelog streams: 7-day egocentric recordings from 6 participants, split into 3,347 five-minute chronological segments.

2. For each segment, an anchor-construction agent extracts “evidence anchors”: user-specific facts that could matter for future assistance, such as preferences, commitments, roles, constraints, plans, or capabilities.

3. For each evidence anchor, it generates two future task queries:
   `T1`: initial task  
   `T2`: follow-up task  
   Both require the same hidden anchor, but neither query explicitly states it.

4. A review agent filters candidates for:
   evidence support, subject attribution, consistency, no leakage, actual need for the evidence, naturalness, and non-identical task scenarios.

5. During evaluation, the memory system ingests the lifelog chronologically up to the segment containing the target anchor.

6. Before task execution, the benchmark checks `Fidelity`: whether the system’s exposed memory delta contains the anchor with correct participant attribution, temporal scope, and factuality.

7. The system receives `T1` and answers `R1`.

8. A simulated user/evaluator scores `R1` for `Initial Evidence Use` (`IEU`): did the answer actually use the hidden anchor?

9. If `R1` is wrong, the simulated user gives corrective feedback containing the missing evidence. The system answers again with `RF`.

10. The benchmark scores `Feedback Incorporation` (`FI`): did the system use the correction in the same interaction?

11. The completed interaction is committed through the memory system’s normal memory-formation interface.

12. The system receives `T2` and answers `R2`.

13. The benchmark scores `Follow-up Reuse` (`FUR`): did the later answer reuse the original evidence or the corrected experience?

**Why it works**

The causal claim is that memory quality cannot be inferred from storage alone. A system can retain evidence but fail to retrieve or apply it when needed, can use explicit feedback locally but fail to consolidate it, or can answer the first task correctly but lose the behavior on follow-up.

The benchmark works by forcing the same evidence anchor through a lifecycle:

observed evidence → stored memory → initial task behavior → feedback repair → later task reuse

That lifecycle decomposes failures that a single memory-recall score would collapse. The paper’s central theoretical point is: future-oriented personal assistance requires evidence to become behavior, not merely stored text.

**Preconditions**

The benchmark requires:

1. A chronological observation stream with identifiable source observations.

2. Extractable user-specific evidence that is transferable beyond the immediate scene.

3. Evidence anchors tied to source observations strongly enough for review and scoring.

4. Paired downstream tasks where the correct answer depends on the hidden anchor.

5. A memory system with some interface for stream ingestion, memory update, and later task answering.

6. Exposed memory deltas for the Fidelity metric. Without this, only black-box task-side metrics are available.

7. LLM judges/user simulators reliable enough for semantic scoring. The paper mitigates this by running judgments three times per anchor and majority-voting, but this is still a model-judge dependency.

8. Evaluation settings where simulated feedback is acceptable. This is weaker than real user feedback.

9. Privacy controls if used with real personal data. The paper explicitly warns about consent, minimization, access control, inspection, correction, and deletion.

**Measured results**

Dataset:

- EgoLife source: 7-day continuous egocentric recordings.
- Participants: 6.
- Segments: 3,347 five-minute segments.
- Approximate observations per segment: 200.
- Evidence anchors: 8,107.
- Queries: 16,214, two per anchor.
- Query types: 86.5% state queries, 13.5% infer queries.
- Subject focus: 47.4% about the wearer/user, 52.6% about other people in the user’s social context.

Evaluation setup:

- Memory systems: 8 total.
- Retrieval baselines: `RAGraw`, `RAGext`.
- Agentic/fact/consolidation systems: `Mem0`, `EverMemOS`, `A-Mem`, `MemOS`, `MemoryOS`.
- Procedural memory: `MemSkill`.
- Backbones: `DeepSeek-V4-Flash`, `Gemini-3-Flash`.
- Anchor/review/eval/user agents: `DeepSeek-V4-Pro`.
- Retrieval encoder: `bge-m3`, `top-k = 10`.
- Decoding: temperature 0, fixed seed.
- Judge repetitions: 3 per anchor, majority vote.
- CIs: not reported.
- Pre-frontier flag: the paper uses 2026-labeled DeepSeek/Gemini systems; not flagged as pre-frontier from the text. I did not independently verify model frontier status.

Manual audit:

- Random sample: N = 100 anchors.
- T1 plausibility: 90.0%.
- Feedback plausibility: 93.5%.
- Cohen’s κ: 0.336 for T1, 0.424 for feedback.
- Interpretation: only fair/moderate agreement, so data quality is useful but not clean enough to treat judge-generated tasks as ground truth without skepticism.

**Limitations / failure modes / non-transfer**

1. It evaluates a selected set of memory systems, not the full commercial/research space.

2. It uses simulated user feedback, not real user correction behavior.

3. The benchmark depends heavily on LLM-generated anchors, LLM review, and LLM scoring. Majority vote helps but does not remove judge bias.

4. No confidence intervals are reported, so the significance of close differences is unclear.

5. Fidelity can be inflated by raw retention. `RAGraw`, `A-Mem`, and `MemoryOS` get 100.0 Fidelity in some settings, but this does not mean they use the memory well.

6. The extracted evidence comes from egocentric lifelog data, which is privacy-sensitive and not directly analogous to our agentlogs unless we define clear consent/control boundaries.

7. The license/intended-use appendix says StreamMemBench and EgoLife-derived artifacts are academic-research-only. We should pattern-extract the mechanism, not adopt the dataset as an operational dependency.

8. The task distribution is mostly state application, not deep procedural harness work. Direct transfer to agent-infra governance, hooks, evals, and workflow decisions would require our own anchor/task construction.

9. Low κ in the manual audit means the benchmark’s task naturalness and feedback naturalness are not airtight.

10. The main transferable result is diagnostic structure, not the absolute memory-system ranking.

**Integration into OUR system**

`/eval + ~/Projects/evals`: applicable. Build a small “StreamMemBench-for-agentlogs” eval where anchors are real human corrections or accepted MEMORY lessons, not lifelog facts. Metrics should mirror `Fidelity`, `IEU`, `FI`, `FUR`: was the lesson stored, did the agent use it on the next similar task, did feedback repair it, and did it persist into a later task? This belongs in `/eval`, not as a production hook first.

`session-trace / agentlogs.db`: applicable. Add evidence-anchor tracing over raw transcripts: condensed lesson → originating session span → later similar prompt → whether the behavior changed. This directly fixes the primer’s stated gap that the link from condensed MEMORY to raw agentlogs is not first-class.

`MEMORY`: applicable. Add source links from each condensed memory item to raw `agentlogs` spans and later reuse evidence. Do not rewrite MEMORY into a benchmark dataset; append metadata or sidecar indexes that make memory-to-trace falsifiable.

`act-drain / blindspot loop`: applicable. Extend classifications beyond `GROW_COVERAGE / RAISE_AUTONOMY / REDUCE_ERROR` with lifecycle failure labels: formation failure, initial-use failure, feedback-incorporation failure, correction-consolidation failure, evidence-use persistence failure. This directly targets the measured accretion problem by diagnosing where a rule failed before adding another rule.

`predict-then-falsify`: strongly applicable. For every harness/rule/memory edit, pre-register which lifecycle metric should move. Example: “This rule should reduce initial-use failures for cross-repo git operations.” Accept only if later traces show the intended mechanism fired. Otherwise revert or mark ineffective.

`skills/rules/hooks`: applicable but only after eval evidence. Use the lifecycle labels to decide whether the fix is a skill, rule, or hook. Formation failure means memory/indexing issue. Initial-use failure may need retrieval or prompt surfacing. Feedback-incorporation failure may need interaction handling. Persistence failure may need MEMORY/session-trace linkage. Do not add flat rules just because FUR failed.

`Workflow`: applicable. Use file-bus workflows to run the two-episode evaluation: initial task, feedback, commit/memory update, follow-up task. This maps cleanly onto the paper’s trajectory without needing a hosted framework.

`ToolSearch`: applicable. Treat deferred tools as a memory surface: when a past correction says “use Context7 for library docs” or “use GitHub app for PR comments,” evaluate whether ToolSearch retrieves and the agent actually invokes the right tool on the later task. Metrics map cleanly to Fidelity = tool hint exists, IEU = tool used initially, FI = uses it after correction, FUR = uses it later without correction.

`act-drain`: concrete bolt-on should be a diagnostic report, not an auto-enforcer. Start by labeling a sample of prior corrections against the lifecycle taxonomy and count which failure class dominates. If over-ask remains the dominant blindspot, check whether failures are from missing memory, failure to apply known memory, or persistence after correction.

`NOT-APPLICABLE`: adopting StreamMemBench itself as a dependency is not applicable. It is tied to EgoLife, academic-only data, egocentric personal observations, and LLM-generated tasks. The useful part for us is the evidence-anchor lifecycle and four-metric evaluation shape.
