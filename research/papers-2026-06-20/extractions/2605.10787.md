**Mechanism**

ComplexMCP is a deterministic benchmark for tool-using agents in large, stateful MCP environments.

Step by step:

1. Define a task as `M = <S, T, I, sigma, G, Phi>`:
   `S` is environment state, `T` is MCP toolset, `I` is user instruction, `sigma` is random seed, `G` is target goal state, and `Phi` is evaluator.

2. Build a synthetic knowledge base `C` containing entities such as user profiles, message histories, tickers, carts, contacts, flights, etc.

3. Instantiate the initial state from seed:
   `s0 = Sample(C; PRNG(sigma))`.
   Same seed gives reproducible state; different seeds change concrete entities, permissions, cart contents, histories, etc.

4. Expose the agent to MCP tools:
   15 MCP servers, 315 tools total.
   Seven stateful servers: `LightOS`, `LightTalk`, `LightShop`, `LightWeather`, `LightFlight`, `LightStock`, `LightNews`.
   Eight stateless servers: math, crypto, chemistry, time, network, string, unit, graph.

5. Run agent rollouts for up to `H` steps:
   at each step the model receives history/tool observations and emits a tool call.

6. Make tools interdependent:
   later tools require state or ids produced by earlier tools. Example: send a message may require network acceleration, UID resolution, block/permission checks, and privilege escalation.

7. Inject seed-driven perturbations:
   execution is subject to deterministic stochasticity `eta(sigma)`, simulating transient failures, network latency, unavailable entities, or environmental noise while staying reproducible.

8. Evaluate by state diff, not LLM judgment:
   compare `envold`, `envgt`, and `envnew` over relevant nested key paths.

9. Compute:
   `T`: required changed elements.
   `M`: correctly modified required elements.
   `Mb`: unintended changed elements.
   `Rc = M / T`.
   `Rb = Mb / T`.

10. Count task success only if:
   `Rc = 1` and `Rb = 0`.

11. Evaluate 47 manually curated tasks, each with annotated ground-truth trajectory and deterministic outcome. Hard tasks require more than 30 distinct tools and over 60 total tool invocations in the gold path.

**Why it works**

The causal claim is that real commercial software automation fails not at isolated function calling but at stateful, interdependent, noisy workflows. ComplexMCP makes those hidden requirements measurable.

The benchmark is supposed to work because:

1. Seeded state prevents hard-coded heuristics:
   the environment logic is stable, but concrete entities and permissions vary, forcing active perception.

2. Stateful sandboxes expose clean-slate bias:
   agents must inspect current state before acting. If they assume empty carts, default permissions, or clean sessions, they create collateral state changes.

3. Interdependent tools test latent prerequisite discovery:
   success requires finding unmentioned intermediate tools, not merely retrieving semantically obvious final-action APIs.

4. Deterministic state-diff scoring avoids LLM-judge noise:
   correctness is grounded in final environment state and collateral damage, not a subjective trajectory score.

5. Dynamic failures test recovery:
   transient or logical tool failures distinguish agents that retry, verify, or route around problems from agents that rationalize failure.

**Preconditions**

The mechanism needs these to hold:

1. The sandbox state must be rich enough that naive final-action calls fail or cause side effects.

2. Ground-truth trajectories and target states must be manually correct. This is load-bearing: the benchmark has only 47 tasks because annotation is expensive.

3. The evaluator must ignore irrelevant volatile keys like timestamps/random ids while preserving all correctness-relevant state paths.

4. Seeded stochasticity must be deterministic under replay; otherwise comparisons across models/runs are not clean.

5. Tool docs and MCP interface must be identical across humans and models. The paper says the human baseline used the same MCP interface, instructions, and tool documentation.

6. Agent prompts must expose the tool interface in a way models can actually use. The reported full-context setup includes descriptions for over 300 tools, about 30k prompt tokens.

7. For RAG comparisons, the retriever must be held fixed. The paper uses `all-MiniLM-L6-v2`.

8. Claims about model capability are snapshot-bound. The evaluated models include older/pre-frontier models relative to our current 2026 stack, especially `GPT-4o`, `Claude-sonnet-3.5`, and Llama-3 series; even `GPT-5.1`, `Claude-opus-4`, and `Gemini-3-*` are paper-era snapshots, not necessarily current live rates.

**Limitations / failure modes / non-transfer**

Paper limitations:

1. Only 47 tasks. The paper explicitly calls this a deliberate trade-off for determinism and manual trajectory integrity.

2. Manual expert annotation is expensive. Scaling the benchmark requires more manual mapping of tool dependencies and ground-truth trajectories.

3. Synthetic sandboxes may not fully transfer to live commercial software. The paper argues they simulate last-mile complexity, but they are still controlled environments.

4. Model results are time-bound. Several evaluated systems are pre-frontier or at least not guaranteed to match our live model surfaces. Do not import the percentages as current model capability rates.

5. Full-context baseline is expensive and may be implementation-dependent. The token bottleneck partly reflects the ReAct/full-tool-description prompt strategy.

6. RAG comparison is narrow: all-MiniLM-L6-v2, two models, and semantic retrieval variants. It does not prove all retrieval or graph-aware tool planners fail.

7. No confidence intervals; only mean ± SD over three runs. Small run count limits statistical confidence.

8. Potential vendor/conflict issue: authors Y.L., X.Y., L.W., W.L. are affiliated with Alibaba Group; Alibaba develops Qwen-3-Max, which is evaluated. Qwen is not top-performing here, but the conflict is still relevant.

Observed agent failure modes:

1. Tool retrieval saturation: some models degrade as distractor tools scale toward 300+.

2. Clean-slate bias / over-confidence: agents skip environment verification and assume empty/default state.

3. Strategic defeatism: agents stop after recoverable errors instead of retrying or finding compensatory paths.

4. Collateral damage: success requires not only achieving the target but avoiding unintended state changes.

5. Latent dependency miss: semantically obvious tools are not enough when prerequisite state-producing tools are hidden.

**Integration into OUR system**

Primary integration: `/eval + ~/Projects/evals`.

Concrete bolt-on: build a small ComplexMCP-style harness eval for our own agent stack, not by adopting their benchmark wholesale. Use our existing eval home to create seeded, replayable, state-diff tasks over our actual surfaces: `ToolSearch`, file-bus `Workflow`, and session/agentlogs operations. Score `Rc` and `Rb` by deterministic state diff, plus recovery after injected tool failures. This directly fits our belief that “harness on a frozen model” is the lever.

Second integration: `predict-then-falsify`.

Concrete bolt-on: before any harness/rule/tooling edit, require a pre-registered prediction of which failure class should move: clean-slate verification miss, strategic defeatism, retrieval miss, or collateral state mutation. Accept only if `session-trace` shows the intended mechanism fired. Example: a new “verify current state before mutating” hook should reduce tasks where the agent mutates without first reading sibling/current state; if it only increases over-asking, revert.

Third integration: `session-trace / agentlogs.db`.

Concrete bolt-on: add trajectory labels for ComplexMCP-like failure modes in trace forensics:
`clean_slate_bias`, `latent_tool_dependency_miss`, `strategic_defeatism`, `collateral_mutation`, `tool_retrieval_saturation`.
Use existing raw transcript replay to identify whether the agent checked environment state before mutation, retried after transient failure, and recovered through alternate tools.

Fourth integration: `skills/rules/hooks`.

Concrete bolt-on: add a rule or hook pattern for mutating actions: before irreversible or stateful mutation, the agent must have a recent read/check of the relevant current state unless the command itself is the read. This should be scoped to concrete tool classes, not a broad “be careful” instruction, to avoid policy-maze accretion. Good targets: git staging/commit, file edits, calendar/email writes, repo mutation gateways, act-drain apply lanes.

Fifth integration: `ToolSearch`.

Concrete bolt-on: make deferred tool retrieval dependency-aware. The paper is a warning that semantic top-k alone misses latent prerequisite tools. For ToolSearch, store or infer prerequisite clusters: e.g. “send email” retrieves search/read/draft/send tools; “schedule meeting” retrieves calendar availability, attendees, rooms, create/update, timezone helpers. A retrieved tool should bring its prerequisite chain or affordance cluster, not just nearest-neighbor descriptions.

Sixth integration: `Workflow tool / file-bus just recipes`.

Concrete bolt-on: add seeded fault injection to workflow evals: transient tool failure, stale state, missing id, permission block. Then require retry/alternate path behavior before declaring dry. This maps directly to debug-until-dry and loop-until-dry surfaces.

Seventh integration: `act-drain / blindspot loop`.

Concrete bolt-on: classify human corrections matching this paper’s modes:
`GROW_COVERAGE`: missing prerequisite tool/rule.
`RAISE_AUTONOMY`: strategic defeatism / over-ask after recoverable failure.
`REDUCE_ERROR`: clean-slate mutation or collateral damage.
Be skeptical: do not add one rule per incident; aggregate by failure mode to avoid the primer’s noted accretion/policy-maze failure.

Eighth integration: `MEMORY`.

Concrete bolt-on: append only if this mechanism recurs in our own traces. The paper’s general lesson is useful, but MEMORY should not store vendor benchmark percentages as if they were our rates. Store links from condensed lesson to raw `session-trace` examples when our own failures match.

Not applicable as dependency: adopting ComplexMCP itself as a framework/runtime.

Why: primer says we do not adopt frameworks as deps and reject hosted/server/DB stand-up requirements. The right move is pattern extraction: seeded state, deterministic state-diff scoring, failure-mode labels, and prerequisite-aware tool retrieval.
