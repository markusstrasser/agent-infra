**Mechanism**

SkillDAG turns a flat skill library into a typed directed graph exposed to the agent at runtime.

1. Represent every skill as a node.
2. Add typed edges:
   `depends_on`, `specializes`, `composes_with`, `similar_to`, `conflicts_with`.
3. Keep `depends_on` and `specializes` as an acyclic directed backbone.
4. Expose graph access through agent-callable operations:
   `search`, `show`, `propose-edge`, `edit-edge`.
5. `search(q, K, D)` returns three separate fields:
   `matches`: top-K semantic vector matches;
   `neighbors`: bounded BFS neighbors over positive walkable edge types;
   `conflicts`: one-hop `conflicts_with` edges to avoid.
6. `show` fetches full skill bodies only after the agent chooses candidates.
7. Cold-start graph construction embeds each skill in two views:
   `e_self`: what the skill does;
   `e_needs`: what it requires, generated by an LLM HyDE-style prerequisite summary.
8. Candidate pairs come from self/self and needs/self cosine rankings using adaptive threshold `max(0.35, min(0.75, mean + 1 SD))`.
9. An LLM classifier assigns `depends_on`, `specializes`, `composes_with`, `similar_to`, or `none`; `conflicts_with` is excluded from cold-start.
10. During episodes, the agent can propose graph edits from execution evidence.
11. `propose-edge` previews the edit and pair history.
12. `edit-edge` commits add/delete/retype operations if invariants pass:
   acyclicity, non-contradiction, append-only reversibility.
13. Every accepted edit logs origin, reason, task id, and history for rollback.

**Why it works**

The causal claim is that skill selection fails because flat similarity collapses different operational relations into one score. A prerequisite, a redundant alternative, and a harmful conflict can all be “near” in embedding space but require different agent behavior.

SkillDAG claims gains from three mechanisms:

1. Typed relations preserve action-relevant semantics:
   prerequisites are loaded, duplicates can be avoided, conflicts can be pruned.
2. Agent-callable retrieval preserves agency:
   the LLM sees separate evidence channels instead of receiving an opaque ranked bundle from a fixed graph policy.
3. Online edits accumulate execution-backed structure:
   the graph improves across episodes, while structural invariants prevent obvious incoherence.

The strongest theoretical point is not “graphs are better”; it is “the graph should be an interface, not a hidden retriever policy.” The agent decides how to use typed evidence.

**Preconditions**

SkillDAG needs:

1. A large enough skill/tool surface that flat retrieval or full enumeration is failing.
2. Skill descriptions/bodies informative enough for embeddings and pair classification.
3. A runtime where the agent can call retrieval repeatedly, not just receive one static context bundle.
4. A meaningful notion of skill relations:
   dependencies, specialization, composition, redundancy, conflict.
5. Execution traces rich enough to justify online edits.
6. Cheap enough embedding and pair-classification passes.
7. Guardrails for graph mutation:
   acyclicity, contradiction checks, append-only history.
8. Evaluation that distinguishes retrieval recall from downstream task success.

Non-precondition: a hosted service or new framework. The paper’s mechanism can be pattern-extracted into local tooling.

**Limitations / failure modes / non-transfer**

1. Single-observation edits are risky.
   The paper’s own limitation says one execution observation can commit an edge; structural checks bound graph corruption but do not validate semantic truth.

2. No CIs, no paired reruns.
   The main downstream reward comparison mixes quoted baseline numbers with new SkillDAG runs. That weakens causal attribution.

3. Retrieval gains do not always transfer to task gains.
   On `gpt-5.2-codex`, ALFWorld ties GoS at `93.6`; the paper itself says the routing aid “vanishes” once the backbone can reason past poor bundles.

4. Recall monotonicity is not context monotonicity.
   The edited graph cannot evict hits in the untruncated union, but actual agents have context budgets. More retrieved ground-truth skills can still add noise.

5. Conflict detection is under-evidenced.
   `conflicts_with` is online-only because static text cannot infer co-use harm. But the paper does not show strong aggregate conflict-edge precision.

6. Edge types are semantically hard.
   Operational definitions mention measurable counterfactual success drops/lifts, but the implementation uses LLM classification and single-agent judgment, not actual counterfactual experiments per edge.

7. ALFWorld failure modes show selection is not the whole problem.
   Tight loops and grounding failures persisted even when the graph supplied correct procedural skills.

8. The benchmark surface is skill-selection-heavy.
   Transfer to our system should be limited to surfaces with many skills/tools/rules and observable retrieval failures, not treated as a general agent-autonomy result.

9. Hosted/runtime dependency is not needed and should not be adopted.
   The useful part is the typed graph + audit/edit protocol, not the paper’s implementation as a framework dependency.

**Integration into OUR system**

ToolSearch:
Concrete bolt-on. Add typed relation metadata to deferred tool/skill discovery: `depends_on`, `conflicts_with`, `similar_to`, `specializes`, `composes_with`. Return separate fields from search: lexical/vector matches, typed neighbors, conflicts. Do not replace ToolSearch ranking wholesale; expose structure as evidence.

skills/rules/hooks:
Concrete bolt-on. Convert the currently flat skills/rules/hooks lists into a local typed graph. Start with deterministic/static edges from existing metadata and path scopes:
`skill depends_on rule`, `hook enforces rule`, `skill conflicts_with hook/rule only when observed`, `rule specializes global rule`, `similar_to duplicate rule`.
Require append-only edit history and no positive edge coexisting with conflict.

MEMORY:
Concrete bolt-on. Add first-class links from condensed MEMORY entries to raw `agentlogs.db` session ids and exact trace spans. This mirrors SkillDAG’s “edge reason + task_id” auditability. Do not store free-floating lessons without raw provenance when they become graph edges.

session-trace / agentlogs.db:
Concrete bolt-on. Use session-trace as the evidence source for proposed edges:
when a session shows “agent needed skill X before skill Y,” emit a candidate `depends_on`;
when loading two rules caused bad behavior, emit candidate `conflicts_with`;
when two hooks/rules repeatedly fire on same predicate, emit `similar_to` or consolidation candidate.
Keep this as candidate generation, not auto-truth.

act-drain / blindspot loop:
Concrete bolt-on. Replace monotonic rule/hook accretion with graph-aware proposals:
new blindspot can produce either add-edge, retype-edge, delete-edge, or conflict-edge, not only “add another rule.”
This directly targets the primer’s measured accretion / policy-maze failure.

predict-then-falsify:
Concrete bolt-on and required gate. Before accepting a graph edit or new retrieval behavior, pre-register the mechanism:
example: “adding `depends_on(A,B)` should increase searches that load B after A-related queries and reduce missed-prerequisite corrections.”
Accept only if later traces show that mechanism fired. This is stronger than SkillDAG’s single-observation commit.

`/eval + ~/Projects/evals`:
Concrete bolt-on. Build a retrieval eval over our own skill/tool/rule queries:
gold: historically correct skill/tool/rule loaded in successful sessions;
metrics: Ret@5, Ret@1, MRR, token cost, false-conflict rate, and downstream over-ask reduction.
Run frozen-model before/after harness changes. This paper’s numbers are not enough for adoption.

Workflow:
Partial bolt-on. Workflow/file-bus recipes can consume graph search to load prerequisite procedures and avoid conflicting ones. But do not make Workflow mutate the graph directly. Mutation should go through act-drain/session-trace evidence plus predict-then-falsify.

act-drain:
Concrete bolt-on. Add an “edge proposal drain” stage:
session corrections → candidate typed edges → invariant checks → append-only proposal log → eval/predict gate → accepted graph update.

NOT-APPLICABLE:
Do not adopt the paper’s repository as a dependency. Primer says reject hosted runtime/server/DB stand-up and pattern-extract mechanisms. Our system is single-operator local; the useful transplant is a typed, auditable retrieval graph over existing surfaces, not a new framework.
