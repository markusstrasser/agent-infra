**Mechanism**

CAHL is a hierarchical tool-use training method with two learned policies:

1. The high-level planner receives the user query `q` and tool set `T`.
2. It emits a global plan `Z = [z1, z2, ..., zk]`, where each subtask is supposed to name the intended tool and argument values extracted from the query.
3. The low-level executor receives prior feedback `F1:k`, a planner subtask `zk`, and the tool set `T`.
4. It emits either a tool call, formatted as JSON/code, or a natural-language response.
5. The high-level planner is rewarded by:
   - parameter reward: do expected argument values appear in the generated plan?
   - execution reward: after the low-level executor follows the plan, does the resulting trajectory match the ground-truth sequence?
6. The low-level executor is rewarded by:
   - format reward: required special tokens/tags are present and ordered.
   - syntax reward: tool call arguments conform to schema and types.
   - semantic reward: selected tool names, parameter names, and parameter values match ground truth.
7. Both policies are optimized with GRPO. The high-level policy samples candidate plans; each plan is parsed into subtasks; the low-level executor samples executions; rewards are computed; low-level updates happen during execution; high-level updates happen after full trajectory evaluation.
8. At inference, CAHL first plans, then executes each planned step. This adds latency but is intended to reduce coarse/underspecified plans and hallucinated executor parameters.

**Why it works**

The causal claim is planner-executor capability alignment.

The paper argues that ordinary hierarchical systems fail because the planner is optimized for logically correct decomposition, while the executor is optimized separately for tool-call mapping. That creates two failure modes:

- The planner emits a subtask too coarse or too fine for the executor’s actual tool/action space.
- The executor misses the planner’s intent, drops constraints, or hallucinates missing schema fields.

CAHL’s claimed fix is to couple planner reward to actual executor outcomes and executor reward to schema/semantic correctness. This should push the planner toward executable granularity and push the executor toward faithful realization of planner intent.

Skeptical read: the causal story is plausible, but the evidence is mostly benchmark deltas plus ablations. It does not prove general planner-executor alignment outside these tool-use benchmarks.

**Preconditions**

CAHL needs:

- A separable planner/executor architecture.
- Stable tool schemas with machine-checkable names, parameters, and types.
- Ground-truth tool trajectories or final answers sufficient to compute rewards.
- A verifier/reward function that can distinguish correct tool names, parameter names, parameter values, formatting, and semantic text outputs.
- A training environment where both planner and executor can be fine-tuned.
- Enough training data: they use a 4,000-sample composite dataset from ToolACE, Hammer, and xLAM.
- Compute: they train on 2 NVIDIA A40 GPUs for 15 epochs, using Qwen-2.5-Instruct-7B with LoRA rank 16 and Unsloth acceleration.
- Tasks where a high-level plan can actually improve execution. For single-shot or trivial tool calls, the extra planning layer may be overhead.

**Limitations / failure modes / non-transfer**

The paper’s own limitation: hierarchical planning adds inference latency and training cost. The reported multi-turn latency is 13.21s vs 7.79s for ToolRL, and training VRAM is 36GB vs 15GB.

Additional skeptical limitations:

- It is a fine-tuning method, not a prompt-only orchestration pattern.
- It depends on verifiable rewards and ground-truth tool trajectories. Our open-ended agent work often has partial/noisy verifiers.
- The result may not transfer to subscription-hosted frontier agents where we cannot jointly train planner and executor weights.
- Benchmarks emphasize tool-call correctness and final answer accuracy, not long-lived local harness maintenance, governance drift, or human-supervision reduction.
- Bamboogle only measures final answer accuracy, not intermediate tool-call correctness.
- The text does not report CIs, p-values, seeds, variance, or replication.
- Some baselines were not evaluated on Bamboogle due to unavailable public checkpoints.
- The strongest observed deltas are in constrained tool-use environments; do not inflate this into a general “hierarchical agents work better” claim.
- It may worsen simple tasks where planning overhead dominates.
- It assumes planner/executor roles are explicit. Many Codex/Claude sessions interleave planning, acting, and repair in one policy loop.

**Integration into OUR system**

Applicable as pattern extraction, not as a dependency or framework adoption.

- **/eval**: bolt on a planner-executor alignment eval. Use session traces where a plan or instruction led to a wrong tool call, dropped constraint, over-ask, redundant loop, or schema mismatch. Metrics should mirror the paper where useful: invalid tool-call rate, redundant-call ratio, dropped-required-parameter rate, and task success. Pre-register expected movement before changing harness behavior.

- **predict-then-falsify**: strong fit. For any harness edit inspired by CAHL, predict the mechanism explicitly: “schema-aware plan lint should reduce dropped required parameters in tool calls by X on replay set Y.” Accept only if session-trace replay shows the intended mechanism, not just a vague quality bump.

- **session-trace / agentlogs.db**: add labels for planner-executor misalignment cases in trace forensics: coarse plan, over-specific plan, dropped constraint, unavailable-tool plan, hallucinated parameter, wrong call order, redundant loop. This is the closest analogue to their trajectory-level evidence.

- **skills/rules/hooks**: add lightweight “plan-schema anchoring” checks where a plan names or implies a tool. The check should verify that required parameters from the tool schema are either present, explicitly deferred, or marked unknown. Keep this advisory first; block only after measured false-positive data.

- **ToolSearch**: strong bolt-on. ToolSearch should return not only tool names but a capability envelope: required parameters, side effects, verifier availability, and common failure modes. Planner-facing outputs should make the executor’s actual capability boundary visible before a plan is written.

- **Workflow tool / file-bus just recipes**: add an optional plan contract artifact for multi-step workflows: intended tool, required args, verifier, expected output, and dependency on previous step. Executors consume the contract; trace replay can score whether execution matched it. Do not create a hosted runtime or new service.

- **act-drain / blindspot loop**: add “planner-executor misalignment” as a correction subtype if it is not already covered by existing taxonomy. The daily miner can surface cases where the human corrected an agent because the plan was reasonable in prose but not executable by the actual tool surface.

- **MEMORY**: use only for condensed, canonical lessons linked back to raw trace IDs. CAHL’s relevant idea is not “remember to plan better”; it is “store the capability boundary and the failure trace so future planning can load it.”

- **NOT-APPLICABLE: full CAHL RLVR training**. Our system is a single-operator local harness over Claude Code, Codex CLI, and Cursor with subscription dispatch. We do not control frontier model weights, and we reject hosted runtime/server/DB adoption here. The portable mechanism is capability-aware plan contracts plus trace-level falsification, not joint GRPO fine-tuning.
