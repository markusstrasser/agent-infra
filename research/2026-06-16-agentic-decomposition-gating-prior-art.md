## Scope / decision being made
Should we build, and how, three things:
1. Fan-out isolation for parallel agents on a shared repo.
2. Decomposition-time / pre-merge invariant or blast-radius gating.
3. The "expect garbage → decompose → fan out" loop as a named pattern with empirical backing.

### Key mechanism details / footguns (transferable)
- **Worktrees isolate the filesystem, NOT the runtime** — ports, databases, `.env`, Docker daemon all still collide. Field-standard fix = per-worktree `.env.local` (gitignored) overriding ports/DB-URL + base committed `.env` with non-secret defaults. The "production standard for >4 concurrent agents" = **worktree per agent + one lightweight container per worktree** (isolated DB + dev server). (zylos.ai, codeongrass.com, upsun.com)
- **Disk overhead is real**: a Cursor user hit 9.82 GB in 20 min on a 2 GB codebase from auto-worktree creation (~5× base repo per active worktree set; each gets its own `node_modules`/`dist`). Audit disk before spinning up many. (appxlab.io, zylos.ai) — *matches genomics `disk-preflight.md` instinct.*
- **Prevent merge hell at the boundary, not at merge time** (codewithseb.com, the strongest practitioner playbook): scope by module — tasks in the same module share a worktree *sequentially*; tasks across modules go to parallel worktrees, so two agents never edit the same file. **Rebase, not merge, between worktrees** (merge commits pollute `git log` and confuse agents reading history; linear chains read better). 20-min review cadence. Practical ceiling **2–4 sessions** per human before you need a review partner or subagent delegation.
- **incident.io runs 4–5 parallel Claude agents routinely** (cited datapoint, upsun.com). Gartner: 1,445% surge in multi-agent adoption Q1'24→Q2'25; avg Claude Code session grew 4min→23min (Anthropic data).

### The 2026 orchestrator ecosystem (a whole product category exists)
A dedicated tool category now runs N agents in isolated worktrees with a Kanban/review layer — **all of them standardize on git-worktree-per-agent** (kanban card = worktree = agent): **Conductor** (Melty Labs, macOS, Claude Code + Codex), **Vibe Kanban** (BloopAI, Apache-2.0, cross-platform, **10+ agents incl. Claude Code/Codex/Gemini/Copilot/Amp/Cursor/OpenCode/Droid/Aider/Qwen**, To Do→In Progress→Review→Done columns — *note: Bloop announced shutdown early 2026, project continues community-maintained*), **Claude Squad**, **Nimbalyst** (Crystal fork + visual editing), **Superset**, **Emdash**, **Baton**, **ccswarm**, **Google Antigravity Mission Control** (~5 concurrent, adopted Claude Code's skill standard in early 2026). Augment Code's roundup of 9 orchestrators states the unsolved-by-tooling residual plainly: *"most still leave task alignment, conflict resolution, and merge decisions on my plate."* (augmentcode.com, rustman.org, nimbalyst.com, htdocs.dev)

**The single most-repeated practitioner finding across this entire category (rustman.org states it most sharply):** *"Stack six sessions and your bottleneck becomes: did you decompose the work well enough that six things can run in parallel without stepping on each other?... the moment two lanes need to modify overlapping code, worktree isolation doesn't save you — you get six drift-parallel solutions to the same problem, and the merge review becomes the new bottleneck. The skill this forces is task decomposition that doesn't overlap."* → **Isolation (axis 1) is a SOLVED commodity; the binding constraint has moved entirely to decomposition quality (axis 2) and review throughput (axis 3).**

**This validates the genomics repo's existing stance** (`subagent isolation: "worktree"`, CAID worktree-beats-soft-by-7.8pp in CLAUDE.md). The single most transferable *new* item: the **module-scoping rule as conflict PREVENTION at decomposition time** (codewithseb) — which is the bridge to axis 2.

## Axis 2 — Decomposition-time / pre-merge invariant or blast-radius gating

**Verdict so far: the blast-radius / affected-graph half is a MATURE, solved engineering practice (monorepo CI). The "gate at TASK-SPLIT time for an AI agent, with per-subtask acceptance checks" half is EARLY and only partially solved — one MCP tool (CodeImpact) does the pre-edit blast-radius gate; the spec-then-decompose-with-acceptance-checks-per-subtask planner pattern exists in agent frameworks but isn't packaged as a reusable gate. This is the part worth not reinventing where it exists, and the genuinely open part where it doesn't.**

### A. Blast-radius / affected-graph (MATURE — monorepo CI)
- **Nx `affected`**: Git diff → project graph → transitive closure of dependents. `nx graph --affected` visualizes. Failsafe: lockfile change marks *all* projects affected (tunable via `projectsAffectedByDependencyUpdates`). On a 500-pkg repo, 45min→8min CI. (nx.dev primary)
- **Bazel + `bazel-diff`** (Tinder): exact impacted target set between two git revisions; **directly impacted** (rule attrs / source deps changed) vs **indirectly impacted** (only a dep changed) — i.e. it already distinguishes a hub-edit from a leaf-edit via build-graph distance metrics. (github.com/Tinder/bazel-diff primary)
- **Aviator affected-targets merge queue**: PRs declare affected targets (computed via bazel-diff/Nx/Turborepo); non-overlapping PRs merge in disjoint queues in any order, overlapping PRs get stacked + tested together. Quote: *"an organization's implementation of how they compute affected targets acts as a dial of how aggressively or conservatively to merge."* This is exactly the **conflict-free-parallel-merge gate** at the PR level. (docs.aviator.co primary)
- **Caveat (the hub problem, stated)**: "If you're modifying a project used by a large portion of the monorepo, you end up running tasks for almost all projects" (nx.dev) and "circular deps are the #1 cause of everything-runs-on-every-PR" (how2.sh). So affected-graph tooling *detects* a high-fan-in hub edit by construction (it blows up the affected set) — that signal is reusable as a "this task touches a hub → don't parallelize / require human" gate.

### B. Ownership / invariant-boundary gating (review-time)
- **CODEOWNERS** = review-time only ("controls who approves, does NOT prevent runtime imports across team boundaries" — how2.sh). For build-time enforcement you need **Nx project boundaries** or **Bazel visibility rules**. Full isolation = both layers.
- **`@nx/owners` plugin**: ownership by *project matcher* (not just file paths), compiled to CODEOWNERS; survives project relocation. GitLab sections support `numberOfRequiredApprovals`. (nx.dev primary)
- **Aspect.build's CODEOWNERS-as-continuous-delivery** insight: aggregate per-dir `OWNERS` files into a root CODEOWNERS via bot commit on green main; an OWNERS change is governed by the OLD owners (you can't remove your reviewers in the same PR). Clean model for "ownership boundary is evaluated against committed state, not the proposed diff." (blog.aspect.build)

### C. THE DIRECTLY-TRANSFERABLE FINDS — pre-edit/pre-merge blast-radius + change-classification gates FOR AGENTS
**Axis 2's "decomposition-time check" is MORE solved than expected — a whole cluster of 2026 OSS tools do exactly this, most shipping an MCP server so they slot into an agent harness. Several go beyond blast-radius to semantic change-classification (refactor vs logic) AND test-gap analysis (does this logic change have a test?), which is the strongest building block for per-subtask acceptance coverage.** Ranked by fit to genomics (Python, MCP-native, deterministic, gate-shaped):

1. **`Ataraxy-Labs/inspect`** (Feb 2026) — strongest fit. CLI + **MCP server (6 tools)**. For every changed entity computes: **classification** (text-only / syntax / functional / combos — 7 categories, based on ConGra arXiv:2409.14121), **risk score 0–1** (= classification + blast radius + dependent count + public-API exposure; cosmetic gets 70% discount), **blast radius** (entities transitively affected, from full repo entity graph not just changed files), and **Union-Find commit untangling** (separates independent logical changes within one commit → reviewable as separate units — *directly relevant to "decompose a too-big diff"*). Emits a **verdict ladder: LikelyApprovable / StandardReview / RequiresReview / RequiresCarefulReview.** Local/free/OSS, BYO-LLM for the optional deep pass. Part of a 3-tool suite incl. `weave` (entity-level **semantic merge driver for git** — direct merge-conflict mitigation).
2. **`kailayerhq/kai`** (Dec 2025, **production: 2.8M commits analyzed, 71 change types, 5 langs**) — "semantic infrastructure for code change." `kai query impact src/x.ts` = transitive downstream impact; `kai ci plan` = minimal test selection (80% CI reduction). **Ships MCP server with 11 tools** giving agents call graphs, dependency maps, impact analysis, **test coverage**. Explicit thesis: *"Agent proposes edit → Kai validates impact → agent executes with proof, not generation with hope."* Roadmap: "verified agent loop." This is the most mature; the question is Python support depth (5 langs claimed, verify).
3. **`flakestorm/vibediff`** (Apr 2026) — "git-native semantic **intent** auditor." Parses diff via tree-sitter AST, sends only **metadata (never source)** to LLM, returns a **Vibe Score** over 4 dims: **Logic Match (35%)**, **Scope Adherence (30%)** (`feat(auth)` should not touch payment/config — *this is the invariant/ownership-boundary check at the diff level*), **Side-Effect Detection (20%)** (shared modules touched without mention), **Structural Proportionality (15%)** (1-line fix rewriting 3 files → scrutiny). CI ladder ALIGNED/DRIFTING/SUSPECT/MISALIGNED with configurable fail thresholds; pre-commit hook; SARIF. Explicitly targets "individual devs using Cursor/Copilot/Claude/Devin." This is the closest to **"this task crosses an invariant/ownership boundary"** stated in the prompt.
4. **`NexumCorpus/Nexum-Graph`** (Mar 2026, TS/Python/Rust) — semantic graph + **multi-agent coordination against that graph** + **semantic LOCKS** (`nex lock`/`nex validate` lock coverage before commit; CRDT-backed lock state) + `nex check --install-hook` installs a **`pre-merge-commit` git hook** for branch-conflict detection + tamper-evident audit log with replay/rollback. This is the only one that fuses *fan-out coordination* AND *pre-merge gating* AND *audit trail* in one system — closest architecturally to what the user is hand-rolling. Early (v0.1.0).
5. **`vk0dev/code-impact-mcp`** (Apr 2026) — the lightest: PASS/WARN/BLOCK in seconds, no DB, MIT, Husky hook. `analyze_impact` / `gate_check` / `detect_cycles`. **BLOCK = risk over threshold OR changed file in a cycle.** Full TS/JS; **Python is file-level only** (the genomics-relevant limitation).
6. Adjacent, language-specific: **`gosemdiff`** (Go; classifies MOVE/RENAME/REFACTOR/LOGIC, roadmap'd test-gap analysis "warn if no test for a LOGIC change" + breaking-API guard); **GauntletCI / "Behavioral Audit Layer"** (.NET/Roslyn; "Behavioral Change Risk" pessimistic pre-merge gate, "100% coverage can still hide a behavioral regression"); **`jamesaphoenix/diff-core`** (Rust core; flow-group clustering + review-ordering by data flow); **OpenLore `structural_diff`** (deterministic graph diff: signature changes + **stale callers** = callers in canonical graph NOT in this change = "what this edit may have broken under it" — the cleanest primitive for hub-blast-radius). Prior art for AST diffing itself = **difftastic**.

**Bottom line for axis 2C: do NOT build a semantic/blast-radius diff gate from scratch.** Multiple deterministic, MCP-native, gate-shaped tools exist (inspect, kai, vibediff, nexum-graph). Per CLAUDE.md "evaluate external tools as dependencies first": the evaluation order is **inspect** (best classification+untangling+MCP fit) → **kai** (most mature, test-coverage-aware, MCP) → **vibediff** (best intent/scope-boundary check) → **nexum-graph** (if you also want fan-out coordination + locks + audit in one). Open verification gaps before adopting: (a) Python parse-depth for each (genomics is Python; code-impact is file-level-only on Python, a known weak spot), (b) whether "invariant boundary" in genomics' sense (the 6 grading vocabularies / forward-strand / denominator-gating rules) is expressible — these are *domain* invariants, not import-graph or commit-message-scope invariants, so the OSS tools cover the structural half but **the domain-invariant half is genomics-specific and not in any tool** (that part is genuinely yours to build, but as a thin policy layer on top of an existing graph engine, not a new graph engine).

### D. Per-subtask acceptance-check / spec-then-decompose (WELL-ESTABLISHED as a planner pattern; NOT packaged as a hard gate)
This pattern is mature and converged in agent tooling — **per-subtask acceptance checks ARE a known, named pattern.** But it is a *planning convention enforced by prompts/checklists*, not a deterministic blast-radius gate. The two are complementary, not the same thing.

- **GitHub Spec Kit** (`github/spec-kit`, Aug 2025, 30 agent integrations incl. Claude/Codex/Gemini): the canonical **Spec → Plan → Tasks → Implement** SDD pipeline. `/speckit.tasks` generates tasks with: task breakdown **organized by user story**, **dependency ordering** (models→services→endpoints), **parallel-execution markers `[P]`**, **exact file paths per task**, **TDD structure (test tasks ordered before impl)**, and **checkpoint validation per user-story phase to validate independent functionality**. `/speckit.taskstoissues` converts to GitHub issues. There is an explicit **"Review & Acceptance Checklist"** the agent self-checks against the spec. (github.github.io/spec-kit primary)
- **Kiro** (AWS): **Prompt → Requirements → Design → Tasks → Code**. Each user story gets **EARS-notation acceptance criteria** (covering edge cases). Each task auto-includes **unit tests, integration tests, loading states, accessibility** and is **linked back to a requirement ID** so nothing falls through. *"Run all Tasks" analyzes dependencies and runs independent tasks concurrently.* Most relevant: **"requirements analysis"** — a neuro-symbolic step that **auto-formalizes requirements into formal logic and runs SMT solvers to flag ambiguous acceptance criteria, contradictions, and completeness gaps BEFORE design/code** — the only example found of formal pre-decomposition invariant checking. (kiro.dev/docs/specs, kiro.dev/blog/deep-spec-analysis — primary)
- **Claude Code `subagent-driven-development` skill** (jonathansblog, Apr 2026): orchestrator (1) decomposes into subtasks with **clear inputs/outputs/acceptance criteria per subtask**, (2) does **dependency mapping** → serialize dependent, parallelize independent, (3) focused context per agent, (4) **failure/retry at subtask level not whole-task**, (5) human reviews the decomposition before dispatch. Guidance: *"keep subtasks atomic — bounded set of files, verifiable independently."* This is essentially the user's target loop, already skill-ized.
- **Smart ticket scoping** (zachwills, Sep 2025): if estimated effort > 2 days, auto-split into 2–3 interconnected tickets each with its own scope — a **size-threshold-triggered decomposition**, the ticket-level analog of the user's >1500-line trigger.
- **Anthropic "Building Effective Agents"** (the canonical taxonomy): names **Prompt-chaining** (clean decomposable→fixed subtasks), **Parallelization** (independent subtasks for speed/confidence), **Orchestrator-workers** (subtasks NOT predictable in advance — determined by orchestrator at runtime; "in coding, the number of files to change depends on the task"). The user's loop is precisely **orchestrator-workers** (decompose-at-runtime), not prompt-chaining.

**Crucial counter-evidence (do not over-build):** AgentPatterns.ai cites *"Do More Agents Help? Controlled and Protocol-Aligned Evaluation"* — across 10 benchmarks, **most multi-agent configs UNDERPERFORMED a single-agent baseline; only 1 of 6 workflows beat it.** Parallel dispatch pays off ONLY when subtasks are genuinely independent; adding workers to a task that doesn't decompose cleanly buys coordination cost with no quality return. And a review of 94 multi-agent SE papers (arXiv:2511.08475) confirms parallelism+specialization as the *rationale* but the benefit is **conditional, not automatic**. Multi-agent systems consume **~15× the tokens of chat** (Anthropic) — task value must justify it. **This is the strongest reason the decomposition GATE (axis 2) matters more than the fan-out itself: the gate is what decides whether a task decomposes cleanly enough to be worth fanning out.**

## Axis 3 — The "expect garbage → decompose if too big → fan out" pattern itself

### Is the full loop named/published? PARTIALLY — its three components are each named; the *composite* (garbage-first + size-gated decompose + fan-out) is not a single branded pattern, but each piece has a name and the composite is folklore practitioners describe.
- **"Draw the rest of the owl"** is an established meme for the leap from trivial first step to hard finish; it surfaces in agentic-coding writing as shorthand for "the loose first attempt won't be the deliverable." Not formalized as a method.
- The **size-threshold-triggered decompose** = zachwills' "smart ticket scoping" (>2 days → split) and Kiro/spec-kit task-splitting. Threshold-based splitting is real and shipped.
- The **fan-out** = orchestrator-workers (Anthropic taxonomy) / "parallel coding agent lifestyle" (Simon Willison, via Pragmatic Engineer Oct 2025). Willison's key admission frames the whole bottleneck: *"I can only focus on reviewing and landing one significant change at a time… the natural bottleneck is how fast I can review the results."* → **review throughput is THE constraint, which is exactly why a diff-size review threshold is the right gate variable.**
- **"Expect garbage" first pass** maps to the well-known agentic stance of iterate-from-a-rough-draft; closest formalization is the orchestrator-worker "synthesis is a reasoning step, not aggregation" + Clouâtre's SCOUT(rough)→GUARD(adversarial)→PLAN→BUILD→CHECK pipeline (fresh context per phase, JSON handoffs in `$WORKTREE/.handoff/`).

### (a) Diff-size thresholds for human reviewability — STRONG EMPIRICAL CONVERGENCE (the most quantitatively solid finding in this whole scan)
Multiple independent studies converge on the **200–400 changed-lines** band:
- **SmartBear/Cisco study** (2006, 2500 reviews / 10 months — the foundational dataset): defect *density* highest below 200 LOC; review effectiveness drops sharply above 400 LOC; **200–400 LOC over 60–90 min yields 70–90% defect discovery**; defect-discovery rate starts falling above ~300 LOC, significant tail-off above 500. Reviewer effectiveness ceiling ≈ **400 LOC in one sitting** (cognitive fatigue after 60–90 min). (tekin.co.uk, opensource.com, brunoarine.com)
- **Google internal**: review quality degrades above 200 lines; **median time-to-review DOUBLES per +100 lines**; PRs >500 lines have much higher post-merge defect rate. Soft limit 400, hard limit 600 → must split. (em-tools.io, deployhq.com)
- **Propel Code 50,000+ PR / 200+ team study** (the largest cited): **200–400-line PRs have ~40% fewer defects than larger PRs; PRs >1,000 lines have <half the defect-detection rate of small PRs; 3× faster review cycles under 400.** One team's **automated warning for PRs >400 lines → 35% reduction in post-merge defects.** (propelcode.ai, tiniacoleyba.com)
- **cubic.dev**: 50-line PRs are **15% less likely to be reverted** than 250-line; focus fatigue after 60 min.
- **Caveat to the user's 1500-line trigger**: the literature's actionable threshold for *human reviewability* is **200–400 lines (hard split at ~600)**, an order of magnitude below 1500. A 1500-line trigger is fine as the "this is definitely garbage / must decompose" alarm, but the *terminal* review-threshold (the "under threshold → stop decomposing, hand to human") should be **~200–400 lines**, not 1500, if the goal is genuine reviewability. The one nuance everyone repeats: **a pure mechanical rename can be 400+ lines and trivially reviewable** (gustavwengel, tiniacoleyba) — so **"time-to-review < ~60 min" / single-logical-change is a better terminal predicate than raw line count.** Use line count as the cheap trigger, logical cohesion + reviewable-in-an-hour as the real gate.

### (b) Decompose-vs-monolith agent output quality — CONDITIONAL, see Axis-2D counter-evidence
"Do More Agents Help?" (10 benchmarks): most multi-agent configs underperformed single-agent; benefit only when subtasks genuinely independent. So **decompose-then-fan-out is NOT free quality** — it wins on *clean* decompositions and *loses* (coordination cost, integration bugs) on tasks that don't cleanly split. The subagent-driven-development skill's own warning: if the orchestrator gets dependencies wrong, "you get integration problems." [GAP: no head-to-head "monolithic agent vs decomposed-fan-out on the SAME feature task, diff-quality measured" study surfaced — this specific A/B appears unpublished.]

### (c) Parallel-agent merge-conflict rates — NO HARD NUMBERS FOUND; qualitative consensus only
No study quantifying merge-conflict *rate* across parallel agents surfaced. Qualitative consensus is unanimous and prescriptive:
- Merge conflicts are *the* #1 failure mode of parallel worktrees (codewithseb: "merge hell when two sessions edit overlapping code").
- The fix is **prevention by module-scoping at decomposition time** (never let two agents own the same file) + **rebase-not-merge** + Aviator's affected-targets disjoint-queue model — i.e. the conflict rate is meant to be driven toward zero *structurally* by the decomposition, so nobody measures a residual rate. [GAP: an empirical parallel-agent merge-conflict-rate study would be novel; none exists publicly as of this scan.]

## Synthesis

`[INFERENCE]` over the three axes, oriented to the agent-infra decision (the operator's feature-work loop, homed here):

**1. Isolation is a solved commodity — do not build.** `[SOURCE: §1 vendor docs]` Every harness converged on git-worktree-per-agent (+ container-per-task for runtime); Claude Code ships it (`-w`, subagent `isolation: worktree`, `/batch`). The field's own verdict (rustman, §1): isolation is no longer the bottleneck — **decomposition quality and review throughput are.**

**2. Decomposition / blast-radius gating — buy the structural half, build only the domain half (thin).** `[SOURCE: §2A/§2C]` Affected-graph (Nx/Bazel) and a 2026 cluster of MCP-native diff-gates (`inspect`, `kai`, `vibediff`, `nexum-graph`) already do change-classification + blast-radius + commit-untangling + scope-boundary checks. Per "evaluate as dependencies first," any eventual gate = `inspect`/`kai` + a thin domain-invariant policy layer — `[INFERENCE]` NOT a from-scratch engine. `[UNVERIFIED]` Python parse-depth — probe before adopting (`code-impact-mcp` is file-level-only on Python).

**3. The bottleneck is review throughput; the numbers that would justify a gate don't exist.** `[SOURCE: §3]` Willison: *the natural bottleneck is how fast I can review.* Human reviewability tops out at **200–400 changed lines / ~60 min** `[SOURCE: SmartBear, Google, Propel Code]` — so the 1500-line trigger is a fine "definitely-decompose" alarm but **~10× too high as the terminal review gate**; the real terminal predicate is *single-logical-change / reviewable-in-an-hour*. Decompose-vs-monolith quality is **conditional, not free** `[SOURCE: "Do More Agents Help?" — 1/6 workflows beat single-agent]`; parallel-agent merge-conflict rate has **no published number** `[INFERENCE: GAP]`.

**Decision-relevant bottom line `[INFERENCE]`:** the review side of the loop is already a live agent-infra experiment (`risky_diff_review_shadow.py`, promote/cut ~2026-06-21). The genuinely open, non-duplicative, telos-aligned work is to **measure the decompose / fan-out / merge moments** — the numbers §3b/§3c say nobody has — on the existing substrate (`agentlogs`, `loop_funnel`, `supervision-kpi`), and gate any gate-build on that measured demand. Build-first here repeats the repo's documented build-then-undo failure (`decisions/2026-06-13-rsi-outer-loop-skill.md` FINDING 5).
